## ルールの洗い出しと正常系・異常系の分類

### 機能名: 起動準備とホーム画面表示
**機能概要:** 設定の読み込みが完了して起動準備画面に到達した後、進行中であることを示しながら、設定画面のタブレット名・設置空間に不備がないかを確認する。不備があれば設定画面へ誘導し、不備がなければ予約認証モードで各種データを並列に取得し、顔情報の同期を除くすべての取得が揃った時点でホーム画面を表示する。揃わない間はホーム画面へ遷移せず、待機理由と再試行の秒数を示しながら30秒間隔で再試行する。

**起動準備の処理順序:** ①進行表示の開始 → ②共通セットアップ（Firestoreリスナーの配線） → ③設定の不備確認 → ④並列データ取得（顔情報の同期を除くすべてが揃うまで待ち、揃わない間は待機表示のまま30秒間隔で未完了の処理のみ再試行） → ⑤すべて揃った後にホーム画面へ遷移。③で不備が見つかった場合のみ、④以降は実行されない。

**責務の切り分け:** 以下は本機能の対象外とし、記載のチケットで検証する（`_master/feature-map.html` の決定台帳を参照）。

| 対象外とする処理 | 移管先のチケット | 台帳 |
| :--- | :--- | :--- |
| 端末の登録状態・初期設定の完了状態の判定、組織→タブレットID→端末設定の解決 | 設定値の読み込みが行える | #1〜#3 |
| 利用不可・利用時間外の表示 | 利用不可・利用時間外を表示できる | #5 |
| ホーム画面の表示状態（空室／待機中／使用中）と、予約データの反映内容・反映先 | ホーム画面の予約・予約状態の更新 | #9 |
| 起動準備中に実行される顔情報の同期 | 顔の特徴量を同期できる | #6 |
| オフライン起動時の振る舞い | オフライン時のフォールバックを設計・検討できる | #7 |

### ルール①: 起動準備の実行中は進行中であることが示され、利用者の操作を受け付けない
**推奨テスト階層:** Presentation Unitテスト (JVM / Turbine)
**割り振り理由:** 進行表示の開始・継続・解除はViewModelの状態変化であり、実機描画なしで検証できるため。

> 本ルールの「操作できる要素は表示されない」は、並列データ取得が進行している間を対象とする。取得が揃わないまま滞留した場合の待機表示とログアウト動線はルール⑤で定める。

| 対象 | 状況 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 起動準備画面 | 画面の表示直後 | 🟢 正常系：起動準備画面に到達する | 「設定を反映しています」という進行中の表示が現れる |
| 起動準備画面 | 並列データ取得の実行中 | 🟢 正常系：起動準備の処理が続いている | 進行中の表示が維持され、操作できる要素は表示されない |
| 起動準備画面 | ホーム画面への遷移時 | 🟢 正常系：起動準備が完了する | 進行中の表示が解除される |

---

### ルール②: 設定画面のタブレット名・設置空間に不備があると、起動準備は中断され設定画面へ誘導される
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 設定の不備判定とその後の分岐（設定画面への誘導／起動準備の継続）を、外部依存をFakeに差し替えて通しで検証する必要があるため。

> 不備を検出して設定画面へ送り返すのは本機能の責務（台帳 #4）。タブレット名・設置空間を入力するのは初期設定と設定画面の責務であり、誘導された後の設定画面の挙動（キャンセルが提供されないこと）は「管理者が予約認証の設定を変更できる」で検証する。

| 対象 | 設定の状態 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 端末 | タブレット名・設置空間ともに設定済み | 🟢 正常系：設定に不備がない状態で起動準備を開始する | 設定画面へは遷移せず、並列データ取得（ルール③・④）が開始される |
| 端末 | タブレット名が未設定（空文字） | 🔴 異常系：タブレット名が空の状態で起動準備を開始する | 予約データの取得は行われず、設定画面へ遷移して設定を促す |
| 端末 | 設置空間が未設定（未選択または空） | 🔴 異常系：設置空間が未設定の状態で起動準備を開始する | 予約データの取得は行われず、設定画面へ遷移して設定を促す |

---

### ルール③: 顔情報の同期を除く並列処理がすべて揃うまで、ホーム画面へ遷移しない
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 複数の並列処理の完了待ち合わせと、揃った時点での遷移を、各処理をFakeに差し替えて通しで検証する必要があるため。

> 待ち合わせの対象は①スペースデータのローカル展開、②解錠デバイスの取得と接続確認待ち（台帳 #8）、③予約データ4種の初回取得（ルール④）の3つ。**顔情報の同期は待ち合わせの対象に含めない**（台帳 #6 のとおり「顔の特徴量を同期できる」で検証する）。
> ①スペースデータのローカル展開はローカルキャッシュを1回読むだけで、読み込みに失敗しても例外を握りつぶして完了として扱うため、未完了のまま滞留する状況は発生しない（ユーザーから観測できないためルール化しない）。
> 参照元（iOS）にある「全体60秒を超えたら打ち切ってホーム画面へ進む」挙動は、Android版では採らない（台帳 #12）。揃わない間の待機表示と再試行はルール⑤で定める。

| 対象 | 状況 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 起動準備 | 対象の並列処理がすべて完了 | 🟢 正常系：スペースデータの展開・解錠デバイスの接続確認・予約データの初回取得がすべて完了する | ホーム画面へ遷移する |
| 起動準備 | 解錠デバイスの接続確認が未完了 | 🟡 例外系：予約データは揃ったが、解錠デバイスの接続確認が完了しない | ホーム画面へ遷移せず、待機表示のまま再試行が続く（ルール⑤） |
| 起動準備 | 予約データが未受信 | 🟡 例外系：解錠デバイスの接続確認は完了したが、予約データが揃わない | ホーム画面へ遷移せず、待機表示のまま再試行が続く（ルール⑤） |

---

### ルール④: 予約認証モードでは、予約データ4種すべての初回受信をもって「揃った」と判定する
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 予約一覧・空間ステータス・予約設定・利用不可時間の初回到着判定を含むユースケースフローであり、受信状況をFakeで再現して通しで検証する必要があるため。

> 対象は予約一覧・空間ステータス・予約設定・利用不可時間の4種。**受信した内容が空（予約が0件・利用不可時間の設定なし）であっても「揃った」とみなす**。
> 参照元（iOS）は4種すべてが非空になることを条件に最大10秒待って打ち切る実装だが、Android版では空の受信も到着として扱い、打ち切りは行わない（台帳 #12・2026-10-21 のリファインメントでの決定）。

| 対象 | 状況 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| タブレット | 予約認証モード | 🟢 正常系：起動準備を開始する | 予約データ準備が実行され、Firestoreリスナーが配線されて予約一覧・空間ステータス・予約設定・利用不可時間の取得が始まる |
| 予約データ | 4種すべてを受信 | 🟢 正常系：4種すべての初回データを受信する | 予約データは揃ったものとして扱われ、ホーム画面への遷移条件（ルール③）を満たす |
| 予約データ | 内容が空のまま4種すべてを受信 | 🟢 正常系：対象空間に予約が0件で、利用不可時間の設定もない状態で4種すべてを受信する | 内容が空でも揃ったものとして扱われ、ホーム画面へ遷移する |
| 予約データ | 4種のうち一部のみ受信 | 🟡 例外系：予約一覧のみ受信し、残り3種が未受信のまま | 揃っていないものとして扱われ、ホーム画面へは遷移せず待機表示となる（ルール⑤） |

---

### ルール⑤: 並列処理が揃わない間は待機理由と再試行の秒数が示され、30秒間隔で未完了の処理のみ再試行される
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 待機状態への切り替え・再試行の間隔と対象・ログアウト動線の表示条件を、時間経過をFakeで再現して通しで検証する必要があるため。

> 「設定値の読み込みが行える」（⑥ SettingLoader ルール④・⑤）の復旧待ちと同じ方式を採る。最初の試行から30秒が経過しても揃わない場合に待機表示へ切り替え、**30秒間隔・上限なし**で**未完了の処理のみ**再試行する。
> ログアウト動線は最初から出さず、**3回目の再試行が完了した時点**（30秒間隔のため最初の試行から約90秒後）で表示する。それまでは利用者の操作を求めない。なお⑥ SettingLoader の閾値（再試行10回超過）は変更しない。
> ログアウト動線を選択すると即座にログアウトせず、「ログアウトしますか」の確認ダイアログを挟む。確定した場合のみログイン画面へ戻る。確認ダイアログ自体の挙動（キャンセル・ダイアログ外タップ・バックキーなど）は別チケットで切り出して検証するため、本機能では扱わない。

| 対象 | 状態 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 起動準備画面 | 待機表示への切り替え | 🟡 例外系：最初の試行から30秒が経過しても並列処理が揃わない | ホーム画面へは遷移せず、待っている理由（未完了の処理）と次の再試行までの秒数が表示される |
| 起動準備画面 | 再試行の対象 | 🟡 例外系：予約データのみ未受信の状態で30秒が経過する | 完了済みの処理はやり直されず、未完了の処理（予約データの取得）のみが再試行される |
| 起動準備画面 | 待機の継続（2回目の再試行の完了まで） | 🟡 例外系：再試行が2回目まで完了しても並列処理が揃わない | 待機理由と再試行の秒数が表示され続け、エラーダイアログは表示されず、ログアウト動線も表示されない |
| 起動準備画面 | 待機の継続（3回目の再試行の完了時点） | 🟡 例外系：3回目の再試行が完了しても並列処理が揃わない | ログアウト動線が表示される（待機理由と再試行の秒数の表示は継続する） |
| 起動準備画面 | 待機中に揃う | 🟢 正常系：再試行によって未完了だった処理が完了する | 待機表示が解除され、ホーム画面へ遷移する |
| 起動準備画面 | 利用者がログアウトを選択 | 🟢 正常系：ログアウト動線を選択し、確認ダイアログでログアウトを確定する | 「ログアウトしますか」の確認ダイアログを経て、ログイン画面へ戻る |

- [ ] ログアウトの確認ダイアログの具体（文言・ボタンのラベル・ダイアログ外タップ／バックキーでの閉じ方、確定後に進行中の再試行を停止するか）は未確定。ダイアログ自体の挙動は別チケットで扱うため、ルール⑤では「確認を挟んだうえで確定するとログイン画面へ戻ること」までを期待結果としている
