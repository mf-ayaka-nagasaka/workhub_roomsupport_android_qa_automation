## ルールの洗い出しと正常系・異常系の分類

### 機能名: 管理メニュー
**機能概要:** タブレット設置管理者が、特定のジェスチャー操作から起動する隠し管理メニューを、パスワードまたは顔認証で保護した上で開き、端末情報確認・基本設定の更新・顔認証関連管理・ログアウトを行う。

---

### ルール①: 特定のジェスチャー操作で管理メニューの認証画面をトリガーできる
**推奨テスト階層:** Presentation Unitテスト (Turbine)
**割り振り理由:** ジェスチャー検知→認証画面表示のUI状態遷移を検証するため。

| 対象 | 状態 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| ホーム画面のWorkhubロゴ | 未認証 | 🟢正常系：ロゴをダブルタップ後、指を離さず1.5秒以上長押しする | パスワード入力画面 or 顔認証ダイアログが表示される |
| 予約認証のカメラ認証画面の画面背景 | 未認証 | 🔴異常系：認証が必要な操作を実行してカメラ認証画面を表示し、画面背景で同様の操作を行う | トリガーされない（何も起こらない。予約認証のカメラ認証画面にはトリガー自体が実装されていない） |
| ホーム画面のWorkhubロゴ | 未認証 | 🔴異常系：ダブルタップのみで長押ししない | 何も起こらない |
| ホーム画面のWorkhubロゴ | 未認証 | 🔴異常系：ダブルタップ後、2秒以上経ってから長押しする | トリガーされない（タップ状態がリセットされる） |
| 管理メニュー（基本設定の更新から復帰） | **認証済み**（管理メニュー→基本設定の更新→設定画面を離脱） | 🟡例外系：管理メニューから「基本設定の更新」を選び、設定画面で保存/離脱操作を行う | パスワード・顔認証を経由せず、直接管理メニューのメインメニューに戻る |

**注記:** RoomSupport Android版は予約認証モードのみで運用されるため、iOS版で常時認証モードのカメラ認証画面に実装されているトリガー（画面背景への長押し）は対象外。トリガー対象は**ホーム画面のWorkhubロゴのみ**であり、カメラ認証画面（予約認証モード）にはロゴの表示もトリガーの実装もない。チケット記載の「カメラ認証画面が表示されている」という前提は、Android版では管理メニューのトリガー元にはならない点に注意。
ここでいう**予約認証のカメラ認証画面**とは、ホーム画面で認証が必要な操作（主ボタン「今すぐ入室」「入室する」「退室する」、および延長・再解錠・キャンセル等のサブボタン）を実行した後に表示される認証画面を指す。操作そのものの成否は各操作のチケットの責務であり、本ルールは**その画面に管理メニューのトリガーが存在しないこと**のみを対象とする。

### ルール②: 顔認証設定の有無で認証方式が自動選択される
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 端末設定の判定→認証方式分岐の一連ロジックを検証するため。

| 顔認証設定 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| 有効 | 🟢正常系：顔認証有効の端末でトリガー | 2Dジェスチャー方式の顔認証ダイアログが表示される |
| 無効 | 🟢正常系：顔認証無効の端末でトリガー | パスワード入力画面が表示される |

**注記:** Android版のなりすまし防止は、3Dの深度判定が利用できないため、**利用者に指示した動作を行わせる2Dジェスチャー方式**で実装する。管理メニューの顔認証ダイアログにもこの方式を導入するため、端末の3D対応可否による認証方式の分岐は存在しない。

### ルール③: 顔認証はスーパーユーザー（bitkey.jpドメイン かつ システム管理者権限保有）かつ非テナントの人物のみ管理メニューへの入室が許可される
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 顔認証結果受け取り→権限判定（スーパーユーザー／非テナント）→画面遷移のユースケースフローを検証するため。

| 対象人物 | 認証結果 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| スーパーユーザー（bitkey.jpドメイン＆システム管理者権限、非テナント） | 認識成功 | 🟢正常系：本人の顔で認証成功 | メインメニューが表示される |
| bitkey.jpドメインだがシステム管理者権限を持たないアカウント | 認識成功 | 🔴異常系：ドメインは一致するが権限なし | 「管理メニューを開く権限がありません」エラー表示＋トップ画面へ遷移 |
| システム管理者権限はあるがbitkey.jp以外のドメインのアカウント | 認識成功 | 🔴異常系：権限はあるがドメイン不一致 | 同上（権限なしエラー） |
| スーパーユーザーだがテナント所属扱いの人物 | 認識成功 | 🔴異常系：スーパーユーザー条件を満たすがテナント扱い | 同上（権限なしエラー） |
| - | 指示された動作を実施 | 🟢正常系：ダイアログに表示された指示（アイコンと文言）どおりの動作を規定回数行う | 顔の照合が進み、権限判定の結果に応じた画面が表示される |
| - | 指示と異なる動作 | 🔴異常系：指示とは異なる動作を行う | 「顔の動きが正しくなかったため もう一度最初からやりなおしてください」が表示され、最初の指示からやり直しになる |
| - | 時間内に動作しない | 🔴異常系：指示された動作を行わないまま待つ | 「顔が認識できませんでした。もう一度最初からやりなおしてください」が表示され、最初の指示からやり直しになる |
| - | なりすましを検知 | 🔴異常系：写真・動画をかざす／静止しない／距離が遠い | 検知の理由に応じた案内（「もう一度画面に顔を映してください」「静止してください」「画面に少し近づいてください」）が表示され、ダイアログは閉じず認識を継続する |
| - | 顔が端末に未登録 | 🔴異常系：顔情報が登録されていない人物（別組織の人物を含む）が認証を試みる | 「顔情報が未登録です」が表示され、ダイアログは閉じず認識を継続する |
| - | 端末内の顔情報と不整合 | 🟡例外系：顔は認識されたが、特徴量に対応する顔情報が端末内に無い（同期未完了・キャッシュ不整合） | 画面には何も表示されず、カメラでの認識を継続する |
| - | 顔が検出されない | 🟡例外系：画角から外れる | 新しい案内は表示されず、直前に表示された案内が残ったまま認識を継続する |
| - | 位置・角度・環境の不備を検知 | 🟡例外系：遠い／近い／上下左右にずれる／正面を向いていない／マスク／暗い・明るい | 検知した理由に応じた案内（「画面に少し近づいてください」「正面を向いてください」「マスクを外してください」等）が表示され、ダイアログは閉じず認識を継続する |
| - | - | 🟢正常系：顔認証ダイアログで「パスワード認証」を選択 | パスワード入力画面に切り替わる |
| - | - | 🟢正常系：顔認証ダイアログで「キャンセル」を選択する、またはダイアログ外を押下する | 認証を中断し元の画面（トップ）へ戻る |

**注記:** 2Dジェスチャー方式の指示は、**指示する動作に応じたアイコンと文言**をダイアログに表示する。動作は「左を向く／右を向く／下を向く／目を閉じる」の4種で、規定回数ぶん繰り返される。各検知理由の文言はSDKが返す結果に対応するため、本ルールでは**アプリがその結果を正しく表示・継続に反映できているか**を対象とし、SDKの判定精度そのものは対象外とする。

### ルール④: 正しいパスワードで管理メニューを開ける
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** パスワード照合→メニュー表示のユースケースフローを検証するため。

| パスワード設定状態 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| 端末固有パスワード設定済み | 🟢正常系：設定済みの管理パスワードを入力 | メインメニューが表示される |
| **端末にパスワード未設定** | 🟡例外系：既定のデフォルト管理パスワードを入力 | メインメニューが表示される |
| いずれか | 🔴異常系：誤ったパスワード（空文字含む）を入力 | 画面遷移せずインラインでエラーメッセージが表示され、再入力できる（試行回数制限なし） |
| いずれか | 🟢正常系：「キャンセル」を選択 | 認証を中断しトップ画面へ戻る |

### ルール⑤: メインメニューの表示項目は顔認証設定の有無で切り替わる
**推奨テスト階層:** Presentation Unitテスト (Turbine)
**割り振り理由:** 端末設定値によるメニュー項目リストのUiState切り替えを検証するため。

| 顔認証設定 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| 有効 | 🟢正常系：メインメニュー表示 | タブレット情報／アクセスコントロールの確認／基本設定の更新／顔情報登録／顔情報の再取得／顔認識機能のデバッグ／ログアウト の7項目が表示される |
| 無効 | 🟢正常系：メインメニュー表示 | タブレット情報／アクセスコントロールの確認／基本設定の更新／顔認証アクティベーション申請／ログアウト の5項目が表示される（顔に関する3項目の代わりに申請のみ表示） |
| 有効→表示中に無効化 | 🟡例外系：メニュー表示中に端末設定がリモートで無効化された状態で「顔情報登録」「顔情報の再取得」「顔認識機能のデバッグ」のいずれかを押す | 「顔認証の利用が制限されています。利用する場合はBitkeyにお問い合わせください。」エラー表示（画面遷移しない）。エラーを閉じた後、メインメニューは実態に合わせて更新され、顔認証が無効な端末と同じ5項目の構成になる |

---

### ルール⑥: メインメニューの各項目選択で対応する情報表示・画面遷移が行われる
**推奨テスト階層:** Presentation Unitテスト (Turbine)
**割り振り理由:** ボタン押下によるUiState/Effect（シート表示・画面遷移）を検証するため。

| 選択項目 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| タブレット情報 | 🟢正常系：選択する | タブレット情報がシート形式で表示され、13項目（AppVersion／OrganizationId／tabletName／tabletId／UUID／UDID／SerialNumber／DeviceName／Battery／Access token refreshed at／Last AC Downloaded at／Access Control Cache Count／Last Face Downloaded at）が表示される |
| タブレット情報（解錠テスト） | 🟢正常系：解錠デバッグ設定が有効で、解錠デバイスが連携されている | 解錠テストボタンが表示される |
| タブレット情報（解錠テスト） | 🔴異常系：解錠デバッグ設定が有効だが、解錠デバイスが連携されていない | ボタンの代わりに、解錠デバイスが連携されていない旨のメッセージが表示される |
| タブレット情報（解錠テスト） | 🔴異常系：解錠デバッグ設定が無効 | 解錠テストボタンもメッセージも表示されない |
| タブレット情報（通知テスト） | 🟢正常系：選択する | 解錠デバッグ設定に関わらず、通知テストボタンが表示される |
| アクセスコントロールの確認 | 🟢正常系：ACローカルキャッシュ・解錠デバイス一覧・人物情報の3つが揃った状態で選択する | 最終取得日時と、人物コード・氏名・ゲート名の一覧がシート形式で表示される |
| アクセスコントロールの確認 | 🔴異常系：ゲートIDに一致する解錠デバイスが端末に無い | 該当する行は一覧に表示されない |
| アクセスコントロールの確認 | 🔴異常系：人物情報がサーバーから取得できない | 該当する行は一覧に表示されない |
| アクセスコントロールの確認 | 🟡例外系：対象が100件を超える | 表示上限のメッセージが表示され、100件までに制限される |
| アクセスコントロールの確認 | 🟡例外系：対象が0件 | 該当なしのメッセージが表示される |
| アクセスコントロールの確認 | 🟢正常系：フィルタに文字を入力する | 人物コード・メールアドレス・氏名・ゲート名のいずれかに部分一致する行だけが表示される |
| アクセスコントロールの確認 | 🟡例外系：最終取得日時が取得できない | 最終取得日時が unknown と表示される |
| 基本設定の更新 | 🟢正常系：選択する | ローディング表示後、設定画面へ遷移する |
| 顔情報登録（顔認証有効時） | 🟢正常系：選択する | 社員番号検索画面へ遷移する |
| 顔情報の再取得（顔認証有効時） | 🟢正常系：選択する | 顔認証キャッシュがリセットされる（画面遷移なし） |
| 顔認識機能のデバッグ（顔認証有効時） | 🟢正常系：選択する | 顔認識機能のデバッグ画面へ遷移する |
| 顔認証アクティベーション申請（顔認証無効時） | 🟢正常系：選択する | 申請中のローディング表示後、申請が送信される |

**注記:** アクセスコントロールの確認の一覧は、**①定期ダウンロードしたACローカルキャッシュ（既定30分間隔・端末設定で変更可）／②端末に読み込まれた解錠デバイス一覧／③サーバーから取得する人物情報** の3つが揃って初めて成立する。②③が欠けた行は一覧から除外されるため、揃っているかどうかは表示件数の差として観測できる。
**注記:** タブレット情報の各項目は、**項目が表示されること**を単体テストで確認し、**UDID・SerialNumber・Battery など端末やMDMに依存する値の妥当性**は実機で確認する。

### ルール⑦: 管理メニューを閉じるとトップ画面へ戻り認証状態がリセットされる
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 認証状態のリセット→画面遷移のユースケースフローを検証するため。

| 操作元 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| パスワード確認画面 | 🟢正常系：「キャンセル」を選択 | トップ画面に戻り認証状態がリセットされる |
| メインメニュー画面 | 🟢正常系：右上「閉じる」を選択 | トップ画面に戻り認証状態がリセットされる |
| 顔認証ダイアログ | 🟢正常系：「キャンセル」を選択 | トップ画面に戻る |

---

### ルール⑧: ログアウトで認証情報をクリアしログイン画面へ戻る
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 認証状態リセット→強制ログアウト処理→画面遷移の一連フローを検証するため。

| 対象 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| メインメニュー表示中の管理者 | 🟢正常系：「ログアウト」を選択 | 認証状態がリセットされた上で強制ログアウトが実行され、ログイン画面へ遷移する |

### ❓ 疑問点・未確認事項（赤カード）
- [ ] タブレット情報の「3D Anti Spoofing（Supported / Not Supported）」の項目をAndroid版でも表示するか。2Dジェスチャー方式に決定したため常に Not Supported となり、項目としての意味をなさない（本成果物の13項目からは除外している）。
- [ ] タブレット情報の解錠テスト・通知テストは、実行結果がアプリ画面に表示されない（iOS版はログ出力のみ）。Android版で成否のフィードバックを表示するか。
- [ ] 端末にパスワード未設定の場合の既定デフォルトパスワードの扱いをAndroid版でも同様に踏襲するか。
- [ ] 顔認証アクティベーション申請の送信失敗時に、ユーザーへエラーフィードバックを表示するか（iOS版コード上は成否に関わらずローディングが閉じるのみ）。
- [ ] 顔情報の再取得の完了時のユーザーへの完了フィードバック（トースト等）の有無（iOS版コード上は見当たらず）。
- [ ] 顔が画角から外れた際、直前に表示されていた案内をどう扱うか（iOS実装では案内が更新されず残る。Android版では案内を消す案をリファインメントへ提案中）。
