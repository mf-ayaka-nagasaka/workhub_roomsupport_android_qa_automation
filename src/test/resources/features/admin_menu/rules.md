## ルールの洗い出しと正常系・異常系の分類

### 機能名: 管理メニュー
**機能概要:** タブレット設置管理者が、特定のジェスチャー操作から起動する隠し管理メニューを、パスワードまたは顔認証で保護した上で開き、端末情報確認・設定更新・顔認証関連管理・ログアウトを行う。

---

### ルール①: 特定のジェスチャー操作で管理メニューの認証画面をトリガーできる
**推奨テスト階層:** Presentation Unitテスト (Turbine)
**割り振り理由:** ジェスチャー検知→認証画面表示のUI状態遷移を検証するため。

| 対象 | 状態 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| ホーム画面のWorkhubロゴ | 未認証 | 🟢正常系：ロゴをダブルタップ後、指を離さず1.5秒以上長押しする | パスワード入力画面 or 顔認証ダイアログが表示される |
| カメラ認証画面の画面背景 | 未認証 | 🔴異常系：画面背景で同様の操作を行う | トリガーされない（何も起こらない。カメラ認証画面にはトリガー自体が実装されていない） |
| ホーム画面のWorkhubロゴ | 未認証 | 🔴異常系：ダブルタップのみで長押ししない | 何も起こらない |
| ホーム画面のWorkhubロゴ | 未認証 | 🔴異常系：ダブルタップ後、2秒以上経ってから長押しする | トリガーされない（タップ状態がリセットされる） |
| 管理メニュー（設定更新から復帰） | **認証済み**（管理メニュー→設定更新→設定画面を離脱） | 🟡例外系：管理メニューから「設定更新」を選び、設定画面で保存/離脱操作を行う | パスワード・顔認証を経由せず、直接管理メニューのメインメニューに戻る |

**注記:** RoomSupport Android版は予約認証モードのみで運用されるため、iOS版で常時認証モードのカメラ認証画面に実装されているトリガー（画面背景への長押し）は対象外。トリガー対象は**ホーム画面のWorkhubロゴのみ**であり、カメラ認証画面（予約認証モード）にはロゴの表示もトリガーの実装もない。チケット記載の「カメラ認証画面が表示されている」という前提は、Android版では管理メニューのトリガー元にはならない点に注意。

---

### ルール②: 顔認証設定と端末性能の組み合わせで認証方式が自動選択される
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 端末設定・デバイス性能の判定→認証方式分岐の一連ロジックを検証するため。

| 顔認証設定 | 3Dなりすまし防止対応 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 有効 | 対応 | 🟢正常系：顔認証有効かつ対応端末でトリガー | 3Dなりすまし防止付き顔認証ダイアログが表示される |
| 有効 | **非対応** | 🟡例外系：顔認証有効だが非対応端末でトリガー | 顔認証は要求されず、パスワード入力画面が表示される（要確認：対象端末Kyocera KC-T306での扱い） |
| 無効 | - | 🟢正常系：顔認証無効の端末でトリガー | パスワード入力画面が表示される |

---

### ルール③: 顔認証はスーパーユーザー（bitkey.jpドメイン かつ システム管理者権限保有）かつ非テナントの人物のみ管理メニューへの入室が許可される
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 顔認証結果受け取り→権限判定（スーパーユーザー／非テナント）→画面遷移のユースケースフローを検証するため。

| 対象人物 | 認証結果 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| スーパーユーザー（bitkey.jpドメイン＆システム管理者権限、非テナント） | 認識成功 | 🟢正常系：本人の顔で認証成功 | メインメニューが表示される |
| bitkey.jpドメインだがシステム管理者権限を持たないアカウント | 認識成功 | 🔴異常系：ドメインは一致するが権限なし | 「管理メニューを開く権限がありません」エラー表示＋トップ画面へ遷移 |
| システム管理者権限はあるがbitkey.jp以外のドメインのアカウント | 認識成功 | 🔴異常系：権限はあるがドメイン不一致 | 同上（権限なしエラー） |
| スーパーユーザーだがテナント所属扱いの人物 | 認識成功 | 🔴異常系：スーパーユーザー条件を満たすがテナント扱い | 同上（権限なしエラー） |
| - | SDKが認識不可と判定（なりすまし検知・距離不適切等） | 🟡例外系：SDK側のエラー | ダイアログ内にインラインメッセージが表示され、ダイアログは閉じずカメラでの認識を継続する |
| - | 顔特徴は検出されたが対応する人物情報が取得できない | 🟡例外系：ローカル顔情報未同期・人物情報取得失敗 | 画面には何も表示されず、カメラでの認識を継続する |
| - | - | 🟢正常系：顔認証ダイアログで「パスワード認証」を選択 | パスワード入力画面に切り替わる |
| - | - | 🟢正常系：顔認証ダイアログで「キャンセル」を選択 | 認証を中断し元の画面（トップ）へ戻る |

### ルール④: 正しいパスワードで管理メニューを開ける
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** パスワード照合→メニュー表示のユースケースフローを検証するため。

| パスワード設定状態 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| 端末固有パスワード設定済み | 🟢正常系：設定済みの管理パスワードを入力 | メインメニューが表示される |
| **端末にパスワード未設定** | 🟡例外系：既定のデフォルト管理パスワードを入力 | メインメニューが表示される |
| いずれか | 🔴異常系：誤ったパスワード（空文字含む）を入力 | 画面遷移せずインラインでエラーメッセージが表示され、再入力できる（試行回数制限なし） |
| いずれか | 🟢正常系：「キャンセル」を選択 | 認証を中断しトップ画面へ戻る |

---

### ルール⑤: メインメニューの表示項目は顔認証設定の有無で切り替わる
**推奨テスト階層:** Presentation Unitテスト (Turbine)
**割り振り理由:** 端末設定値によるメニュー項目リストのUiState切り替えを検証するため。

| 顔認証設定 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| 有効 | 🟢正常系：メインメニュー表示 | タブレット情報／ACデータ表示／設定更新／顔登録／顔キャッシュリセット／顔認証デバッグ／ログアウト の7項目が表示される |
| 無効 | 🟢正常系：メインメニュー表示 | タブレット情報／ACデータ表示／設定更新／顔認証利用申請／ログアウト の5項目が表示される（顔登録等3項目の代わりに利用申請のみ表示） |
| 有効→表示中に無効化 | 🟡例外系：メニュー表示中に端末設定がリモートで無効化された状態で「顔登録」を押す | 「顔認証が有効化されていません」エラー表示（画面遷移しない） |

---

### ルール⑥: メインメニューの各項目選択で対応する情報表示・画面遷移が行われる
**推奨テスト階層:** Presentation Unitテスト (Turbine)
**割り振り理由:** ボタン押下によるUiState/Effect（シート表示・画面遷移）を検証するため。

| 選択項目 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| タブレット情報 | 🟢正常系：選択する | タブレット情報がシート形式で表示される |
| ACデータ表示 | 🟢正常系：選択する | アクセスコントロール（施解錠連携）キャッシュデータがシート形式で表示される |
| 設定更新 | 🟢正常系：選択する | ローディング表示後、設定画面へ遷移する |
| 顔登録（顔認証有効時） | 🟢正常系：選択する | 対象者検索画面へ遷移する |
| 顔キャッシュリセット（顔認証有効時） | 🟢正常系：選択する | 顔認証キャッシュがリセットされる（画面遷移なし） |
| 顔認証デバッグ（顔認証有効時） | 🟢正常系：選択する | 顔認証デバッグ画面へ遷移する |
| 顔認証利用申請（顔認証無効時） | 🟢正常系：選択する | 申請中のローディング表示後、申請が送信される |

---

### ルール⑦: 管理メニューを閉じるとトップ画面へ戻り認証状態がリセットされる
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 認証状態のリセット→画面遷移のユースケースフローを検証するため。

| 操作元 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| パスワード確認画面 | 🟢正常系：「キャンセル」を選択 | トップ画面に戻り認証状態がリセットされる |
| メインメニュー画面 | 🟢正常系：右上「閉じる」を選択 | トップ画面に戻り認証状態がリセットされる |
| 顔認証ダイアログ | 🟢正常系：「キャンセル」を選択 | トップ画面に戻る |

---

### ルール⑧: ログアウトで認証情報をクリアしログイン画面へ戻る
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 認証状態リセット→強制ログアウト処理→画面遷移の一連フローを検証するため。

| 対象 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- |
| メインメニュー表示中の管理者 | 🟢正常系：「ログアウト」を選択 | 認証状態がリセットされた上で強制ログアウトが実行され、ログイン画面へ遷移する |

### ❓ 疑問点・未確認事項（赤カード）
- [ ] トリガー操作をAndroid版でどう再現するか（iOS版は「ダブルタップ→1.5秒以上長押し」の複合ジェスチャー。チケット記載の単純な「ロゴ長押し」で良いか、同じ複合ジェスチャーにするか）。
- [ ] 対象端末Kyocera KC-T306（Android 15）が3Dなりすまし防止（depth sensing）に対応していない場合、Android版で顔認証による管理メニュー入室機能自体を提供するか（常にパスワードのみにするか、2Dモードで許可するか）。開発チームへの確認が必要。
- [ ] 端末にパスワード未設定の場合の既定デフォルトパスワードの扱いをAndroid版でも同様に踏襲するか。
- [ ] パスワード誤り時の試行回数制限（iOS版には制限なし）をAndroid版で新設するか。
- [ ] 顔認証利用申請の送信失敗時に、ユーザーへエラーフィードバックを表示するか（iOS版コード上は成否に関わらずローディングが閉じるのみ）。
- [ ] 顔キャッシュリセット完了時のユーザーへの完了フィードバック（トースト等）の有無（iOS版コード上は見当たらず）。
- [ ] 管理メニューを閉じた際の遷移先を「常にトップ画面固定」にするか、「入室前の画面（ホーム／カメラ認証画面）に戻す」にするか（iOS版は常にトップ画面固定）。
