## ルールの洗い出しと正常系・異常系の分類

### 機能名: QRコードで利用者を特定できる

**機能概要:** カメラ認証画面（予約認証モード用）で、カメラに映ったQRコードから利用者本人を特定し、特定結果を持って操作ごとの画面へ進むまでを扱う。読み取ったQRコードがどの認証失敗にあたるかの振り分けもここで扱う。解錠と入退室の更新はこの画面では行わず、特定結果を受け取った先の画面が行う。

**処理の順序:** ①ホーム画面の操作ボタンからカメラ認証画面に入ると、認証方法にQRコードが含まれる端末ではQRコードの読み取りが始まり、**認証待ち**になる → ②QRコードが読み取られると読み取りが止まり、**読み取りの演出**に変わる → ③読み取ったQRコードから解錠のアクセス権と人物が解決される → ④人物情報を取得し、認証手段をQRコードとした特定結果を持って、操作ごとの画面へ進む。③で解決できないときは、見出しが**照会中**に変わった後、QRコードの中身に応じた認証失敗になる。

> **注記:** 読み取りの演出が終わると見出しが「照会中です...」に変わる（演出の長さは参照元（iOS）で約1秒）。特定が演出より早く終わったときは照会中にならないまま画面が切り替わるため、**成功の判定には照会中の表示を使わず、操作ごとの画面へ進むことで判定する**。失敗のときは演出の完了を待ってから失敗の表示に切り替わるため、必ず一度は照会中になる。

**合否の判定:** 画面に出ている要素と、そこに書かれている文言で判定する。

**画面の要素の呼称:**

- **見出し** … 画面上部の案内（「QRコードまたは顔を画面に映してください」「照会中です...」など）
- **読み取りの演出** … QRコードが読み取られた直後の演出（画面中央の読み取り枠が縮み、画面が暗くなる）。合否の判定には使わない
- **失敗の表示** … 認証に失敗したときに出る、エラーメッセージを伴う表示
- **受付の案内** … 受付が済んでいない人のQRコードを読んだときに出る専用の表示（「受付が未完了です」）

### ルール②: 読み取ったQRコードの中身によって、どの認証失敗になるかが決まる

> 失敗の表示・受付の案内そのものの見え方、出ている時間、認証待ちへの戻り方は⑭の範囲。ここでは**どのQRコードがどの失敗になるか**だけを見る（台帳 #51）。
>
> アクセス権を取得できなかったQRコードは、続けて受付用のQRコードかどうかが照会される。この照会の打ち切りまでの **5秒** は参照元（iOS）の実装値。
>
> 失敗のときは読み取りの演出が終わるのを待ってから失敗の表示に切り替わるため、**必ず一度は見出しが「照会中です...」になる**（実機で確認済み）。切り替わること自体の検証は⑭（台帳 #51）。
>
> **照会の打ち切りは、通信エラーとは別の失敗として扱う。** 打ち切りは回線がつながっていても起こり（サーバーの応答が遅いだけで5秒を超える）、利用者が取るべき次の行動も違うため（打ち切り＝もう一度かざせば成功しうる／オフライン＝かざし直しても直らない）。参照元(iOS)は両者を同じ `catch` でまとめてどちらも「インターネットに接続されていません」にしている（`ReservationCameraAuthenticationViewModel.swift:758-807`）ため、**Android版での新たな決定**として扱う（**赤カード③**）。具体的な文言は確定待ちのため、期待値は「**確認できなかったことが分かり、もう一度かざせばよいと分かること**」の粒度で記述する（文言そのものの確定は⑭へ申し送る）。
>
> **カギの有効時間の内か外かによる可否はルール⑤で見る。** 有効時間の外（開始前・終了後）は、このルールの「QRコードが不正です」には含めない。

| 対象 | QRコードの種類 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 利用者 | この部屋のアクセス権に人物が紐づかない | 🔴異常系：解錠の権限が無い人のQRコードをかざす | 見出しが「照会中です...」に変わった後、「解錠権限がありません」のメッセージが出る失敗の表示になる |
| ゲスト | 受付が済んでいない人の受付用QRコード | 🔴異常系：受付を済ませていないゲストが自分のQRコードをかざす（照会は打ち切りまでに終わる） | 見出しが「照会中です...」に変わった後、受付の案内（「受付が未完了です」）になる |
| 利用者 | この部屋では使えない、受付用でもない | 🔴異常系：他の部屋のQRコードをかざす | 見出しが「照会中です...」に変わった後、「QRコードが不正です」のメッセージが出る失敗の表示になる |
| 利用者 | アクセス権を取得できないQRコード | 🟡例外系：受付用かどうかの照会が通信エラーになる | 見出しが「照会中です...」に変わった後、「インターネットに接続されていません。(CODE: ◯◯)」のメッセージが出る失敗の表示になる |
| 利用者 | 受付が済んでいない人の受付用QRコード | 🟡例外系：受付用かどうかの照会が打ち切りの時間を超える | 受付の案内にはならず、確認できなかったことが分かり、もう一度かざせばよいと分かるメッセージが出る失敗の表示になる（通信エラーの文言とは区別される） |

### ルール③: 照会の間はQRコードを読み取らず、認証待ちに戻ると読み取りを再開する

| 対象 | 状況 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 従業員 | 同じQRコードを続けてかざす | 🟡例外系：QRコードが読み取られた直後に、同じQRコードをもう一度かざす | 2回目の照会は始まらず、1回だけ操作ごとの画面へ進む |
| 従業員2名 | 照会の間に別の人が割り込む | 🟡例外系：1人目のQRコードが読み取られた直後に、2人目が自分のQRコードをかざす | 2人目の照会は始まらず、1人目の特定結果だけで操作ごとの画面へ1回だけ進む |
| 従業員 | 顔での照会の間にQRコードをかざす | 🟡例外系：顔が一致して照会が始まった直後に、QRコードをかざす | QRコードは読み取られず、顔での特定結果だけで操作ごとの画面へ進む |
| 利用者 | 失敗の後にやり直す | 🟢正常系：失敗の表示が消えて認証待ちに戻った後、有効なQRコードをかざす | 人物が特定されて操作ごとの画面へ進む |

### ルール④: カメラ認証画面に入った後にネットワークが切れても、端末内の控えにアクセス権があればQRコードで特定できる（**理想の振る舞いの提案**）

> 対象は**カメラ認証画面に入った後に回線が切れた場合**のみ。予約認証モードでは、ホーム画面がオフラインを検知すると画面全体に進行表示を出して操作を受け付けなくなるため（`MainMenuViewModel.swift:766-772`）、**オフラインの状態から新たにカメラ認証画面へ入ることはできない**。オフラインの状態から操作を始められるかどうかと、オフライン全般の方針は㉛の範囲（台帳 #53）。
> 控えに記録が無いときは、続けて行われる受付用かどうかの照会もネットワークが要るため失敗し、**オフラインであることが分かるメッセージ**（通信エラーの扱い）になる。照会の打ち切りとは区別される（ルール②）。
> 本ルールは参照元（iOS）の実装の延長ではなく、**Android版での新たな提案**として書いている（**赤カード①**）。

| 対象 | 端末内の控え | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 従業員 | アクセス権の記録がある | 🟡例外系：カメラ認証画面に入った後に回線が切れ、有効なQRコードをかざす | 人物が特定され、操作ごとの画面へ進む |
| 利用者 | アクセス権の記録が無い | 🟡例外系：カメラ認証画面に入った後に回線が切れ、控えに記録の無いQRコードをかざす | 特定されず、オフラインであることが分かるメッセージが出る失敗の表示になる |

### ルール⑤: QRコードに紐づくカギの有効時間の内側でだけ、QRコードで利用者を特定できる

> カギの有効時間は管理画面で設定する（予約に紐づいて自動発行されるカギは「予約開始の◯分前から予約終了の◯分後まで」）。**分数そのものはこの成果物には書かず**、有効時間の内側／外側で判定する。
> アプリは読み取ったQRコードから**現時刻で使用可能なアクセス権**だけを取り出すため、有効時間の外側のカギは取り出せない（`AccessControlV1Service.swift:135-143`・`AccessControl.swift:84-97`）。境界ちょうど（開始ちょうど・終了ちょうど）は使える側。
> 参照元（iOS）では、有効時間の外側のカギは「アクセス権が取れない」として受付用かどうかの照会に回り、受付用でもないため**開始前も終了後もどちらも「QRコードが不正です」になる**（`ReservationCameraAuthenticationViewModel.swift:780-785`）。**Android版では「まだ利用できない」と「利用できる時間が終わった」を出し分ける**方針とする。具体的な文言は⑭の範囲のため、期待値は「どちらであるかが分かること」の粒度で記述する。
> **前提となる設定の組み合わせ**：開始前のケースは、端末の**事前入室可能時間がカギの有効時間の前倒し幅より長い**設定のときだけ作れる（ホーム画面に入室の導線は出ているが、カギはまだ有効になっていない、という状態になるため）。終了後のケースは、予約が終わってホーム画面が空室に戻った後の導線から入る。どの操作の導線が出るかの条件そのものは⑦⑩⑳の責務で、本ルールは**導線に到達してカメラ認証画面に入れた状態**からを見る。

| 対象 | カギの種類 | かざした時刻 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- | :--- |
| 従業員 | 予約に紐づいて自動発行されたカギ | 有効時間の開始前 | 🔴異常系：予約の開始時刻より前で、まだカギの有効時間に入っていないときにQRコードをかざす | 見出しが「照会中です...」に変わった後、まだ利用できないことが分かるメッセージが出る失敗の表示になる |
| 従業員 | 予約に紐づいて自動発行されたカギ | 有効時間内（予約開始前） | 🟢正常系：予約の開始時刻より前だが、カギの有効時間には入っているときにQRコードをかざす | 人物が特定され、操作ごとの画面へ進む |
| 従業員 | 予約に紐づいて自動発行されたカギ | 有効時間の終了後 | 🔴異常系：予約の終了時刻を過ぎ、カギの有効時間も過ぎてからQRコードをかざす | 見出しが「照会中です...」に変わった後、利用できる時間が終わったことが分かるメッセージが出る失敗の表示になる |

### ❓ 疑問点・未確認事項（赤カード）

- [ ] **①ルール④は参照元（iOS）の実装の延長ではない（議題）。** 予約認証モードには**オフラインの控えを育てる仕組みが無い**。オフライン関連の設定は4項目とも常時認証モードでしか表示されず（`SettingViewModel.swift:1091-1101`）、控えを作るジョブの開始も常時認証モードのカメラ画面からのみ（`AlwaysCameraAuthenticationViewModel.swift:776`。予約認証モードのカメラ画面は終了時に `stopJob()` を呼ぶだけ／`ReservationCameraAuthenticationViewModel.swift:385`）。ルール④は「控えに記録があれば特定できる」というAndroid版での新たな提案であり、採用するなら**控えを予約認証モードでも育てる**必要がある。リファインメントで採否を決めたい。なお「QAが無効の状態を作れるか」は解決済みで、**作れない**（端末の設定画面に項目が無く、予約認証モードのオフラインのセクションには「予約認証モードでは設定できる項目がありません。」と出る／`SettingView.swift:2116-2120`）。

- [ ] **②同一のQRコードを続けて読んだときの、時間による抑止が常時認証モード専用でよいか。** 受け入れ条件③に「同一QRの連続読み取りで二重処理が起きない」とあるが、参照元では時間による抑止は常時認証モード専用の設定が有効なときだけ効き、予約認証モードではルール③（照会の間は読み取らない／認証待ちで再開する）が二重処理を防いでいる。この認識で合っているか（台帳 #50）。

- [ ] **③ルール②の照会の打ち切りを通信エラーと分けることも参照元との差分（議題）。** 参照元(iOS)は打ち切りと通信エラーを同じ `catch` でまとめ、どちらも「インターネットに接続されていません」にしている（`ReservationCameraAuthenticationViewModel.swift:758-807`）。そのため**オンラインでもサーバーの応答が5秒を超えただけで「インターネットに接続されていません」が出る**。分ける方針の採否と、打ち切り側の具体的な文言を確定したい（文言そのものは⑭の範囲）。

- [ ] **④アプリはQRコードの発行種別を区別しない、という認識で合っているか。** 管理画面には従業員向け・ゲスト向けのほか、受付用QRが2種（予約単位／受付利用可能時間の設定あり）と入館用QRがあるが、**アプリ側にはそれらを分ける概念が無い**。受付用かどうかの照会は `keyData` の一致と `condition.end_date` が**今日の前後7日**に入るかだけで判定し（`FirestoreReceptionKeyDatas.getPeriodDatasByKeyData` / `GetValidReceptionKeyDatasUseCase:26-28`）、受け取るモデル `ReceptionKeyData` も種別のフィールドを持たない。そのためルール②の分岐は発行種別では増えないと判断したが、①受付用QR2種がどちらも同じく受付の案内になること、②入館用QRが「QRコードが不正です」に落ちること、③**前後7日の窓が管理画面のどの設定に対応するか**（受付利用可能時間を過ぎたQRの見え方）は、いずれもコードからの読みで**実機未確認**。確認したい。
