## 抽出の根拠

RoomSupportは会議室入口に常設されるキオスク型iPadアプリであり、一般的なモバイルアプリとは大きく異なるセキュリティリスクプロファイルを持つ。OWASP Mobile Top 10の全10カテゴリのうち、以下のプロダクト特性に基づき重点度を設定した。

**最重要リスク領域:**
- **物理的アクセスが無制限** — 端末はオフィスの共用エリアに設置され、不特定多数のユーザーが直接触れる。デバイスの物理的セキュリティ（MDM/Guided Access）の突破や、ローカルストレージの窃取リスクが一般アプリより格段に高い。
- **スマートロック連動** — Bitlock BLE解錠は物理セキュリティ（会議室への入室）に直結するため、認証・認可の不備は即座に物理的侵入を許す。QRコード盗み見やリプレイ攻撃による不正解錠は、デジタル被害にとどまらず現実空間のセキュリティインシデントとなる。
- **常時無人稼働** — 管理者不在の環境で24時間稼働するため、異常検知や即時対応が困難。攻撃者に時間的猶予が与えられ、試行回数制限や監視がなければブルートフォースやリプレイ攻撃の標的となる。
- **Firebase/GRDB二重データ層** — Firestore（クラウド）とGRDB/SQLite（ローカル）の二重データ層は、キャッシュ不整合による権限チェック漏れや、ローカルDB改ざんによるオフライン時の認可バイパスリスクを生む。

**重点度マトリクス（RoomSupport固有）:**

| OWASP カテゴリ | RoomSupport重点度 | 根拠 |
|---|---|---|
| M1: 不適切な資格情報の使用 | ★★★ 最重要 | Firebase Auth トークン、Bitlock解錠キー、管理者パスワード（SHA-256）の保護 |
| M3: 安全でない認証/認可 | ★★★ 最重要 | QR/顔認証バイパス → 不正解錠。権限チェック漏れ → 他人の予約操作 |
| M9: 安全でないデータ保存 | ★★★ 最重要 | GRDB(SQLite)・UserDefaults に解錠トークン・個人情報が平文保存されるリスク |
| M5: 安全でない通信 | ★★☆ 重要 | BLE通信の傍受/リプレイ、API通信の中間者攻撃 |
| M8: セキュリティ設定の不備 | ★★☆ 重要 | キオスク端末のMDM/Guided Access設定不備によるアプリエスケープ |
| M6: 不十分なプライバシー管理 | ★★☆ 重要 | 顔認証データ・来訪ゲストの個人情報（PII）の取扱い |
| M2: 不十分なサプライチェーンセキュリティ | ★☆☆ 標準 | 顔認証SDK、Bitlock SDK、ExSGアダプター等の独自SDK |
| M4: 不十分な入出力バリデーション | ★☆☆ 標準 | Firestoreセキュリティルール、予約データの入力検証 |
| M10: 不十分な暗号化 | ★☆☆ 標準 | 管理者パスワードSHA-256、ローカルDB暗号化 |
| M7: 不十分なバイナリ保護 | ☆☆☆ 低（キオスク） | キオスク端末ではApp Store経由の配布リスクは低いが、MDM配布の完全性は検証要 |

## M1: 不適切な資格情報の使用（Improper Credential Usage）

### RoomSupportにおけるリスク

RoomSupportはFirebase Auth（カスタムトークン認証）、BKP API認証、Bitlock SDK（BLE解錠トークン）、管理者パスワード（SHA-256ハッシュ）の4系統の資格情報を扱う。キオスク端末は物理的にアクセス可能なため、ソースコードやバイナリに埋め込まれた資格情報の抽出リスクが一般アプリより高い。また、Keychain ポーリングによる自動ログイン検出機能は、Keychain項目のアクセス制御が不適切だと、同一バンドルプレフィックスの他アプリから資格情報を窃取される可能性がある。

### セキュリティ上の必須要件

| # | Do（推奨） | Don't（禁止） |
|---|---|---|
| 1-1 | Firebase APIキー・カスタムトークン生成ロジックはサーバーサイドで管理する | APIキーやシークレットをアプリバイナリ/Info.plist/ソースコードにハードコードしない |
| 1-2 | Bitlock SDK の解錠トークン・認証キーをiOS Keychainに`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`で保存する | 解錠トークンをUserDefaults/GRDB/NSLog出力に平文保存しない |
| 1-3 | 管理者パスワードはbcrypt/Argon2/PBKDF2で保護する | SHA-256単純ハッシュのみでパスワードを保存しない（レインボーテーブル攻撃に脆弱） |
| 1-4 | Firebase Auth トークンのリフレッシュ時にサーバーサイドでトークンの有効性を検証する | クライアントサイドのみでトークン有効期限を管理しない |
| 1-5 | Keychain項目に明示的な`kSecAttrAccessGroup`を設定してアクセスを制限する | 同一バンドルプレフィックスの全アプリにKeychain項目へのアクセスを許可しない |
| 1-6 | リリースビルドではデバッグログに資格情報を出力しない（`#if DEBUG`ガード） | トークン値・パスワードハッシュをコンソールログに出力しない |

### 具体的なテスト観点

| # | テスト観点 | テスト手法 | 検証ポイント |
|---|---|---|---|
| 1-T1 | ハードコード資格情報の検出 | IPAファイルを展開し、`strings`コマンドやHopper等の逆アセンブラでバイナリを解析する。`firebase`、`api_key`、`secret`、`token`等のキーワードを検索する | APIキー・シークレット・認証トークンがバイナリ内に平文で埋め込まれていないこと |
| 1-T2 | Keychain保存属性の検証 | Jailbreak済み端末またはFrida等のフッキングツールでKeychain項目をダンプし、`kSecAttrAccessible`属性を確認する | Bitlock解錠トークン、Firebase Authトークンが`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`（またはそれ以上の制限）で保存されていること |
| 1-T3 | 管理者パスワードのハッシュ強度 | ローカルストレージ（GRDB/UserDefaults/Keychain）から管理者パスワードのハッシュ値を抽出し、ソルト付きか・ストレッチングが行われているか確認する | SHA-256単純ハッシュではなく、bcrypt/PBKDF2等のストレッチングが適用されていること。レインボーテーブルで逆算不可能であること |
| 1-T4 | デバッグログの資格情報漏洩 | リリースビルドのアプリをXcodeまたは`idevicesyslog`で接続し、ログイン・トークンリフレッシュ・BLE接続時のログ出力を確認する | トークン値、パスワードハッシュ、APIキー等の機密情報がシステムログに出力されていないこと |
| 1-T5 | Keychainアクセスグループの分離 | 同一バンドルプレフィックスを持つテストアプリを作成し、RoomSupportのKeychain項目にアクセスを試行する | 他アプリからRoomSupportのKeychain項目を読み取れないこと |
| 1-T6 | トークンリフレッシュの安全性 | 起動画面のトークンリフレッシュ3回リトライ（5秒間隔）中にネットワークキャプチャを実施し、リフレッシュトークンの送信方法を確認する | リフレッシュトークンがHTTPS経由で送信されていること。リクエストにリプレイ攻撃対策（nonce/タイムスタンプ）が含まれていること |

## M3: 安全でない認証/認可（Insecure Authentication/Authorization）

### RoomSupportにおけるリスク

RoomSupportの認証は多層構造（QRコード認証、顔認証（3D/2Dパッシブ/2Dインタラクション）、パーソナルコード、管理者パスワード）であり、認可は予約操作権限（入室/退室/延長/キャンセル/再入室）に紐づく。**最大のリスクは認証バイパスがBitlock物理解錠に直結する点**である。他人のQRコードを撮影して不正認証したり、顔認証のなりすまし（スプーフィング）で解錠権限を取得すると、会議室への物理的な不正侵入が可能になる。

また、オフラインフォールバック時にFirestoreのサーバーサイド認可チェックが効かず、ローカルキャッシュのみで認可判定が行われる場合、キャッシュ改ざんによる権限昇格リスクがある。

### セキュリティ上の必須要件

| # | Do（推奨） | Don't（禁止） |
|---|---|---|
| 3-1 | すべての認可判定（入室/退室/延長/キャンセル権限）をサーバーサイドで実行する | クライアントサイドのみで認可判定を行わない |
| 3-2 | QRコード認証にワンタイム性を持たせる（使用済みコードの無効化、有効期限の設定） | QRコードを固定値・無期限で運用しない |
| 3-3 | 顔認証になりすまし対策（Anti-Spoofing: 3D深度、2Dインタラクション検出）を実装する | 写真や動画の提示のみで顔認証が通過しない |
| 3-4 | 認証試行回数に制限を設け、連続失敗時にロックアウトまたは遅延を適用する | 無制限の認証試行を許可しない |
| 3-5 | 認証成功後のセッショントークンに有効期限を設け、期限切れ時は再認証を要求する | 一度の認証で無期限のセッションを維持しない |
| 3-6 | オフラインフォールバック時のローカルキャッシュによる認可判定に、改ざん検出機構（HMAC等）を適用する | オフライン時にFirestoreキャッシュの認可データを無検証で信頼しない |
| 3-7 | 管理者メニューアクセス時の認証（SHA-256パスワード or 顔認証）をバイパスできないようにする | デバッグフラグやURL Schemeによる管理者認証バイパスを本番ビルドに残さない |

### 具体的なテスト観点

| # | テスト観点 | テスト手法 | 検証ポイント |
|---|---|---|---|
| 3-T1 | QRコードのリプレイ攻撃 | 正規ユーザーのQRコードを撮影・保存し、時間経過後に同じコードで認証を試行する | QRコードに有効期限があり、期限切れ・使用済みコードでは認証が拒否されること。OTP方式の場合は同一コードの再利用が不可であること |
| 3-T2 | 顔認証のなりすまし（Anti-Spoofing） | 正規ユーザーの写真（スマートフォン画面表示/印刷）、動画再生、3Dマスクを提示して認証を試行する | 2Dパッシブ/2Dインタラクション/3D深度のAnti-Spoofing機能により、写真・動画・マスクが拒否されること。状態マシンの`interaction`ステートが正しく機能すること |
| 3-T3 | 他人の予約への不正操作（IDOR） | ユーザーAの認証で、ユーザーBの予約に対して入室/退室/延長/キャンセル操作をAPIリクエストレベルで試行する（Burp Suite等でリクエスト改ざん） | サーバーサイドで予約所有者/権限チェックが行われ、他人の予約操作が拒否されること。APIレスポンスで`authFailedNoPermissionToExtendReservation`等の適切なエラーが返ること |
| 3-T4 | 認証試行回数制限 | 顔認証・QRコード認証で意図的に連続失敗を繰り返す（10回、50回等） | 連続失敗後にロックアウト（一時的な認証停止）またはプログレッシブ遅延が適用されること。ブルートフォース攻撃が実質不可能であること |
| 3-T5 | オフライン時の権限昇格 | ネットワーク切断状態で、GRDBのローカルキャッシュを直接編集（iExplorer等）し、一般ユーザーに管理者権限を付与した状態で管理者メニューアクセスを試行する | ローカルキャッシュの改ざんが検出されること、またはオフライン時の権限判定が制限されていること |
| 3-T6 | 管理者メニューの認証バイパス | （1）管理者パスワード入力でSQLインジェクションを試行する（`' OR '1'='1`等）。（2）URL Schemeによる管理者メニュー直接遷移を試行する。（3）連続パスワード失敗時のロックアウト動作を確認する | （1）入力値がサニタイズされ、インジェクションが不可であること。（2）外部からの直接遷移が不可であること。（3）連続失敗でロックアウトされること |
| 3-T7 | 認証セッションの有効期限 | カメラ認証成功後にアプリを長時間放置し、セッションの有効期限が切れた後に予約操作（入室/解錠）を試行する | セッショントークン期限切れ時に再認証が要求されること。期限切れセッションでBitlock解錠が実行されないこと |
| 3-T8 | 予約状態の競合操作 | 2台の端末から同一予約に対して同時に入室操作を実行する。または、管理コンソールで予約を削除した直後に端末から入室を実行する | サーバーサイドで楽観的ロック/トランザクション制御が行われ、二重入室や削除済み予約への操作が拒否されること |

## M9: 安全でないデータ保存（Insecure Data Storage）

### RoomSupportにおけるリスク

RoomSupportはGRDB（SQLite）をローカルデータベースとして使用し、予約情報・スペース情報・顔プロパティキャッシュ等を保存する。また、UserDefaultsにタブレット設定が保存される。キオスク端末は物理的にアクセス可能なため、USBケーブル接続やiTunesバックアップによるSQLiteファイルの抽出リスクが高い。暗号化されていないSQLiteファイルからBitlock解錠トークン、Firebase Authトークン、ゲストの個人情報（名前・メールアドレス・顔画像）が漏洩する可能性がある。

### セキュリティ上の必須要件

| # | Do（推奨） | Don't（禁止） |
|---|---|---|
| 9-1 | GRDBデータベースをSQLCipherで暗号化し、暗号化キーはKeychainに保存する | SQLiteファイルを暗号化なしで保存しない |
| 9-2 | 機密データ（トークン、パスワードハッシュ、個人情報）はKeychainに保存する | UserDefaultsやNSLogに機密データを保存しない |
| 9-3 | iTunesバックアップからの機密データ漏洩を防止する（`NSURLIsExcludedFromBackupKey`の設定、またはバックアップ暗号化の強制） | バックアップに機密データを含むSQLiteファイルを無制限に含めない |
| 9-4 | アプリスイッチャーのスナップショットで機密画面を隠す（`applicationWillResignActive`で画面をマスク） | 認証コード入力中、管理者パスワード入力中の画面がスナップショットに残らない |
| 9-5 | ログアウト時にローカルに保存された機密データを完全に消去する | ログアウト後もFirestoreキャッシュ、GRDB内のトークン、顔プロパティキャッシュを残さない |
| 9-6 | クリップボードへのコピー後にタイマーでクリップボードをクリアする | パスワードや認証コードがクリップボードに無期限に残らない |
| 9-7 | キーボードキャッシュ（予測変換辞書）に機密情報が学習されることを防止する（`autocorrectionDisabled`、`SecureField`の使用） | パスワード入力フィールドでオートコレクト/予測変換が有効にならない |

### 具体的なテスト観点

| # | テスト観点 | テスト手法 | 検証ポイント |
|---|---|---|---|
| 9-T1 | SQLiteの平文データ検出 | iExplorer / iFunbox / `ideviceinstaller`でアプリコンテナからGRDB SQLiteファイル（`.sqlite`/`.db`）を抽出し、`sqlite3`コマンドで中身を読み取る | 認証トークン、解錠キー、パスワードハッシュ、ユーザーの個人情報（名前、メール、電話番号）が平文で格納されていないこと。SQLCipher暗号化が適用されている場合、`sqlite3`での直接読み取りが不可能であること |
| 9-T2 | UserDefaultsの機密データ検出 | アプリコンテナの`Library/Preferences/<BundleID>.plist`を抽出し、内容を確認する | Bitlock解錠トークン、Firebaseトークン、管理者パスワードハッシュ等の機密データがUserDefaultsに保存されていないこと。タブレット設定値として保存されるデータに機密情報が含まれていないこと |
| 9-T3 | iTunesバックアップからのデータ抽出 | 端末をiTunesでバックアップ（非暗号化バックアップ）し、バックアップディレクトリからアプリデータを抽出する | 機密データを含むファイルが`NSURLIsExcludedFromBackupKey`でバックアップ対象外に設定されていること。または、データが暗号化されてバックアップに含まれていること |
| 9-T4 | アプリスイッチャーのスナップショット | ログイン画面（パスワード入力中）、管理者パスワード入力中、パーソナルコード入力中にホームボタンを押し、アプリスイッチャーのサムネイルを確認する | 機密情報が表示された画面のサムネイルがマスク（ブラー/スプラッシュ画面）で隠されていること |
| 9-T5 | ログアウト後のデータ残存 | ログアウト操作を実行した後、アプリコンテナ内の全ファイルを確認する（SQLite、Keychain、キャッシュディレクトリ、tmp） | ログアウト後にFirestoreキャッシュ、GRDBデータ、顔プロパティキャッシュ、認証トークンが適切に消去されていること |
| 9-T6 | 顔認証データのローカル保存 | アプリコンテナ内の顔プロパティキャッシュのファイル形式・保存場所を確認する | 顔画像/顔特徴量データが暗号化されて保存されていること。キャッシュリセット（管理者メニューの「顔プロパティキャッシュリセット」）後に完全に消去されること |
| 9-T7 | キーボードキャッシュの確認 | パスワード入力フィールドで複数の文字列を入力後、同フィールドにフォーカスした際の予測変換候補を確認する | SecureFieldが使用されており、入力内容がキーボードキャッシュに学習されていないこと |

## M5: 安全でない通信（Insecure Communication）

### RoomSupportにおけるリスク

RoomSupportは3つの通信経路を持つ：（1）Firebase/バックエンドAPIとのHTTPS通信、（2）Bitlock BLE解錠のBluetooth Low Energy通信、（3）FaceTime（オペレーター呼出し）。特にBLE通信は近距離での傍受が技術的に容易であり、解錠コマンドのリプレイ攻撃は物理セキュリティの直接的な破壊につながる。キオスク端末は設置場所が固定のため、攻撃者がBLEスニファーを設置しやすい環境にある。

### セキュリティ上の必須要件

| # | Do（推奨） | Don't（禁止） |
|---|---|---|
| 5-1 | すべてのAPI通信をTLS 1.2以上（推奨TLS 1.3）で暗号化する | HTTP（平文）通信を許可しない。`NSAppTransportSecurity`の`NSAllowsArbitraryLoads`を`true`に設定しない |
| 5-2 | 重要APIエンドポイント（認証、解錠指示、予約操作）に証明書ピニングを実装する | サーバー証明書を無条件に受け入れない |
| 5-3 | BLE通信にBLE Secure Connections（LE Secure Connections）を使用し、解錠コマンドをエンドツーエンドで暗号化する | BLE通信で解錠コマンドを平文送信しない |
| 5-4 | BLE解錠コマンドにリプレイ攻撃対策（ノンス/タイムスタンプ/シーケンス番号）を含める | 固定値の解錠コマンドを使用しない |
| 5-5 | 証明書ピニング実装にRASP（Runtime Application Self-Protection）防御を組み合わせ、FridaやSSL Kill Switch等によるアンピニングを防止する | 証明書ピニングのみに依存し、実行時のフッキング攻撃に無防備にしない |

### 具体的なテスト観点

| # | テスト観点 | テスト手法 | 検証ポイント |
|---|---|---|---|
| 5-T1 | HTTPS通信の強制確認 | Charles Proxy / mitmproxy をプロキシに設定し、アプリの全通信を確認する。Info.plistの`NSAppTransportSecurity`設定を確認する | すべてのAPI通信がHTTPSであること。HTTP通信が1件もないこと。ATS（App Transport Security）が有効であること |
| 5-T2 | 証明書ピニングの検証 | Charles Proxyの自己署名証明書をプロキシとして挿入し、Firebase Auth/BKP API/予約APIへのリクエストが中間者攻撃を検出して接続を拒否するか確認する | 証明書ピニングが実装されている場合、プロキシの自己署名証明書で通信が失敗すること。失敗時にアプリがクラッシュせず、適切なエラーメッセージが表示されること |
| 5-T3 | BLE通信の傍受テスト | nRF Connect / Wireshark + BLEアダプタでBitlockとの通信を傍受し、解錠コマンドのパケット内容を確認する | 解錠コマンドが暗号化されていること。同一のパケットをリプレイしても解錠されないこと（ノンス/シーケンス番号の検証） |
| 5-T4 | BLEリプレイ攻撃 | 正規の解錠時のBLEパケットをキャプチャし、同一パケットをリプレイツールで再送信する | リプレイされたパケットでBitlockが解錠されないこと。ノンス/タイムスタンプの検証により、過去のコマンドが拒否されること |
| 5-T5 | TLSバージョン・暗号スイートの検証 | `nscurl --ats-diagnostics`または`sslyze`でサーバーのTLS設定を確認する | TLS 1.2以上が有効であること。弱い暗号スイート（RC4, 3DES, NULL等）が無効であること |
| 5-T6 | 通信中の機密データ漏洩 | プロキシでキャプチャしたリクエスト/レスポンスの内容を確認する（証明書ピニングがバイパスされた場合を想定） | 認証トークン、パスワード、個人情報がリクエストボディに適切に含まれていること（URLパラメータに機密データを含めていないこと） |

## M8: セキュリティ設定の不備（Security Misconfiguration）

### RoomSupportにおけるリスク

キオスク端末として最も重大なリスクは、MDM（Mobile Device Management）/Guided Accessの設定不備によるアプリエスケープである。物理的にアクセス可能な端末で、ユーザーがアプリから脱出してSafariや設定アプリにアクセスできると、企業ネットワーク情報やWi-Fiパスワードの漏洩、端末のリセット、他のキオスク端末への攻撃の踏み台化などの重大インシデントにつながる。

### セキュリティ上の必須要件

| # | Do（推奨） | Don't（禁止） |
|---|---|---|
| 8-1 | MDMによるSingle App Mode / Guided Accessを設定し、RoomSupportアプリ以外へのアクセスを制限する | MDM管理なしでキオスク端末を運用しない |
| 8-2 | リリースビルドではデバッグフラグ、テスト用バックドア、開発用設定画面を完全に除去する | `DEBUG`フラグが有効なビルドをキオスク端末にデプロイしない |
| 8-3 | Info.plistのURL Schemeを最小限にし、意図しない外部からの起動を防止する | 不要なカスタムURL Schemeを登録したままにしない |
| 8-4 | アプリのEntitlementsを最小権限原則で設定する（カメラ、Bluetooth、ネットワーク等、必要な権限のみ） | 不要な権限（位置情報、連絡先、フォトライブラリ等）を要求しない |
| 8-5 | FaceTime（オペレーター呼出し）発信後、通話アプリからのRoomSupportへの復帰パスを確保し、通話アプリ内からの他操作を制限する | FaceTime発信でGuided Accessが解除され、他アプリへのアクセスが可能になる状態にしない |
| 8-6 | 端末のiOSバージョンをサポート範囲内の最新に保ち、セキュリティパッチを適用する | 既知の脆弱性が修正されていないiOSバージョンで運用しない |

### 具体的なテスト観点

| # | テスト観点 | テスト手法 | 検証ポイント |
|---|---|---|---|
| 8-T1 | Guided Access / Single App Modeのエスケープテスト | Guided Access有効時に以下のエスケープ手法を試行する：（1）トリプルクリック（ホームボタン/サイドボタン）、（2）Siri起動試行、（3）通知センター/コントロールセンターのスワイプ、（4）スクリーンショット送信からのShare Sheet操作 | すべてのエスケープ手法がブロックされること。RoomSupportアプリ以外の画面に遷移できないこと |
| 8-T2 | FaceTime発信後のアプリエスケープ | カメラ認証画面からオペレーター呼出し（FaceTime）を実行し、通話終了後にRoomSupportに自動復帰するか、または通話アプリ内から他のアプリにナビゲートできないか確認する | FaceTime通話後にRoomSupportに自動復帰すること。通話中/通話後に他アプリにアクセスできないこと |
| 8-T3 | デバッグ機能の残存確認 | リリースビルドのIPAを展開し、デバッグ関連のシンボル、テスト用API エンドポイント、隠しメニュー（設定画面の「顔認証デバッグ」等）へのアクセス可否を確認する | 管理者メニューの「顔認識デバッグ」が管理者認証なしではアクセスできないこと。リリースビルドにテスト用エンドポイントやバックドアが含まれていないこと |
| 8-T4 | URL Scheme経由の不正起動 | Safariや他アプリからRoomSupportのカスタムURL Schemeを呼び出し、意図しない画面遷移（管理者メニュー直接アクセス、設定変更等）が可能か確認する | 外部からのURL Scheme経由で管理者メニューや設定画面に直接遷移できないこと。URL Schemeのパラメータインジェクションが不可であること |
| 8-T5 | Entitlements / 権限の最小化確認 | リリースビルドのIPAから`embedded.mobileprovision`とEntitlementsを抽出し、要求している権限一覧を確認する | カメラ（顔認証/QR）、Bluetooth（Bitlock BLE）、ネットワーク以外の不要な権限が要求されていないこと |
| 8-T6 | 端末設定の物理操作 | Guided Access無効の状態で、物理ボタン操作によるアプリ終了（ホームボタン）、端末リセット（電源+ホーム長押し）、リカバリーモード進入を試行する | Guided Access / MDM有効時にこれらの操作がブロックされること。MDMによるリモートロックが機能すること |

## M6: 不十分なプライバシー管理（Inadequate Privacy Controls）

### RoomSupportにおけるリスク

RoomSupportは顔認証機能で利用者の生体情報（顔画像/顔特徴量）を取得・キャッシュし、予約操作で利用者の氏名・メールアドレス・組織情報を扱う。顔認証データは生体情報としてGDPR/個人情報保護法の下で最も高い保護レベルが求められる。キオスク端末は不特定多数が使用するため、前の利用者の個人情報が次の利用者に表示されるクロスユーザー情報漏洩リスクがある。

### セキュリティ上の必須要件

| # | Do（推奨） | Don't（禁止） |
|---|---|---|
| 6-1 | 顔認証データ（顔画像/特徴量）の保存はローカルのみとし、暗号化して保存する。サーバーへの生データ送信は最小限にする | 顔画像を暗号化なしでFirestoreやGRDBに保存しない |
| 6-2 | 認証完了後の画面遷移で、前の利用者の個人情報（名前、メール、組織名）を即座にメモリから消去する | 前の利用者の情報が次の利用者の画面に残らない |
| 6-3 | 利用者の個人情報収集について、アプリ内またはキオスク端末の設置場所で明示的な同意表示を提供する | 個人情報の取扱いに関する説明なしに顔画像/個人情報を収集しない |
| 6-4 | データ保持期間を定義し、不要になったデータを自動削除する | 顔プロパティキャッシュを無期限に保持しない |

### 具体的なテスト観点

| # | テスト観点 | テスト手法 | 検証ポイント |
|---|---|---|---|
| 6-T1 | クロスユーザー情報漏洩 | ユーザーAが顔認証+入室操作を完了した後、ユーザーBが画面を確認する。また、認証成功画面からメイン画面への遷移時にユーザーAの個人情報（名前等）が残存しないか確認する | 認証完了→メイン画面遷移後にユーザーAの名前・組織情報がUI上に残っていないこと。カメラ認証画面の状態マシンが`complete`→`waiting`に正しくリセットされていること |
| 6-T2 | 顔プロパティキャッシュの暗号化確認 | アプリコンテナ内の顔プロパティキャッシュファイルを抽出し、顔画像/特徴量データが暗号化されているか確認する | 顔画像データが平文のJPEG/PNG等で保存されていないこと。特徴量データが暗号化されていること |
| 6-T3 | 顔プロパティキャッシュの削除確認 | 管理者メニューの「顔プロパティキャッシュリセット」を実行した後、アプリコンテナ内のキャッシュファイルが完全に消去されているか確認する | リセット後にキャッシュディレクトリが空であること。ファイルシステムの未使用領域にもデータが残存しないこと（可能な範囲で） |
| 6-T4 | 予約データの個人情報マスキング | 予約ステータス画面、予約作成画面で表示される利用者情報の表示範囲を確認する | 他の予約の利用者のフルネーム・メールアドレスが不必要に表示されていないこと。表示が最小限の情報（名前の一部等）に制限されていること |
| 6-T5 | ログへの個人情報出力 | リリースビルドのシステムログで、認証・予約操作時のログ出力を確認する | ユーザー名、メールアドレス、顔画像ファイルパス等の個人情報がシステムログに出力されていないこと |

## M2: 不十分なサプライチェーンセキュリティ（Inadequate Supply Chain Security）

### RoomSupportにおけるリスク

RoomSupportは独自SDK（顔認証SDK、Bitlock SDK、ExSGアダプター、プリンターSDK）およびFirebase SDK、GRDB等のオープンソースライブラリを使用する。特に顔認証SDKとBitlock SDKはクローズドソースであり、内部実装の検証が困難である。これらのSDKに脆弱性がある場合、アプリ全体のセキュリティが連鎖的に破壊される。

### セキュリティ上の必須要件

| # | Do（推奨） | Don't（禁止） |
|---|---|---|
| 2-1 | 全依存ライブラリのバージョン・既知脆弱性（CVE）を定期的にスキャンする | 既知の脆弱性が公開されたライブラリを更新せずに使用しない |
| 2-2 | SDKの信頼性を署名検証やチェックサムで担保する | 未検証のSDKバイナリをそのまま組み込まない |
| 2-3 | SDKに付与する権限を最小限にする（顔認証SDKにはカメラのみ、Bitlock SDKにはBLEのみ等） | SDKにアプリの全権限を委譲しない |

### 具体的なテスト観点

| # | テスト観点 | テスト手法 | 検証ポイント |
|---|---|---|---|
| 2-T1 | 依存ライブラリの脆弱性スキャン | `swift package audit`（Swift Package Manager）、Dependabot、Snyk等のツールで依存ライブラリの既知脆弱性をスキャンする | 既知のCVEが報告されたバージョンのライブラリが使用されていないこと。Firebase SDK、GRDB等が最新の安定バージョンであること |
| 2-T2 | SDKの通信先確認 | Charles Proxy / Wiresharkで顔認証SDK、Bitlock SDKの通信先を確認する | SDKが開発者のドキュメントに記載されていない外部サーバーに通信していないこと。不正なデータ収集（テレメトリ等）が行われていないこと |
| 2-T3 | SDKの権限使用状況確認 | 実行時のSDKが要求するシステム権限（カメラ、BLE、ネットワーク、位置情報等）を監視する | 各SDKが最小限の権限のみを使用していること。顔認証SDKが位置情報にアクセスしていないこと等 |

## M4: 不十分な入出力バリデーション（Insufficient Input/Output Validation）

### RoomSupportにおけるリスク

RoomSupportの主要な入力経路は、（1）ログイン画面のメール/パスワード、（2）設定画面の各種入力フィールド（10セクション）、（3）管理者パスワード、（4）パーソナルコード、（5）QRコードの読み取りデータである。特にQRコードは外部から任意のデータを注入可能な攻撃経路であり、不正なQRコードによるSQLインジェクションやパストラバーサルのリスクがある。また、Firestoreセキュリティルールのバイパスによる予約データの改ざんも入出力バリデーションの範疇である。

### セキュリティ上の必須要件

| # | Do（推奨） | Don't（禁止） |
|---|---|---|
| 4-1 | QRコードの読み取りデータを厳密にバリデーションする（期待されるフォーマット・長さ・文字種のホワイトリスト検証） | QRコードのデータを未検証でデータベースクエリやURL構築に使用しない |
| 4-2 | Firestoreセキュリティルールでドキュメントレベルの読み書き制限を実装する | クライアントサイドのみで予約データのアクセス制御を行わない |
| 4-3 | 設定画面の入力値に対してサーバーサイドでもバリデーションを実行する | クライアントサイドのバリデーションのみに依存しない |
| 4-4 | GRDBへのクエリにパラメータバインディングを使用する | SQLクエリを文字列結合で構築しない |

### 具体的なテスト観点

| # | テスト観点 | テスト手法 | 検証ポイント |
|---|---|---|---|
| 4-T1 | 不正QRコードによるインジェクション | SQLインジェクションペイロード（`'; DROP TABLE--`）、XSSペイロード（`<script>alert(1)</script>`）、パストラバーサル（`../../etc/passwd`）を含むQRコードを生成し、カメラ認証画面で読み取らせる | 不正なQRコードが適切に拒否されること。アプリがクラッシュしないこと。エラーメッセージに入力値が反射表示されないこと |
| 4-T2 | Firestoreセキュリティルールのテスト | Firebase CLIの`firebase emulators:start`でエミュレータを起動し、Firestoreセキュリティルールのテストスイートを実行する。異なるユーザーコンテキストで他組織の予約データへの読み書きを試行する | 他組織の予約データへのアクセスが拒否されること。認証なしでの読み書きが不可であること |
| 4-T3 | 設定画面の入力値バウンダリ | 設定画面の数値フィールドに極端な値（0、-1、999999999、空文字、特殊文字）を入力し、保存を試行する | バリデーションエラーが適切に表示されること。不正な値がサーバーに送信されないこと。数値オーバーフローが発生しないこと |
| 4-T4 | GRDB SQLインジェクション | アプリのソースコード（またはバイナリ解析）で、GRDBへのクエリ構築方法を確認する。パラメータバインディングが使用されているか検証する | すべてのGRDBクエリがパラメータバインディング（`?`プレースホルダー）を使用していること。文字列結合によるSQL構築が存在しないこと |

## M10: 不十分な暗号化（Insufficient Cryptography）

### RoomSupportにおけるリスク

管理者パスワードのSHA-256ハッシュ化は、ソルトなしの場合レインボーテーブル攻撃に脆弱である。また、GRDBの暗号化、Bitlock解錠トークンの暗号化、Firebase Authトークンの暗号化において、不適切な暗号化アルゴリズムやキー管理が使用されている場合、暗号化の意味が失われる。

### セキュリティ上の必須要件

| # | Do（推奨） | Don't（禁止） |
|---|---|---|
| 10-1 | パスワードハッシュにはbcrypt/Argon2/PBKDF2（10,000回以上のイテレーション）を使用する | SHA-256/MD5等の汎用ハッシュ関数を単純にパスワードハッシュに使用しない |
| 10-2 | 暗号化キーはKeychainに保存し、暗号化データと同一場所に保存しない | 暗号化キーをソースコードにハードコードしたり、SQLiteのテーブル内に保存しない |
| 10-3 | Apple CryptoKit / CommonCrypto等の検証済み暗号ライブラリを使用する | 独自の暗号化アルゴリズムを実装しない |
| 10-4 | AES-256-GCM（認証付き暗号）等の最新かつ安全な暗号アルゴリズムを使用する | DES、3DES、RC4、ECBモード等の非推奨アルゴリズムを使用しない |

### 具体的なテスト観点

| # | テスト観点 | テスト手法 | 検証ポイント |
|---|---|---|---|
| 10-T1 | 管理者パスワードのハッシュアルゴリズム | ソースコードまたはバイナリ解析で管理者パスワードのハッシュ化処理を特定し、使用されているアルゴリズム・ソルト・ストレッチング回数を確認する | SHA-256単純ハッシュではなく、bcrypt/PBKDF2等のストレッチングアルゴリズムが使用されていること。ソルトがランダムかつユーザーごとに一意であること |
| 10-T2 | SQLite暗号化キーの管理 | GRDBの暗号化設定（SQLCipher使用有無）と暗号化キーの保存場所を確認する | 暗号化キーがKeychainに保存されていること。バンドルID由来の固定キーではないこと |
| 10-T3 | 暗号化アルゴリズムの確認 | IPAバイナリの暗号API呼び出しを解析（class-dump / otool）し、使用されている暗号アルゴリズムを特定する | 非推奨アルゴリズム（DES、3DES、RC4、MD5）が使用されていないこと。AES-256-GCM等の認証付き暗号が使用されていること |

---

## M7: 不十分なバイナリ保護（Insufficient Binary Protections）

### RoomSupportにおけるリスク

キオスク端末はMDM管理下でApp Store / Enterprise配布されるため、一般公開アプリと比較してバイナリ解析のリスクは低い。ただし、MDM管理から脱出した端末やJailbreak端末でのバイナリ解析により、認証ロジックやBitlock SDKの通信プロトコルがリバースエンジニアリングされるリスクは残る。

### セキュリティ上の必須要件

| # | Do（推奨） | Don't（禁止） |
|---|---|---|
| 7-1 | Jailbreak検出を実装し、Jailbreak端末での実行を制限する | Jailbreak端末での実行を無制限に許可しない |
| 7-2 | デバッガー検出（ptrace/sysctl）を実装し、デバッグアタッチを防止する | リリースビルドでデバッガーアタッチを許可しない |
| 7-3 | リリースビルドではビットコード/シンボル情報をストリップする | デバッグシンボルが残ったビルドを配布しない |

### 具体的なテスト観点

| # | テスト観点 | テスト手法 | 検証ポイント |
|---|---|---|---|
| 7-T1 | Jailbreak検出の動作確認 | Jailbreak済み端末（またはcheckra1n等のJailbreakツール適用端末）でRoomSupportを起動する | Jailbreak検出により、アプリが起動を拒否するか、機密機能（解錠等）が制限されること |
| 7-T2 | デバッガーアタッチの防止 | `lldb`でリリースビルドのプロセスにアタッチを試行する | デバッガーアタッチが検出され、プロセスが終了するか機能が制限されること |
| 7-T3 | シンボル情報の除去確認 | `nm`コマンドでリリースビルドのバイナリのシンボルテーブルを確認する | デバッグシンボル、内部クラス名/メソッド名がストリップされていること。特に認証・解錠関連のメソッド名が推測困難であること |
