# 04. コンテキストプロファイル質問票

| 項目 | 内容 |
|---|---|
| **象限** | 📗 リファレンス |
| **対象者** | QA担当（記入）、開発リーダー・PdM（回答・レビュー） |
| **ゴール** | プロダクトの利用文脈を質問に答える形で言語化し、採用すべき指標を機械的に導出できるようになります |

新規プロダクトで品質評価計画書（evaluation plan）を作る最初のステップとして記入します。対象プラットフォームによって回答する群が分岐します。

---

## 0. この質問票の進め方

**所要 30〜60分。開発リーダーと一緒に回答してください。** 運用の実態を知らないと答えられない設問が含まれます（「異常時にその場で人が復旧できるか」など）。

### 方法A：Skillで対話しながら埋める（推奨）

```
/quality-criteria-generator [プロダクト名]
```

Skillが本書の設問を順に質問し、回答から指標の引き当て・判定基準ドラフトの生成まで行います。回答は `docs/quality_criteria/{プロダクト名}/context_profile.md` に保存されます。手順は **08. Claude Code のSkillで品質評価計画書を作る** を参照してください。

### 方法B：手で埋める

**全体の手順は 11. 手で品質評価計画書を作る にあります。** 本書はその [1]（利用文脈の確定）にあたります。本書での作業は以下のとおりです。

| 順 | やること | 本書の該当箇所 |
|---|---|---|
| 1 | A群（前提情報）に回答する | §4 |
| 2 | A-2 の回答に応じて M群 または W群 に回答する | §5 |
| 3 | C〜F群（全PF共通）に回答する | §6 |
| 4 | A-5 が「はい」なら G群 に回答する | §6-G |
| 5 | 回答から文脈タグを確定させる | §7 |

**回答の記入先:** プロダクトごとのページ・ファイルに残してください（品質評価計画書 05 §2 のコンテキストサマリから参照します）。本書そのものには書き込みません。本書はフレームワークの資産で、プロダクトをまたいで共有するためです。

> **ソースコードが参照できる場合は、先に 07 を実施してください。** 下書きが作れる分だけ回答が速くなります。ただし運用形態（常時稼働・無人運用など）はコードから読み取れないため、半分程度は人に聞く前提で進めます。

### 埋め終わったら

文脈タグが確定したら、**03. 指標カタログ** で指標を引き当て、**05. 品質評価計画書テンプレート** に転記して閾値を合意します。手順の詳細は **11 の [2] 以降** にあります。

## 1. なぜ質問票が必要か

判定基準の閾値は、**プロダクトの利用文脈から決まります**。同じ「クラッシュ復帰時間」でも、その場に人がいるプロダクトと無人運用のプロダクトでは求められる値が違います。

本フレームワークの出発点となった既存基準（設置型タブレットアプリ向け）を分析すると、固有性の発生源は以下の3点に集約されました。

| 固有の基準 | 発生源となる利用文脈 |
|---|---|
| 24時間稼働での Thermal Status、12時間でのメモリ増加量 | **電源を切らず連続稼働する** |
| クラッシュ復帰時間（ネットワーク障害時60秒以内） | **異常時にその場で人が復旧できない** |
| 認証→デバイス制御完了 p95 1秒以内 | **人がその場で完了を待っている／外部デバイスを制御する** |

つまり**先に文脈を確定させれば、指標と閾値は機械的に導出できます**。本質問票はそのための入力です。

## 2. 質問票の構造（プラットフォーム分岐）

**A-2（対象プラットフォーム）の回答によって、回答する群が分岐します。**

```
        [A群] 前提情報（必須・全PF共通）
                    │
                    │ A-2 で対象PFを選択
          ┌─────────┴─────────┐
          ▼                   ▼
   [M群] モバイル固有     [W群] Web固有
   （Android / iOS）      （Web）
          └─────────┬─────────┘
                    ▼
        [C群] データ・権限（全PF共通）
        [D群] 通信・セッション（全PF共通）
        [E群] 測定基盤（※PF別に設問が分岐）
        [F群] 外部要件・履歴（全PF共通）
                    │
                    │ A-5 が「はい」の場合のみ
                    ▼
        [G群] AI/ML（全PF共通・条件付き）
```

| 群 | 対象 | 質問数 |
|---|---|---|
| A群 前提情報 | 全PF共通 | 5 |
| M群 モバイル固有 | Android / iOS のみ | 9 |
| W群 Web固有 | Web のみ | 9 |
| C群 データ・権限 | 全PF共通 | 7 |
| D群 通信・セッション | 全PF共通 | 4 |
| E群 測定基盤 | 共通6 ＋ PF別3 | 9 |
| F群 外部要件・履歴 | 全PF共通 | 4 |
| G群 AI/ML | 全PF共通（**A-5 が「はい」の場合のみ**） | 5 |

**複数PFを対象とする場合（例：Android と Web の両方）は、M群とW群の両方に回答します。** その場合、品質評価計画書はPFごとに分けて作成することを推奨します（測定基盤も判定タイミングも異なるためです）。

---

## 3. 記入のルール

- **「わからない」は「わからない」と書いてください。** 推測で埋めると誤った指標が採用されます
- **A群に未回答がある状態で基準作成に進まないでください**
- 回答はプロダクトのページに残し、**リリースごとに見直します**（機能追加で文脈が変わることがあります）
- ソースコードがある場合は、07. ソースコードから質問票の下書きを作る の手順で下書きを作ってから回答すると精度が上がります

## 4. A群：前提情報（全PF共通・必須）

| # | 質問 | 未回答時の影響 |
|---|---|---|
| A-1 | 自組織の不具合重要度定義は何か。段階ごとのリリース可否は決まっているか。固有の段階がある場合はその内容は？ | FS-01・FS-02・FS-12 が定義できません |
| A-2 | **対象プラットフォームは？（Android / iOS / Web / 複数）** | **分岐が決まらず質問票が進行できません** |
| A-3 | 今回の判定対象範囲は？（新規リリース全体／特定機能の改修／リグレッションのみ） | スコープ外宣言が書けません |
| A-4 | リリース判定の最終決定者は誰か。逸脱承認の3つの責務（プロダクト意思決定／技術判断／品質判断）は誰が担うか | 02 の承認フローが回りません |
| A-5 | **判定対象にAI/ML機能を含むか？（自前モデル／外部AI SDK・AI APIの利用を含む）** | **G群の分岐が決まりません。AI固有の指標（AQ群）が採用されません** |

### 4-1. A-1 の分岐

**まず自組織の不具合重要度定義を確認してください。** 判定の進め方は 06. 不具合重要度モデル に、記入先は組織プロファイル §2 にあります。

| 回答 | 対応 |
|---|---|
| 自組織の定義があり、**段階ごとのリリース可否も決まっている** | 06 §3 の変換ルールでラベルに対応付け、組織プロファイル §2-2 に記入します |
| 定義はあるが、**リリース可否が紐づいていない** | 段階ごとに「リリース不可／条件付き可／可」のどれに当たるかを関係者で合意します（06 §4） |
| **固有の段階がある**（例：最上位を分割する） | 06 §5-2 の形式でマッピング表を作成し、FS-01 / FS-02 / FS-12 の集計単位を明記します |
| **固有の判定根拠を追加したい** | 自組織の定義に対する**追加分のみ**を組織プロファイル §2-3 に記載します |
| **定義が無い** | 06 §5-1 の記入例をもとに自組織の定義を作成し、正式なルールとして合意します |

> **注意:** 「条件付きリリース可」の段階は FS-02（P2）として扱います。これを P1（リリース不可）に引き上げる場合は、その理由を品質評価計画書に明記してください。

### 4-2. A-5 の分岐

| 回答 | 対応 |
|---|---|
| **はい** | G群（§6-G）に回答します。文脈タグ `AI機能あり` が立ち、AQ指標群が採用候補に入ります（10. AI拡張） |
| **いいえ** | **G群には回答しません。** AQ指標は1件も母集団に入りません |
| **判断がつかない** | 10 §2 の適用判断の表で確認します。**固定のルール・しきい値による判定は「いいえ」です**（入力が同じなら出力が常に同じもの） |

> **外部のAI SDK・AI APIを呼び出しているだけの場合も「はい」です。** 自前でモデルを学習していなくても、出力の不確実性はアプリ側に現れます。ベンダー責務との線引きは 10 §4 にあります。

### 8-3. 2例の比較から分かること

| 観点 | 内容 |
|---|---|
| **両方で採用される指標** | FS-01〜04, FS-12, PE-02, PE-07, IC-01, IC-02, IC-05, MA-01, MA-03, FL-01, FL-04, SA-02 |
| **例A側だけの指標** | FS-05, FS-11, PE-01, PE-03〜06, CO-01, CO-04, CO-05, RE-01〜05, RE-09, MA-02, FL-02, FL-05, SA-01, SA-03, **AQ-01〜AQ-05, AQ-07〜AQ-09**（AI拡張。`説明責任要求` が立たないため AQ-06 / AQ-10 は不採用） |
| **例B側だけの指標** | FS-06〜10, PE-08〜11, CO-02, CO-03, IC-03, IC-04, RE-06〜08, SE-01, SE-02, SE-04, FL-03 |

**共通部分は全体の約2割**です。残りは文脈タグとPFで分岐します。これがフレームワーク化の効果であり、同時に「共通部分だけをコピーしても基準にならない」ことの根拠でもあります。

記入例は特定のプロダクトを指すものではなく、**利用文脈の類型**として記載しています。自プロダクトに近い型を出発点にしてください。
