# 08. Claude Code のSkillで品質判定基準を作る

| 項目 | 内容 |
|---|---|
| **象限** | 🛠️ ハウツーガイド |
| **対象者** | Claude Code が使えるQA担当 |
| **ゴール** | `/quality-criteria-generator` を実行して、自プロダクトの品質判定基準ドラフトを生成できるようになります |

Skillは**ドラフト生成までを担当します**。閾値の確定と関係者の合意は人が行います。手作業で進める場合は 04 の質問票と 05 のテンプレートを直接使っても同じ成果物が作れます。

---

## 1. 前提

| 項目 | 必要なもの |
|---|---|
| Skillの配置 | `.claude/commands/quality-criteria-generator.md` がリポジトリにあること（INSTALL のパターンBを参照） |
| フレームワーク定義 | `docs/quality_criteria_framework/` に 00〜07 と `assets/metrics_catalog.csv` があること |
| 事前知識 | **00. はじめての品質判定基準づくり を体験済みであること** |

> **00 を先に通してください。** Skillは対話形式で20問以上を尋ねます。仕組みを知らないまま答えると、回答の意味が分からないまま進んでしまいます。

### 手元に用意しておくもの

対話中に聞かれるため、事前に調べておくと早く終わります。

- 不具合管理ツール・テスト管理ツールの名前
- 監視ツールの名前（エラー監視・APM・クラッシュ監視）
- 現行バージョンの実測値（応答時間・エラー率など。なければ「なし」でかまいません）
- リリース判定の最終決定者・逸脱承認の承認者
- 一覧で扱う想定最大件数

---

## 2. 実行する

```
/quality-criteria-generator [プロダクト名]
```

プロダクト名は成果物の保存先ディレクトリ名になります（例：`customer-web-app`）。

所要時間の目安は **40〜80分**です。うち大半が質問への回答で、残りは生成結果のレビューです。

---

## 3. 対話の流れ

Skillは7ステップで進みます。**人が判断する場面は太字**の箇所です。

| Step | 内容 | あなたがすること |
|---|---|---|
| 1 | フレームワーク定義の読み込み | なし |
| 2-0 | ソースコードからの下書き（任意） | **リポジトリのパスを伝えるか「なし」と答える** |
| 2-1 | A群（前提情報）の質問 | **不具合重要度・対象PF・判定範囲・承認者を答える** |
| 2-2 | PF別の質問（M群 または W群） | **9問に答える** |
| 2-3 | 共通の質問（C・D・E・F群） | **群ごとにまとめて答える** |
| 2-4 | 回答の保存 | なし |
| 3 | 指標の導出 | **導出結果を確認して承認する** |
| 4 | 閾値とラベルの設定 | **チーム合意が必要な閾値を判断する** |
| 5 | 判定基準ドキュメントの生成 | なし |
| 6 | セルフチェックと申し送り | **申し送り事項を引き取る** |
| 7 | カタログへのフィードバック（2回目以降） | **カタログ更新案を承認する** |

### Step 2-0：ソースコードからの下書き

「ソースコードが参照できるか」を最初に聞かれます。

- **パスを伝えた場合** — コードを調査し、根拠となるファイルパス付きで回答の下書きを提示します。内容を確認して修正してください
- **「なし」と答えた場合** — すべて対話で質問されます

調査対象と限界は 07 に整理しています。**運用形態（常時稼働・無人運用など）はコードから読み取れない**ため、下書きした場合でも必ず質問されます。

### Step 2-1：A群で止まることがあります

不具合の重要度定義について聞かれます。社内公式定義（Critical / Major / Normal / Minor / Enhancement）をそのまま使う場合は「そのまま使う」と答えれば進みます。固有の段階がある場合は、06 のマッピング表を作る流れになります。

### Step 3：導出結果の承認

以下が提示されるので、内容を確認して承認します。

- 立った文脈タグ
- 採用候補の指標一覧（ISO特性別の件数）
- **除外した指標とその理由**（PF不一致／タグ不成立／測定手段なし）
- 採用候補が0件だった品質特性

**除外理由の確認がいちばん重要です。** 「測定手段なし」で外れた指標は、本来必要だったのに監視が整っていないだけかもしれません。

### Step 4：P1が多すぎると警告されます

P1（リリースブロッカー）が採用指標の60%を超えると、Skillが見直しを促します。P1を増やしすぎると逸脱承認が常態化し、ラベルが意味を失うためです（02 を参照）。

---

## 4. 成果物

```
docs/quality_criteria/{プロダクト名}/
├── context_profile.md   # 質問票への回答（根拠のファイルパス付き）
├── criteria.md          # 品質判定基準ドラフト（05 の5セクション形式）
└── criteria.csv         # CSV版（集計・ツール取り込み用）
```

`criteria.md` は 05 のテンプレートに沿って5セクションが生成されます。**実測値と判定の列は空欄**です。ここは測定後に人が埋めます。

---

## 5. 生成後にやること

Skillは Step 6 で申し送り事項を提示します。以下を必ず引き取ってください。

| 申し送り事項 | やること |
|---|---|
| **TBD 指標の一覧と確定期限** | 誰がいつまでにベースライン計測するかを決める |
| **未回答だった質問と影響** | 採用できなかった指標を確認し、回答できる人に聞く |
| **測定手段未整備の指標** | 監視の仕込みをタスク化する |
| **`NEW-` で作った新規指標** | 判定後に指標カタログのデータベースへ登録する |

そのうえで、**開発リーダー・PdM のレビューを経てから合意**してください。生成結果をそのままリリース判定に使わないでください。

---

## 6. うまくいかないとき

| 症状 | 対処 |
|---|---|
| A群で処理が止まる | 不具合重要度定義が未整備です。06 の社内公式定義を採用する旨を伝えれば進みます |
| 指標が少なすぎる | 文脈タグがほとんど立っていない可能性があります。C群・D群の回答を見直してください |
| 指標が多すぎる | 対象PFを複数選んでいる場合は、PFごとに分けて実行することを検討してください |
| 閾値が TBD ばかりになる | E-3（実測ベースライン）が「なし」の場合は正常な挙動です。計測後に確定させます |
| カタログにない指標を入れたい | `NEW-01` 等のIDで追加され、Step 6 の申し送りに載ります |

---

## 7. 2回目以降の実行

同じプロダクトで再実行すると、Step 7 でカタログへのフィードバックが行われます。

- TBD だった指標のうち実測値が入ったものについて、指標カタログの更新案が提示されます
- `NEW-` 指標の正式登録が提案されます
- 逸脱承認が2回以上繰り返された指標について、閾値の見直しが提案されます

**カタログの更新は承認を得てから実行されます。** 自動では上書きされません。

このフィードバックがフレームワークの生命線です（01 を参照）。リリース後の実測値を反映しない限り、閾値はいつまでも根拠のない数字であり続けます。
