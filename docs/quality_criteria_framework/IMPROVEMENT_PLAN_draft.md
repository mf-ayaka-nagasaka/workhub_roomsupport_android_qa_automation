## 0. 経緯

品質判定基準フレームワーク（`docs/quality_criteria_framework/`）に対して、以下2点のレビュー指摘を受けました。

1. AIプロダクトにも使えるよう **ISO/IEC 25059** を視野に入れたほうがよいのではないか
2. 「品質判定基準」という呼称を含め、手順も案件固有の進め方をもとに作成したが、**公式的な枠組みはないのか**（オリジナルのフレームワークではなく、どのプロダクトにも通用するもの）

あわせて、本フレームワークの目的を以下のとおり確認しました。

- **主目的**: 社内配布フレームワークとしての**汎用性**
- **直近のゴール**: 社内の他チームへの横展開
- **将来のゴール**: 顧客説明にも持っていける形

## 1. 調査結果サマリ

### 1-1. ISO/IEC 25059（AIシステム向け品質モデル）

| 項目 | 内容 |
|---|---|
| 位置づけ | SQuaRE の拡張部門（25050〜25099）。25010 を置き換えず、AI固有の特性のみを差分として追加・修正し、残りは親モデルを継承します |
| 現行版 | ISO/IEC 25059:2023（EN版は2024） |
| 改訂状況 | **DIS の公開審査が 2026-03-12 に終了。改訂進行中です。** 製品品質／利用時品質／AIサービス品質の3モデルへ拡張、環境持続可能性の格上げ、Clause 7 に AIaaS 向けモデル新設、25010:2023・25019:2023 への整合 |

25010 に追加される副特性は以下のとおりです。

| 親特性 | 追加される副特性 | 意味 |
|---|---|---|
| 機能適合性 | 機能適応性（Functional Adaptability） | データや過去の行動結果から情報を獲得し、以降の予測に使える度合い |
| 相互作用機能 | ユーザー制御性（User Controllability） | ユーザーがAIの動作に適切に介入できる度合い |
| 相互作用機能 | 透明性（Transparency） | AIシステムに関する十分な情報が関係者に伝達される度合い |
| 信頼性 | ロバストネス（Robustness） | あらゆる状況下で性能水準を維持できる度合い |
| セキュリティ | 介入可能性（Intervenability） | 危害を避けるためオペレーターが適時に介入できる度合い |

周辺標準として、**ISO/IEC TR 29119-11:2020**（AIベースシステムのテスト。テストオラクル問題を扱います）、**ISO/IEC 5259 シリーズ**（ML用データ品質）、**ISO/IEC 42001**（AIマネジメントシステム）、**ISO/IEC 22989**（用語）があります。

### 1-2. 公式的な枠組みの有無

**「品質判定基準」という名前の国際標準は存在しません。** ただし本フレームワークの各工程は、SQuaRE（ISO/IEC 25000シリーズ）の評価プロセスとほぼ一対一で対応します。**オリジナルの発明ではなく、既存標準の実装として説明し直せます。**

| 本フレームワーク | 対応する公式枠組み | 何に当たるか |
|---|---|---|
| 01 分類軸＝25010:2023 | **ISO/IEC 25002:2024** ＋ 25010:2023 | 25002 は品質モデルの構造・意味論、要求定義／測定／評価との関係を定義する親標準です |
| 04 コンテキストプロファイル | **ISO/IEC 25030:2019**（品質要求フレームワーク） | ステークホルダ要求から品質要求を導出・定義・運用するプロセス。「文脈から基準を導く」発想の正式な根拠です |
| 03 指標カタログ | **ISO/IEC 2502n 系**（25020 / 25021 QME / 25022 / 25023） | 指標＝quality measure、測定方法・データソース＝quality measure element。カタログの列構成はほぼ同じ構造です |
| 02 閾値・根拠・判定 | **ISO/IEC 25040**（評価プロセス。2011→**2024改訂**） | 「decision criteria（決定基準）の確立」は 25040 の正式ステップであり、品質判定基準そのものです |
| 02 判定タイミング・未測定の扱い | **ISO/IEC/IEEE 29119-2/-3** | entry criteria / exit criteria / test completion criteria |
| 05 判定基準表・判定結果 | 25040 の評価結果記録 ＋ 29119-3 の Test Completion Report | |
| 06 不具合重要度モデル | 29119-3 の Incident Report | |
| **02 §5 逸脱承認フロー** | **該当する国際標準なし。** CMMI/TMMi の waiver、IEEE 1012 の異常処理が近いです | 社内ルールとして保持してよく、「標準の空白を埋めた部分」と明示すると価値が伝わります |
| 指標の導出論理 | **GQM / GQM+Strategies**（ISO標準ではないが確立された手法） | 目標→問い→指標。04→03 の導出に相当します |

## 2. 改善案

汎用性が主目的である以上、最大の障害は標準でもAIでもなく、**フレームワーク自体が自社・自プロダクトに結合していること**です。そのため Phase A を最優先とします。「将来の顧客説明」も、固有物を分離すると残った骨格が標準ベースであることが自然に見えるため、同じ方向に収束します。

### Phase A：汎用化（横展開の前提／最優先）

配布先が自分で埋めないと使えないのに、「埋めてください」と書かれていない箇所の一覧です。

| # | 結合箇所 | 現状 | 問題 | 対応案 |
|---|---|---|---|---|
| A-1 | **06 不具合重要度モデル** | 社内公式の5段階定義に直結。Major→P2 等の対応も社内運用前提 | 他社・他部門では定義が違い、顧客説明では提示できません | 06 を「重要度定義の要件と、判定ラベルへの対応付け方」の解説に組み替え、自社の5段階は記入例へ降格します。実データは組織プロファイル（A-5）へ移します |
| A-2 | **03 指標カタログの正本** | 「正本は Notion DB」と断定 | 配布先に自社Notionへのアクセスはなく、配布版では記述が矛盾します | README/03 を「正本は導入組織が自組織のDBとして持つ。CSVは初期データ」に改め、INSTALL に正本引き継ぎ手順を追加します |
| A-3 | **02 §5 承認者** | PdM／開発リーダー／QA担当で固定 | ロール名は組織依存です | 「承認の責務」で定義し、組織のロール名へのマッピング表を組織プロファイルに置きます |
| A-4 | **04 の文脈タグ・例** | 設置型タブレット寄り（常時稼働・キオスク運用・ハードウェア連携） | 例Bで緩和済みですがM群が偏ります | 大きな改修は不要で、タグ辞書に「自組織で追加する手順」を一節追加すれば足ります |
| A-5 | **組織固有設定の置き場がない** | INSTALL §3 に散在 | 何を埋めれば使える状態になるか一覧できません | **`assets/organization_profile_template.md` を新設**し、重要度定義の参照先／承認者ロール／測定基盤／指標DBの所在を1枚に集約します |
| A-6 | **08 が Claude Code 前提** | Skill 実行手順のみ | 配布先にClaude Codeがない場合の扱いが不明です | 冒頭に「Skillは任意。無くても 04→03→05 の手順で完結します」と明記します |

> 08 の INSTALL 上の扱いも整理が必要です。Skill 実体は `.claude/commands/quality-criteria-generator.md` にあり、`scripts/build_quality_criteria_framework.py` が Zip の `skills/` へ同梱しています。配布先のディレクトリ構成が違う前提の設置手順になっているかが確認対象です。

### Phase B：ISO/IEC 25059（AI拡張レイヤー）

独立ドキュメント＋タグ必須の非採用既定で追加します。自プロダクト（顔認証）向けの記述は記入例として置き、本体には混ぜません。

| 対象 | 追加内容 |
|---|---|
| **新規 `10_ai_extension.md`** | 25059 の位置づけ／追加5副特性／周辺標準（TR 29119-11・5259・42001）／外部AI-SDK利用時の責務線引き |
| **04 に G群** | A群に「AI/ML機能を含むか」の分岐を追加し、Yes のみ展開します（非決定的出力か／モデル更新があるか／取り消し・再試行できるか／根拠提示が必要か／ゴールデンセットを持つか） |
| **04 タグ辞書** | `AI機能あり` `非決定的出力` `モデル更新あり` `自動判断` `説明責任要求` |
| **03 / CSV** | `AQ-` 接頭辞の指標群。**`AI機能あり` タグ必須＝既定で非採用**とします |
| **02 に新節** | **非決定的指標の判定ルール**（①固定ゴールデンセット必須 ②基準値に許容幅・試行回数を含める ③前バージョン非劣化で判定）。根拠区分に `ベースライン比較` を追加します |

外部AI-SDK利用時の責務線引き（記入例に使う想定）は以下のとおりです。

| 対象外（ベンダー責務） | 対象（アプリ責務＝指標にする） |
|---|---|
| 顔認証SDKの認識精度そのもの | 認証失敗時に代替手段（手動予約）へ導線が出るか |
| SDKのしきい値アルゴリズム | SDKが返す失敗・タイムアウトを正しくハンドリングするか |
| モデルの学習プロセス | 誤認証時にユーザー／管理者が取り消せるか（ユーザー制御性） |
| — | 逆光・マスク等の悪条件でのフォールバック動作（ロバストネス） |

## 4. リスク・注意点

- **ISO規格は有償です。** 特性名・定義は要約と出典URL併記にとどめ、本文の転載はしません。
- **25059 は改訂進行中です。** 「25059準拠」と書くと改訂時に陳腐化します。「25059を参考に拡張」に留め、INSTALL のウォッチ項目に入れます。
- **25040 は 2024年改訂版**が出ています。引用時は版を明記します。
- 指標カタログの実データは Notion DB が正本のため、**CSV への `standard_ref` 列追加と AQ 指標の追加は、Notion 側を先に更新して再エクスポートする順序**になります。

## 5. 次回の論点（未決定事項）

**進め方そのものが未決定です。** 以下を決めるところから再開します。

1. **着手順** — 推奨は A →（Notion側更新）→ B・C です。A はドキュメント本文の改訂だけで完結し、Notion を触らずに進められます。Aが終われば「他チームに配っても動く」状態になり、BとCはそこへの純粋な追加になります。
2. **スコープの絞り込み** — Phase A 全部をやるのか、A-1／A-2（結合が強い2件）だけ先行するのか。
3. **ブランチの切り方** — Phase A を1本のブランチにまとめるか、ドキュメント単位で分けるか。
4. **09 を先に作って評価するか** — 標準対応ドキュメントを1枚先行作成し、説明材料として妥当か確認してから残りに進む進め方も選択肢です。
