# 02. 運用ルール

| 項目 | 内容 |
|---|---|
| **象限** | 📗 リファレンス |
| **対象者** | QA担当、開発リーダー、PdM |
| **ゴール** | ラベル・判定タイミング・根拠区分の付け方と、未達時の逸脱承認フローを、判定時に迷わず適用できるようになります |

---

## 1. 優先度ラベルの定義

各品質判定基準には必ず優先度ラベルを付与します。ラベルは**未達だったときにどうするか**を定義するものであり、指標の重要度の感想ではありません。

| ラベル | 表記 | 意味 | 未達時の扱い |
|---|---|---|---|
| **P1** | ★★★ | リリースブロッカー | **リリース不可。** 修正して再測定するか、後述の逸脱承認を得るまでリリースしません |
| **P2** | ★★ | 条件付き許容 | **条件付きリリース可。** 未達理由・影響範囲・改善期限を記録したうえで、プロダクト意思決定責務を持つ担当の判断でリリースできます |
| **P3** | ★ | 記録のみ | リリース判断には影響しません。実測値を記録し、次回の閾値見直しの材料とします |

### ラベル付与の判断基準

| 問い | Yes → |
|---|---|
| 未達のまま出すと、ユーザーが業務を遂行できなくなるか？ | P1 |
| 未達のまま出すと、データ消失・不正アクセス・安全上の危害が起きうるか？ | P1 |
| 未達のまま出すと、運用（サポート・保守）が成立しなくなるか？ | P1 |
| 未達でも回避策があり、次リリースで改善できるか？ | P2 |
| 傾向を見たいだけで、今回の合否には使わないか？ | P3 |

> **注意:** P1 を増やしすぎると逸脱承認が常態化し、ラベルが意味を失います。**P1は「本当にリリースを止める覚悟があるもの」に限定してください。**

## 2. 判定タイミング

「いつ測るか」を決めていない基準は測られません。各基準には以下のいずれかのタイミングを必ず割り当てます。

| タイミング | 説明 | 向く指標の例 |
|---|---|---|
| **継続測定** | 開発期間中、日次・CI実行ごとに測定 | 自動テスト通過率、ビルド成否 |
| **テストフェーズ完了時** | システムテスト完了時点で1回測定 | 業務シナリオテスト通過率、互換性カバー率 |
| **RC版での測定** | リリース候補ビルドで測定（**この値が判定に使われます**） | クラッシュフリー率、E2E応答時間、CPU・メモリ |
| **長期測定** | 一定期間の連続稼働が必要 | ロングラン（ソークテスト）、長時間メモリ増加量 |
| **リリース判定会議時点** | 判定会議のその時点のスナップショット | 未対応不具合件数 |

### 長期測定の扱い

ロングランのように**測定に数日〜数週間かかる指標**は、スケジュールの都合で省略されがちです。以下を必ずセットで定義してください。

- 測定開始のトリガー（例：RC1ビルド作成時点で開始）
- 測定に必要な期間（例：2週間）
- 開始が遅れた場合の扱い（例：最低1週間の結果をもって暫定判定とし、P1→P2に降格して記録）

## 3. 測定の記録ルール

各基準の測定結果は以下の粒度で記録します。**「OK」だけの記録は不可**です。

| 記録項目 | 例 |
|---|---|
| 実測値 | クラッシュフリー率 99.4% |
| 測定日時 | 2026-09-25 10:00 〜 2026-09-28 10:00 |
| 測定対象ビルド | v3.2.0 (build 412) |
| 測定環境 | QA環境 / 対象端末：[検証用タブレット A] |
| データソース | クラッシュ監視ツールのダッシュボード |
| 判定 | Pass / Fail / 未測定 |

> **テスト環境・クレデンシャルの記載ルール:** 環境URL・アカウント情報・APIキーは記載せず、「QA環境」「[検証用タブレット A]」等のプレースホルダーを用います。実情報はアクセス制限されたページで管理してください。

---

## 4. 「未測定」の扱い

**未測定は Pass ではありません。** 測定できなかった基準は以下のいずれかに分類して記録します。

| 分類 | 意味 | 扱い |
|---|---|---|
| **測定手段未整備** | 監視・ログの仕込みが間に合わなかった | P1なら逸脱承認が必要。次リリースまでに整備をタスク化します |
| **スケジュール都合** | 時間が足りず測定できなかった | P1なら逸脱承認が必要です |
| **今回対象外** | 該当機能に変更がなく影響範囲外 | 理由を記載のうえ判定対象から除外します（承認不要） |

「今回対象外」を使えるのは、**影響範囲分析の結果として変更影響が及ばないことが示せる場合のみ**です。

## 5. 逸脱承認フロー（未達のままリリースする場合）

P1 未達、または P1 未測定の状態でリリースする場合は、以下を記録し承認を得ます。

### 記録すべき内容

1. **対象基準** — どの基準が未達か
2. **実測値と基準値の差** — 例：クラッシュフリー率 98.2%（基準 99%以上）
3. **影響範囲** — どのユーザー・どの操作にどう影響するか
4. **リリースする理由** — なぜ止めないのか
5. **回避策・軽減策** — 運用でのカバー方法、監視強化の有無
6. **改善期限と担当** — いつまでに基準を満たすか

### 承認の責務

承認者は**責務**で定義します。責務名と自組織の役職名の対応は、**組織プロファイル §3** に記入してください。

| 対象 | 必要な承認 |
|---|---|
| P1 未達 | **プロダクト意思決定責務** ＋ **技術判断責務** |
| P1 未測定 | **プロダクト意思決定責務** ＋ **品質判断責務** |
| P2 未達 | **プロダクト意思決定責務** |

| 責務名 | 責務の内容 |
|---|---|
| プロダクト意思決定責務 | プロダクトの提供可否を最終判断する |
| 技術判断責務 | 未達の技術的影響範囲とリスクを評価する |
| 品質判断責務 | 測定の妥当性と品質リスクを評価する |

> 記入例：プロダクト意思決定責務＝PdM（プロダクトオーナー）／技術判断責務＝開発リーダー／品質判断責務＝QA担当。
> **1人が複数の責務を兼ねる体制でもかまいません**が、その場合も「どの責務として承認したか」を逸脱記録に残します。

### 逸脱記録の保管

逸脱承認の記録はリリース判定ページに残し、**次回リリースの判定時に必ず未解消の逸脱を一覧で確認します。** 逸脱が繰り越され続けている場合は、基準値そのものが実態に合っていない可能性を検討してください。

## 6. 基準の変更ルール

| フェーズ | 変更可否 |
|---|---|
| 合意前（ドラフト段階） | 自由に変更できます |
| 合意後〜テストフェーズ開始前 | 関係者レビューのうえ変更できます |
| テストフェーズ開始後 | **原則変更不可。** 変更する場合は逸脱承認と同じ手続きを踏みます |
| リリース判定会議中 | **変更不可。** 基準を緩めて通すことは禁止です |

> リリース判定の場で基準を緩めることは、品質判定基準の存在意義を失わせます。未達なら逸脱承認フローを通してください。

---

## 7. スコープ外宣言のルール

ISO/IEC 25010 の9特性のうち、今回の判定で扱わない特性は**「扱わない」と明示的に記録します。** 空欄のまま放置しません。

記録フォーマットは以下のとおりです。

| 品質特性 | 今回の扱い | 理由 |
|---|---|---|
| セキュリティ | スコープ外 | 別途セキュリティ診断計画で扱うため |
| 安全性 | スコープ外 | ハードウェア連携がない機能改修のため |
| 柔軟性 | 一部のみ | 対応ブラウザの追加なし。導入性のみ対象 |

> 「それ以外は都度評価必要」という記述は、**何を都度評価するのかが不明**なため使用しません。上表の形式で特性ごとに明示してください。

## 8. 基準値の根拠区分

各基準値（閾値）には、必ず根拠の区分を付します。根拠なしの数字は設定しません。

| 区分 | 意味 | 例 |
|---|---|---|
| **業界基準** | プラットフォーム提供元・標準規格が定める値 | ANR発生率 0.47%未満（Google Play 不良動作のしきい値） |
| **組織標準** | 導入組織の公式ルール・ポリシーが定める値 | 未対応の最重要不具合 0件（自組織の不具合重要度定義。06 を参照） |
| **実測ベース** | 現行バージョンの実測値から設定 | メモリ使用量が OOM 閾値の80%以内 |
| **契約・SLA由来** | 対外的な約束から逆算 | 稼働率 99.9% |
| **チーム合意** | 上記に該当せず、議論のうえ設定 | 未対応Normal/Minor不具合 3件以内 |
| **TBD** | **ベースライン計測待ち。** 測定後に確定させる | — |

> **TBD を恐れないでください。** 根拠のない数字を置くより、「計測して決める」と明示するほうが健全です。ただし TBD のまま判定フェーズに入らないよう、確定期限を設定してください。
