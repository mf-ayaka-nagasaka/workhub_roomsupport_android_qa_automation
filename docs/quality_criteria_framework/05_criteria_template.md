# 05. 判定基準テンプレート

| 項目 | 内容 |
|---|---|
| **象限** | 📗 リファレンス |
| **対象者** | QA担当（作成）、リリース判定に関わる全員（参照） |

**記入ルール**

- **ラベル**: P1 ★★★ / P2 ★★ / P3 ★（02 の付与基準に従います）
- **指標ID**: 指標カタログのID。カタログに無い新規指標は `NEW-01` 等とし、判定後にカタログへ登録します
- **基準値**: 確定できない場合は `TBD（確定期限: YYYY-MM-DD）` と記入します。空欄は不可です
- **根拠区分**: 業界基準 / 社内標準 / 実測ベース / 契約・SLA由来 / チーム合意 / TBD。業界基準・社内標準の場合は出典（URL・参照先）を併記します
- **実測値**: 数値だけでなく、測定日時・対象ビルド・測定環境も記録します
- **判定**: Pass / Fail / 未測定（測定手段未整備・スケジュール都合・今回対象外 のいずれかを併記します）

## 3. 記入例（設置型タブレットアプリ・抜粋）

### §3 スコープ宣言（記入例）

| # | 品質特性 | 今回の扱い | 理由 |
|---|---|---|---|
| 1 | 機能適合性 | 対象 | 主要機能の改修を含むため |
| 2 | 性能効率性 | 対象 | 常時稼働のため資源効率性を含めて全面的に測定 |
| 3 | 互換性 | 一部 | 対応端末の追加なし。連携先システムとの整合性のみ対象 |
| 4 | 相互作用機能 | 一部 | 画面変更のある機能のみ対象 |
| 5 | 信頼性 | 対象 | 無人運用のため最重要 |
| 6 | セキュリティ | スコープ外 | 別途セキュリティ診断計画で実施するため |
| 7 | 保守性 | 対象 | ログ・監視は運用の前提条件 |
| 8 | 柔軟性 | 一部 | バージョンアップ時のデータ移行のみ対象 |
| 9 | 安全性 | 対象 | 物理デバイスの制御を伴うため |

|---|---|---|---|---|---|---|---|---|---|---|
| P1 ★★★ | FS-01 | 機能適合性 | 未対応 Critical 不具合件数 | 0件 | 不具合DBを重要度でフィルタし件数を確認 | 不具合DB | リリース判定会議時点 | 社内標準 | 0件（2026-09-28時点） | Pass |

| P1 ★★★ | RE-02 | 信頼性 | ANR発生率 | 0.47%未満 | ストアの品質指標を確認 | Play Console | RC版での測定 | 業界基準 | 0.12% | Pass |

| P1 ★★★ | RE-03 | 信頼性 | ロングラン検証（ソークテスト） | 2週間の連続稼働で重大な問題なく動作継続 | 検証端末を連続稼働させ日次で状態確認 | 稼働ログ・クラッシュ監視 | 長期測定 | チーム合意 | — | 未測定（スケジュール都合） |

### §5 逸脱記録（記入例）

| # | 対象指標ID | 実測値と基準値の差 | 影響範囲 | リリースする理由 | 回避策・軽減策 | 改善期限 | 担当 | 承認者 |
|---|---|---|---|---|---|---|---|---|
| 1 | PE-04 | +14MB（基準 10MB以下） | 長期稼働時にメモリ不足で再起動が発生する可能性。1日1回の定時再起動運用下では影響は限定的 | 顧客要望の機能追加を優先。定時再起動運用でリスクを軽減できる見込み | 定時再起動の運用手順を顧客に案内。OOM発生を監視 | 2026-11-30 | [開発リーダー] | [PdM] |
| 2 | RE-03 | 未測定（スケジュール都合） | 長期稼働時の安定性が未確認 | リリース後に本番環境でモニタリングし、問題があれば即時パッチ対応する体制を確保 | リリース後2週間、クラッシュ監視を日次確認 | 2026-10-15 | [QA担当] | [PdM] |

> **記入例の要点:** 逸脱記録では「なぜ止めないのか」と「代わりに何をするのか」が必ず対になっています。この2つが書けない場合は、リリースすべきでない可能性が高いです。

## 4. CSV出力用フォーマット

集計やテスト管理ツールへの取り込みのため、§4 をCSVで扱う場合のヘッダ定義です。

```csv
label,metric_id,quality_characteristic,criteria,threshold,measurement_method,data_source,timing,basis,source_url,actual_value,result
```

| 列名 | 対応 |
|---|---|
| `label` | P1 / P2 / P3 |
| `metric_id` | 指標ID |
| `quality_characteristic` | ISO特性名 |
| `criteria` | 判定基準 |
| `threshold` | 基準値 |
| `measurement_method` | 測定方法 |
| `data_source` | データソース |
| `timing` | 判定タイミング |
| `basis` | 根拠区分 |
| `source_url` | 出典URL |
| `actual_value` | 実測値 |
| `result` | pass / fail / not_measured |

## 5. 参考：元の4列フォーマットからの変更点

| 元の列 | 本テンプレート | 変更理由 |
|---|---|---|
| ラベル | ラベル | 変更なし（P3 を追加） |
| 品質特性 | 品質特性 | ISO 2023 の名称に統一 |
| 品質判定基準 | 判定基準 | 変更なし |
| 推奨基準 | 基準値 | 「推奨」を外し、合意済みの確定値であることを明示 |
| — | **指標ID** | カタログとの往復・実績の蓄積のため |
| — | **測定方法** | 判定時に解釈が割れるのを防ぐため |
| — | **データソース** | 誰が見ても同じ数字に辿り着けるようにするため |
| — | **判定タイミング** | いつ測るかを決めないと測られないため |
| — | **根拠区分** | 閾値見直し時に根拠を追えるようにするため |
| — | **実測値** | 「OK」だけの記録を禁止するため |
| — | **判定** | Pass / Fail / 未測定 を明示的に区別するため |

「未達時の扱い」は列にせず、**ラベルから一意に決まります**（02 を参照）。列を増やしすぎないための判断です。
