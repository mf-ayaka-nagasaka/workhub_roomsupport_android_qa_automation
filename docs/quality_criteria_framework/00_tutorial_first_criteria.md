# 00. はじめての品質判定基準づくり（30分）

| 項目 | 内容 |
|---|---|
| **象限** | 🐣 チュートリアル |
| **対象者** | 品質判定基準をはじめて作る方（QA・開発・PdM いずれでも） |
| **ゴール** | 架空のプロダクトを題材に、質問票への回答から判定基準表を作るまでを一通り体験し、フレームワークの仕組みを掴めるようになります |

このチュートリアルは**練習用**です。実務の基準をここで作るのではなく、「どう動くか」を30分で体験することが目的です。網羅性は追いません。

用意するものはありません。手を動かしながら読み進めてください。

---

## 1. 題材：架空のプロダクト

以下の架空プロダクトを題材にします。

> **「社内備品の貸出管理Webアプリ」**
> 社員が備品を検索して貸出申請し、管理者が承認します。ブラウザから使います。
> 備品データは数千件あり、管理者はCSVで一括登録もします。
> 部署ごとにデータが分かれており、他部署のデータは見えてはいけません。

実務では、この説明を「04. コンテキストプロファイル質問票」を使って構造化します。今回はその縮小版をやってみます。

---

## 2. ステップ1：5つの質問に答える（5分）

本来の質問票は約24問ありますが、ここでは5問だけ答えます。上の説明を読んで、答えを考えてみてください。

| # | 質問 | 答え |
|---|---|---|
| A-2 | 対象プラットフォームは？ | **Web** |
| C-1 | 複数の組織のデータを同一基盤で扱うか？ | **はい**（部署ごとに分かれている） |
| C-4 | 一覧・検索で扱う想定最大件数は？ | **数千件** |
| C-5 | CSV等での一括登録機能があるか？ | **はい** |
| C-6 | 不可逆な操作があるか？ | **はい**（備品データの削除） |

ここで大事なのは、**プロダクトの機能ではなく「利用のされ方」を答えている**ことです。「貸出申請できる」ではなく「複数組織のデータを扱う」「数千件ある」を聞いています。

---

## 3. ステップ2：文脈タグを立てる（3分）

答えから、機械的に**文脈タグ**を導き出します。対応表は「04」の §7 にあります。

| 質問の答え | 立つタグ |
|---|---|
| C-1 = はい | `マルチテナント` |
| C-4 = 数千件 | `大量データ表示` |
| C-5 = はい | `一括インポート・エクスポート` |

**これがフレームワークの心臓部です。** 「部署ごとにデータが分かれている」という一言が、`マルチテナント` というタグに変換されました。このタグが次のステップで指標を呼び出します。

---

## 4. ステップ3：指標を引き当てる（10分）

「03. 指標カタログ」から、以下の条件で指標を絞り込みます。

```
対象PF = Web または 共通
かつ
（文脈タグなし ＝ 無条件採用）または（立ったタグを持つ）
```

練習として、ここでは5つだけ拾ってみます。

| 指標ID | 指標名 | 拾えた理由 |
|---|---|---|
| FS-01 | 未対応 Critical 不具合件数 | タグなし＝無条件で採用 |
| FS-03 | 業務シナリオテスト通過率 | タグなし＝無条件で採用 |
| SE-01 | テナント間データ分離 | `マルチテナント` が立ったため |
| FS-06 | 一括インポート／エクスポートのデータ整合性 | `一括インポート・エクスポート` が立ったため |
| PE-07 | 大量データ時の容量耐性 | `大量データ表示` が立ったため |

**逆に、拾われなかった指標にも注目してください。**

| 拾われなかった指標 | 理由 |
|---|---|
| RE-02（ANR発生率） | 対象PFが Android。Webなので対象外 |
| PE-05（発熱・Thermal Status） | 対象PFが Android、かつ `常時稼働` タグも立っていない |
| SA-01（フェイルセーフ） | `ハードウェア連携` タグが立っていない |

この「自動的に外れる」動きが、フレームワークを使う最大の利点です。**モバイル向けの基準表をそのままコピーしていたら、意味のない指標が大量に紛れ込んでいました。**

---

## 5. ステップ4：判定基準表に転記する（10分）

「05. 判定基準テンプレート」の形式に転記します。練習なので5行だけです。

| ラベル | 指標ID | 品質特性 | 判定基準 | 基準値 | 測定方法 | データソース | 判定タイミング | 根拠区分 |
|---|---|---|---|---|---|---|---|---|
| P1 ★★★ | FS-01 | 機能適合性 | 未対応 Critical 不具合件数 | 0件 | 不具合管理ツールで重要度フィルタ | 不具合DB | リリース判定会議時点 | 組織標準 |
| P1 ★★★ | FS-03 | 機能適合性 | 業務シナリオテスト通過率 | 100% | テスト実行結果の集計 | テスト管理ツール | テストフェーズ完了時 | チーム合意 |
| P1 ★★★ | SE-01 | セキュリティ | テナント間データ分離 | 他部署のデータが一切参照できないこと | 複数部署アカウントでの越境アクセス試行 | 画面＋APIレスポンス | テストフェーズ完了時 | チーム合意 |
| P1 ★★★ | FS-06 | 機能適合性 | 一括登録のデータ整合性 | 投入データと出力データが完全一致 | 既知データセットの往復検証 | 差分ツール出力 | テストフェーズ完了時 | チーム合意 |
| P2 ★★ | PE-07 | 性能効率性 | 大量データ時の容量耐性 | 5,000件で表示破綻・性能劣化なし | 5,000件投入し一覧・検索を操作 | 画面確認＋応答時間計測 | テストフェーズ完了時 | チーム合意 |

カタログから転記しただけですが、**1箇所だけ自分で決めた**ところがあります。PE-07 の「5,000件」です。

カタログには「想定最大件数」としか書かれていません。**件数はプロダクトごとに違うため、カタログ側には数字を持たせていない**からです。ステップ1で「数千件」と答えた内容を、ここで具体的な数字にしました。

## 6. ステップ5：スコープ外を宣言する（2分）

最後に、**扱わなかった品質特性を明示的に記録します。** 空欄のまま放置しません。

| 品質特性 | 今回の扱い | 理由 |
|---|---|---|
| 互換性 | スコープ外 | 練習のため（実務では対応ブラウザの確認が必要） |
| 相互作用機能 | スコープ外 | 練習のため |
| 信頼性 | スコープ外 | 練習のため |
| 保守性 | スコープ外 | 練習のため |
| 柔軟性 | スコープ外 | 練習のため |
| 安全性 | スコープ外 | 物理デバイスの制御がないため |

実務では「練習のため」とは書けません。**「なぜ見ないのか」を説明できない特性は、本当は見るべき特性です。**

---

## 7. ここまでで体験したこと

30分で作った5行の表ですが、フレームワークの全工程を通っています。

```
利用のされ方を聞く（ステップ1）
      ↓
文脈タグに変換する（ステップ2）
      ↓
タグで指標を引き当てる（ステップ3）
      ↓
プロダクト固有の数字だけ自分で決める（ステップ4）
      ↓
見ない特性を記録する（ステップ5）
```

**「自分で数字を決める」のはステップ4の一部だけ**という点が重要です。残りは質問への回答から機械的に決まります。だからこそ、別のプロダクトでも同じ手順が使えます。

## 8. 次にやること

実務の基準を作る準備ができました。以下の順に進めてください。

| 順番 | やること | 参照先 |
|---|---|---|
| 1 | 不具合の重要度定義を確認する | 06. 不具合重要度モデル |
| 2 | 質問票（全24問）に回答する | 04. コンテキストプロファイル質問票 |
| 3 | 指標を引き当てる | 03. 指標カタログ |
| 4 | ラベル・閾値・根拠を決める | 02. 運用ルール |
| 5 | 判定基準表に転記して合意を取る | 05. 判定基準テンプレート |

**ステップ1（重要度定義の確認）を飛ばさないでください。** これが決まらないと FS-01 の「Critical とは何か」が定義できません。

### Claude Code で自動化する場合

上の2〜5は、Claude Code の Skill で対話しながら進められます。手順は **08. Claude Code のSkillで品質判定基準を作る** を参照してください。

```
/quality-criteria-generator [プロダクト名]
```

Skillが質問票の質問を投げかけ、回答から指標を導出し、判定基準のドラフトまで生成します。**閾値の確定と関係者の合意は人が行います。**

「そもそも品質判定基準とは何か」を先に理解したい場合は、01. 品質判定基準とは を読んでください。
