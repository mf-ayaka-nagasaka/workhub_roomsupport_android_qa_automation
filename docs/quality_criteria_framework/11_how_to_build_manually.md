# 11. 手で品質評価計画書を作る

| 項目 | 内容 |
|---|---|
| **象限** | 🛠️ ハウツーガイド |
| **対象者** | Claude Code を使わずに品質評価計画書を作るQA担当 |
| **ゴール** | 新規プロダクトの品質評価計画書を、どの順に何をすればよいか迷わず最後まで作り切れるようになります |

**Claude Code が使える場合は 08 を参照してください。** 本書と同じ工程を Skill が対話で進めます。本書は Skill を使わない場合の手順書です。

> **はじめて触る方は、先に 00. はじめての品質評価計画書づくり を30分で通してください。** 架空プロダクトで全工程を体験してから本書に入ると、迷いが減ります。

---

## 1. 全体の流れ

```
[準備] 不具合重要度定義の確認（06）
   ↓
[1] 利用文脈を確定させる（04）        … 30〜60分・開発リーダーと一緒に
   ↓  文脈タグが確定
[2] 指標を引き当てる（03）            … 30分
   ↓  採用指標が確定
[3] ラベル・閾値・根拠を決める（02）  … 1〜2時間・関係者と合意
   ↓
[4] 品質評価計画書に転記する（05）
   ↓
[5] セルフチェックと申し送り
   ↓
[6] 関係者の合意を取る → 運用開始
```

**所要は合計2〜3時間**（回答者との打ち合わせ時間を含む）です。1人で完結しません。**[1] は開発リーダー、[3] と [6] は PdM・開発リーダーの同席が必要**です。

---

## 2. 準備：不具合重要度定義の確認

**最初に、自組織の不具合重要度定義を確認します。** これが決まらないと機能適合性の判定基準（FS-01 / FS-02 / FS-12）が書けません。

| 状況 | やること |
|---|---|
| 定義があり、段階ごとのリリース可否も決まっている | 06 §3 の変換ルールでラベルに対応付け、所在を組織プロファイル §2 に記入します |
| 定義はあるが、リリース可否が紐づいていない | 段階ごとに「リリース不可／条件付き可／可」のどれに当たるかを関係者で合意します（06 §4） |
| **定義が無い／見つからない** | **止まらなくて構いません。** 06 §5-1 の記入例を暫定採用して先に進み、**「自組織の重要度定義を整備する」タスクを起票**します（[5] の申し送りに必ず含めます） |

> **組織プロファイルが未作成でも進められます。** 未記入の項目は「後で埋める」として記録し、作業を止めないでください。ただし同じ聞き取りを毎回繰り返すことになるため、2プロダクト目に入る前に作成することを推奨します。

---

## 3. 手順

### [1] 利用文脈を確定させる

**使うもの:** 04. コンテキストプロファイル質問票

| 順 | やること | 参照先 |
|---|---|---|
| 1-0 | （任意）ソースコードから回答を下書きする | 07 |
| 1-1 | A群（前提情報）に回答する | 04 §4 |
| 1-2 | A-2 の回答に応じて M群 または W群 に回答する | 04 §5 |
| 1-3 | C群・D群・E群・F群に回答する | 04 §6 |
| 1-4 | A-5 が「はい」なら G群 に回答する | 04 §6-G |
| 1-5 | 回答から文脈タグを確定させる | 04 §7 |

**記入先:** プロダクトごとのページ・ファイルに残します。**04 そのものには書き込みません**（フレームワークの資産であり、プロダクトをまたいで共有するためです）。

> **「わからない」は「わからない」と書いてください。** 推測で埋めると誤った指標が採用されます。
> **E群（測定基盤）で「監視手段なし」と判明した指標は、この時点で採用対象から外します。** 測れないものは基準にできません。外した事実は [5] で記録します。

**完了条件:** 文脈タグの一覧が確定し、A群に未回答が無い。

---

### [2] 指標を引き当てる

**使うもの:** 03. 指標カタログ（実体は自組織の指標DB、または `assets/metrics_catalog.csv`）

```
採用指標 =（対象PFが一致する指標）
        ∩（文脈タグなし ∪ [1] で立ったタグを持つ指標）
        −（E群で測定手段なしと判明した指標）
```

1. 対象PF（Android / iOS / Web / 共通）で絞り込みます
2. 文脈タグで絞り込みます。**タグが付いていない指標は無条件で採用候補**です
3. **AI/ML機能がある場合**（A-5 が「はい」）は、`metrics_catalog_ai_extension.csv` の AQ指標10件も母集団に加えます（10. AI拡張）
4. **除外した指標と除外理由**（PF不一致／タグ不成立／測定手段なし）を控えておきます。[5] で使います
5. ISO 9特性のうち**採用候補が0件の特性**を特定します。本当にスコープ外でよいかを確認し、必要なら新規指標を `NEW-01` 等のIDで追加します

**完了条件:** 採用指標の一覧と、除外指標＋理由の一覧がそろっている。

---

### [3] ラベル・閾値・根拠を決める

**使うもの:** 02. 運用ルール、03 の推奨初期値

**ラベル（P1 / P2 / P3）**

カタログの推奨ラベルを初期値とし、02 §1 の4つの問いをプロダクトの文脈に当てはめて調整します。

> **P1 が採用指標の6割を超えたら見直してください。** 逸脱承認が常態化し、ラベルが意味を失います。

**閾値（基準値）**

以下の優先順位で決めます。**根拠が無い数字は置きません。**

| 優先 | 根拠区分 | 決め方 |
|---|---|---|
| 1 | 契約・SLA由来 | F-1 の回答から逆算。SLAより緩い基準は設定しません |
| 2 | 標準由来 / 業界基準 | カタログの推奨初期値を採用し、**出典URLを必ず併記**します |
| 3 | 実測ベース | E-3 のベースラインがある場合のみ |
| 4 | ベースライン比較 | **出力が毎回同じとは限らない指標（AQ群）はここ。** 前バージョンとの非劣化で判定します（02 §9） |
| 5 | チーム合意 | 推奨初期値を提示し、関係者で合意します |
| 6 | TBD | 上記いずれも不可の場合。**確定期限を必ず設定**します |

**プロダクト固有の値を具体化します。** 「主要データ書き込み操作」→ D-4 の回答、「想定最大件数」→ C-4 / C-5 の回答、など。

**完了条件:** 全採用指標にラベル・基準値・根拠区分がある。TBD には確定期限がある。

---

### [4] 品質評価計画書に転記する

**使うもの:** 05. 品質評価計画書テンプレート

05 §2 のテンプレートを複製し、以下の5セクションをすべて埋めます。

| セクション | 書くこと |
|---|---|
| §1 基本情報 | プロダクト名・対象リリース・判定対象範囲・作成者 |
| §2 コンテキストサマリ | [1] の回答要約、立った文脈タグ、重要度定義の参照先、監視基盤。**AI機能がある場合はゴールデンセットの版と件数も** |
| §3 スコープ宣言 | **ISO 9特性すべて**の扱い（対象／一部／スコープ外）と理由。**空欄禁止** |
| §4 品質測定量に対する判定基準一覧 | [3] の結果を11列で記入。実測値・判定列は判定時に埋めます |
| §5 判定結果と逸脱記録 | 空のまま（判定時に記入） |

> **テスト環境のURL・アカウント情報は書きません。** 「QA環境」「[検証用端末A]」等のプレースホルダーを使います（02 §3）。

**完了条件:** §1〜§4 が埋まり、空欄が無い（TBD は可）。

---

### [5] セルフチェックと申し送り

転記が終わったら、以下を自分で確認します。

- [ ] ISO 9特性すべてが §3 に記載されている（空欄なし）
- [ ] 不具合重要度定義の参照先が §2 に書かれている
- [ ] 対象PFに合致しない指標が混入していない
- [ ] 根拠区分が「標準由来」「業界基準」の指標に出典URLがある
- [ ] 基準値が空欄の指標が無い（TBD は可、空欄は不可）
- [ ] TBD の全指標に確定期限と担当がある
- [ ] 測定方法とデータソースが全指標に書かれている
- [ ] 環境URL・アカウント情報が書かれていない
- [ ] P1 の比率が過大でない

**申し送り事項**として以下を明示的に残します。

1. **TBD 指標の一覧と確定期限** — 誰がいつまでに実測するか
2. **未回答だった質問と、その結果採用できなかった指標**
3. **測定手段未整備の指標** — 監視の仕込みが必要なもの
4. **カタログへの登録候補** — `NEW-` で追加した指標
5. （重要度定義が無かった場合）**定義を整備するタスクの起票**

---

### [6] 合意を取る

**判定基準は合意されて初めて機能します。** 以下を関係者（プロダクト意思決定責務・技術判断責務・品質判断責務）で確認し、合意日と合意者を §1 に記入します。

- P1 の指標について、**本当にリリースを止める覚悟があるか**
- TBD の確定期限が現実的か
- スコープ外とした特性の理由に納得できるか

> **テストフェーズ開始後は原則変更できません**（02 §6）。合意前に違和感を潰してください。

---

## 4. 詰まりやすいところ

| 症状 | 対処 |
|---|---|
| A-1（重要度定義）で止まる | 06 §5-1 の記入例を暫定採用して進みます。整備タスクを起票すれば問題ありません |
| 指標が少なすぎる | 文脈タグがほとんど立っていない可能性があります。C群・D群の回答を見直してください |
| 指標が多すぎる／P1 だらけ | 02 §1 の4つの問いを厳密に当ててください。「止める覚悟があるか」が基準です |
| 閾値が決められない | **TBD＋確定期限で構いません。** 根拠のない数字を置くより健全です |
| 測定手段が無い指標がある | 採用せず「測定手段未整備」として記録し、次リリースまでの整備をタスク化します |
| AI機能があるが精度の基準が置けない | ゴールデンセットが無ければ AQ-01 / AQ-02 / AQ-08 は採用しません（10 §6-1） |

---

## 5. 運用開始後

| タイミング | やること | 参照先 |
|---|---|---|
| 判定タイミングごと | 実測値を §4 に記録する。**「OK」だけの記録は不可** | 02 §3 |
| リリース判定時 | 基準と照合し §5 に総合判定を記入。P1 未達なら逸脱承認フローへ | 02 §5 |
| リリース後 | TBD だった指標の実測値をカタログに反映。`NEW-` 指標を正式登録 | 03 §8 |
