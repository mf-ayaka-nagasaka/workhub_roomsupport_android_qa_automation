# 01. 品質判定基準とは

| 項目 | 内容 |
|---|---|
| **象限** | 🧠 解説・説明 |
| **対象者** | QA担当、開発リーダー、PdM、リリース可否を判断する立場の全員 |
| **ゴール** | 品質判定基準の定義・目的・役割を共通認識として持ち、他の概念（テスト計画・受入基準・SLA）と区別できるようになります |

---

## 1. 定義

**品質判定基準**とは、あるプロダクトを**リリースしてよいかどうかを判断するための、事前に合意された観測可能な合否ライン**です。

以下の3要素をすべて満たすものだけを品質判定基準と呼びます。

| 要素 | 内容 | 満たさない例 |
|---|---|---|
| **観測可能性** | 誰が測っても同じ結果になる測定方法とデータソースがある | 「動作が軽快であること」 |
| **合否の明確さ** | 閾値があり、満たす／満たさないが二値で判定できる | 「なるべくクラッシュしないこと」 |
| **事前合意** | リリース判定の場ではなく、それ以前に関係者が合意している | 判定会議でその場で決めた基準 |

---

## 2. 目的

### 2-1. リリース可否判断を属人化させない

「QAが大丈夫と言ったから出す」という判断を、「合意済みの基準を満たしたから出す」に置き換えます。これにより判断の再現性と説明責任が担保されます。

### 2-2. 判定の場を「交渉」ではなく「照合」にする

閾値を事前に決めておくことで、リリース判定会議では**基準を満たしたかどうかの照合**だけを行います。不具合が出てから「この程度なら許容範囲か」を議論すると、スケジュール圧力によって判断が歪みます。

### 2-3. 品質の観点漏れを防ぐ

ISO/IEC 25010 の品質特性を網羅的に見たうえで「今回はどこを見て、どこを見ないか」を明示します。**見ないと決めたこと自体を記録に残す**ことが重要です。

### 2-4. テスト活動のゴールを定義する

品質判定基準は、テスト計画・テスト設計の上位にあります。「何をもってテストが十分か」を基準から逆算できます。

---

## 3. 役割（誰が何をするか）

| ロール | 責務 |
|---|---|
| **QA担当** | 基準のドラフト作成、測定の実施、判定結果の記録 |
| **開発リーダー** | 測定方法の実現可能性レビュー、技術的な閾値の妥当性判断 |
| **PdM / プロダクトオーナー** | 事業観点での閾値の承認、未達時のリリース可否の最終判断 |
| **全員（合意の場）** | 基準の事前合意、スコープ外とする品質特性の承認 |

---

## 4. 品質判定基準では「ないもの」（非目的）

誤用を防ぐため、以下は品質判定基準の役割ではないことを明示します。

| 混同されやすいもの | 違い |
|---|---|
| **テスト計画書** | テスト計画は「どうテストするか」。品質判定基準は「何をもって合格とするか」 |
| **受入基準（Acceptance Criteria）** | 受入基準は個々の機能・ストーリー単位。品質判定基準はリリース単位・プロダクト単位 |
| **SLA / SLO** | SLAは本番運用中の対外的な約束。品質判定基準はリリース前の内部ゲート。参照はしますが同一ではありません |
| **品質目標（KPI）** | KPIは改善の方向性。品質判定基準は特定リリースの合否ライン |
| **不具合の重要度定義** | 重要度定義は品質判定基準の**入力**であり、基準そのものではありません |

また、以下は品質判定基準として設定してはいけません。

- **測定方法が定まっていない指標** — 判定時に必ず解釈が割れます
- **測定コストが判定サイクルに見合わない指標** — 形骸化して「未測定」のまま通過します
- **チームがコントロールできない指標** — 外部SDK・バックエンド内部の品質など（※アプリ側のハンドリングは対象です）

---

## 5. 品質判定基準の適用ライフサイクル

```
[1] 企画・要件定義フェーズ
     └─ コンテキストプロファイル記入 → 基準ドラフト作成
[2] 開発フェーズ
     └─ 基準の関係者合意（ここで確定・以降は変更に承認が必要）
     └─ 測定可能性の実装（ログ・監視の仕込み）
[3] テストフェーズ
     └─ ベースライン計測（TBD項目の閾値確定）
[4] リリース判定
     └─ 基準との照合 → 合否判定 → 未達項目の逸脱承認
[5] リリース後
     └─ 実測値のフィードバック → 次回の閾値・指標カタログを更新
```

**[5] のフィードバックがフレームワークの生命線です。** リリース後の実測値を指標カタログの「推奨初期値」に反映しない限り、閾値はいつまでも根拠のない数字であり続けます。

## 6. 基礎となる標準

本フレームワークは品質特性の分類軸として **ISO/IEC 25010:2023（システム及びソフトウェア製品の品質モデル）** を採用しています。

2011年版（8特性）ではなく **2023年版（9特性）** を採用する理由は以下の3点です。

- `相互作用機能（Interaction Capability）` が独立し、ユーザビリティ・アクセシビリティを扱えるようになりました
- `柔軟性（Flexibility）` が新設され、マルチブラウザ・マルチテナント等の適応性を扱えるようになりました
- `安全性（Safety）` が新設され、ハードウェア連携プロダクトのリスクを扱えるようになりました

## 7. ISO/IEC 25010:2023 品質特性一覧（分類軸）

| # | 品質特性 | 英語名 | 副特性 |
|---|---|---|---|
| 1 | 機能適合性 | Functional Suitability | 機能完全性 / 機能正確性 / 機能適切性 |
| 2 | 性能効率性 | Performance Efficiency | 時間効率性 / 資源効率性 / 容量満足性 |
| 3 | 互換性 | Compatibility | 共存性 / 相互運用性 |
| 4 | 相互作用機能 | Interaction Capability | 適切度認識性 / 習得性 / 操作性 / ユーザーエラー防止性 / ユーザーエンゲージメント / インクルーシビティ / ユーザー支援性 / 自己記述性 |
| 5 | 信頼性 | Reliability | 無欠陥性 / 可用性 / 障害許容性 / 回復性 |
| 6 | セキュリティ | Security | 機密性 / インテグリティ / 否認防止性 / 責任追跡性 / 真正性 / 抵抗性 |
| 7 | 保守性 | Maintainability | モジュール性 / 再利用性 / 解析性 / 修正性 / テスト容易性 |
| 8 | 柔軟性 | Flexibility | 適応性 / 拡張性 / 導入性 / 代替性 |
| 9 | 安全性 | Safety | 運用上の制約 / リスク特定 / フェイルセーフ / 危険警告 / 安全統合 |

各副特性の詳細な定義は §6 の参考URLを参照してください。プロダクト別のテスト観点辞書を別途持っている場合は、そちらを併用します。
