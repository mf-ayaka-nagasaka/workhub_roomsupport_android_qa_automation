# 10. AI拡張（AI/ML機能を含むプロダクト向け）

| 項目 | 内容 |
|---|---|
| **象限** | 📗 リファレンス |
| **対象者** | AI/ML機能を含むプロダクトのQA担当・開発リーダー・PdM |
| **ゴール** | AI/ML機能に固有の品質特性を判定基準として表現し、出力が毎回同じとは限らない指標でも合否を判定できるようになります |

**AI/ML機能を含まないプロダクトでは、本書を読む必要はありません。** 本書で追加する指標（AQ群）と文脈タグは、04 §4 の A-5 で「AI/ML機能を含む」と回答した場合にのみ採用候補になります。

---

## 1. このドキュメントの位置づけ

本フレームワークの本体（00〜09）は、ISO/IEC 25010:2023 の9特性を分類軸としています。**AI/ML機能を含むプロダクトでは、この9特性だけでは表現しきれない品質があります。**

| 本体では表現しづらいこと | 例 |
|---|---|
| 同じ入力でも出力が毎回同じとは限らない | 認識・推論結果のばらつき |
| モデルの更新によって、コードを変えずに振る舞いが変わる | SDK・モデル版の更新 |
| 判断の根拠が利用者に見えない | 認識に失敗した理由が分からない |
| 自動判断を人が止められないと危害につながりうる | 誤認識のまま物理デバイスを制御する |

**ISO/IEC 25059:2023** は、この差分を扱うために 25010 を拡張した規格です。25010 を置き換えるものではなく、**AI固有の特性のみを追加し、残りは親モデルを継承します。** 本書もその構造を踏襲し、本体に手を入れず**追加レイヤー**として定義しています。

```
[01 §7] ISO/IEC 25010:2023 の9特性     ← 本体の分類軸（AIの有無によらず適用）
                 ＋
[10 §3]   AI固有の副特性（5つ）        ← 本書。A-5 が「はい」のときのみ
                 ↓
[10 §5]   AQ指標群（10指標）           ← 既定で非採用。タグ `AI機能あり` が必須
```

### 「ISO/IEC 25059 準拠」とは記載しません

09 §1 と同じ方針です。本書は **25059 を参考にした拡張（based on）** であり、適合性評価を受けていません。加えて **25059 は 2026-03 に改訂版の公開審査（DIS）が終了し、改訂が進行中**です。版が変わる前提で参照してください（§8）。

規格本文は有償のため、本書には**副特性の位置づけの要約のみ**を記載し、定義文は転載していません。正確な定義は §9 の出典から規格を参照してください。

## 2. 適用の判断

以下のいずれかに当てはまる場合、本書の対象です。

| # | 条件 | 例 |
|---|---|---|
| 1 | 学習済みモデルによる推論結果を、機能の成否判断に使っている | 生体認証、画像認識、異常検知 |
| 2 | 生成系モデルの出力を、ユーザーに提示している | 要約、文章生成、対話 |
| 3 | 利用データに応じて振る舞いが変化する仕組みを持つ | レコメンド、学習型の最適化 |

**外部のAI SDK・AI APIを呼び出しているだけの場合も対象です。** 自前でモデルを学習していなくても、出力の不確実性はアプリ側に現れるためです。責務の線引きは §4 を参照してください。

逆に、以下は対象外です。

- 固定のルール・しきい値による判定（「AI」と呼んでいても、入力が同じなら出力が常に同じもの）
- モデルの出力を一切使わず、ログ収集のみを行っている機能

## 3. 追加される副特性（ISO/IEC 25059 を参考）

25059 が 25010 の親特性に追加する副特性のうち、リリース前の内部ゲートで観測できるものを採用しています。

| 親特性（25010） | 追加される副特性 | 位置づけの要約 | 本書での扱い |
|---|---|---|---|
| 機能適合性 | **機能適応性**（Functional Adaptability） | データや過去の結果から情報を獲得し、以降の予測に使える度合い | AQ-01 / AQ-02 |
| 相互作用機能 | **ユーザー制御性**（User Controllability） | 利用者がAIの動作に適切に介入できる度合い | AQ-03 / AQ-04 |
| 相互作用機能 | **透明性**（Transparency） | AIシステムに関する十分な情報が関係者に伝達される度合い | AQ-05 / AQ-06 |
| 信頼性 | **ロバストネス**（Robustness） | あらゆる状況下で性能水準を維持できる度合い | AQ-07 / AQ-08 |
| セキュリティ | **介入可能性**（Intervenability） | 危害を避けるため運用者が適時に介入できる度合い | AQ-09 / AQ-10 |

> **親特性は 25010 のままです。** AQ指標も 03 の指標カタログと同じ「ISO特性」列を使い、上表の親特性に分類します。スコープ宣言（02 §7）も9特性の枠組みのまま運用します。

### 周辺の標準

AIの品質を扱う際、25059 の周辺に以下の規格があります。**本フレームワークはいずれも採用していません**が、取り組みを広げる際の参照先として記載します。

| 規格 | 扱う範囲 | 本フレームワークとの関係 |
|---|---|---|
| **ISO/IEC TR 29119-11:2020** | AIベースシステムのテスト。**テストオラクル問題**（期待結果を一意に定義できない問題）を扱います | §6 の非決定的指標の判定ルールが対応する課題です |
| **ISO/IEC 5259 シリーズ** | 機械学習用データの品質 | ゴールデンセット（§6）の整備品質に関わります。学習データ自体の品質保証は本フレームワークの対象外です |
| **ISO/IEC 42001** | AIマネジメントシステム（組織の仕組み） | 組織としてのAIガバナンス。リリース判定ゲートの外側です |
| **ISO/IEC 22989** | AIの用語・概念 | 用語定義の参照先です |

## 4. 外部AI SDK・AI APIを利用する場合の責務の線引き

**ベンダーが提供するモデルの性能そのものは、判定基準にしません。** 自組織で制御できない値を基準に置くと、未達時に打つ手がなく逸脱承認が常態化します。

判定基準にするのは、**モデルの出力を受け取ったアプリが何をするか**です。

| 対象外（ベンダー責務） | 対象（アプリ責務＝指標にする） |
|---|---|
| モデルそのものの認識・推論精度 | 失敗時に代替手段への導線が出るか（AQ-04） |
| 内部のしきい値アルゴリズム | SDKが返す失敗・タイムアウトを正しくハンドリングするか（FS-05） |
| モデルの学習プロセス・学習データ | 誤った結果をユーザー・管理者が取り消せるか（AQ-03） |
| ベンダー公表のベンチマーク値 | 自プロダクトの利用条件下でのフォールバック動作（AQ-07） |

> **既存の FS-05（外部SDKの成否ハンドリング）で足りる部分は、AQ指標を追加しません。** AQ群は「SDKが成功を返したあとに残る不確実性」を扱います。

### 精度そのものを基準にしたい場合

ベンダーの精度を基準に置くのは、**契約・SLAでその水準が約束されている場合に限ります。** その場合の根拠区分は `契約・SLA由来` です（02 §8）。約束がない場合は、自プロダクトのゴールデンセットに対する実測（AQ-01）を基準にし、ベンダー値は参考値として併記してください。

## 5. AQ指標群（AI拡張指標）

**全10指標です。すべて文脈タグが必須のため、既定では採用されません。** AI/ML機能を含まないプロダクトでは、1件も母集団に入りません。

> **AQ指標は本体の `assets/metrics_catalog.csv`（59行）には含まれず、`assets/metrics_catalog_ai_extension.csv`（10行）として分離しています。** AI/ML機能を含むプロダクトでは、このファイルを自組織の正本DBへ**追加インポート**してください。列定義は本体CSVと同一（スキーマは 03 §5）なので、同じDBにそのまま追加できます。

### 5-1. 指標一覧

| 指標ID | 指標名 | ISO特性 | 25059副特性 | 文脈タグ | 推奨ラベル | 推奨初期値 | 判定タイミング | 根拠区分 |
|---|---|---|---|---|---|---|---|---|
| **AQ-01** | ゴールデンセットに対する成功率 | 機能適合性 | 機能適応性 | `AI機能あり` | P1 | TBD（ベースライン計測後に確定） | RC版での測定 | ベースライン比較 |
| **AQ-02** | モデル・SDK更新時の非劣化 | 機能適合性 | 機能適応性 | `モデル更新あり` | P1 | 前バージョンの成功率を下回らない（許容幅は合意値） | RC版での測定 | ベースライン比較 |
| **AQ-03** | AI判断の取り消し・再試行 | 相互作用機能 | ユーザー制御性 | `自動判断` | P1 | 誤った結果をユーザーまたは管理者が取り消せること | テストフェーズ完了時 | チーム合意 |
| **AQ-04** | 代替手段へのフォールバック導線 | 相互作用機能 | ユーザー制御性 | `AI機能あり` | P1 | AI機能の失敗時、代替手段への導線が画面上に提示されること | テストフェーズ完了時 | チーム合意 |
| **AQ-05** | AI処理であることの明示 | 相互作用機能 | 透明性 | `AI機能あり` | P2 | AIによる処理・判断であることが利用者に分かる表示があること | テストフェーズ完了時 | チーム合意 |
| **AQ-06** | 判断根拠・確信度の提示 | 相互作用機能 | 透明性 | `説明責任要求` | P2 | 判断の根拠または確信度が利用者・管理者に提示されること | テストフェーズ完了時 | チーム合意 |
| **AQ-07** | 悪条件入力でのフォールバック動作 | 信頼性 | ロバストネス | `AI機能あり` | P1 | 想定する悪条件の全ケースで、誤結果を確定させず失敗として扱うこと | テストフェーズ完了時 | チーム合意 |
| **AQ-08** | 出力のばらつき（再現性） | 信頼性 | ロバストネス | `非決定的出力` | P2 | 同一入力のn回試行で結果一致率が合意値以上 | RC版での測定 | ベースライン比較 |
| **AQ-09** | AI機能の緊急停止 | セキュリティ | 介入可能性 | `自動判断` | P1 | 運用者がアプリ更新を伴わずにAI機能を無効化できること | テストフェーズ完了時 | チーム合意 |
| **AQ-10** | AI判断の監査ログ | セキュリティ | 介入可能性 | `説明責任要求` | P1 | 入力の識別子・出力・モデル版・日時が追跡できること | テストフェーズ完了時 | 組織標準 |

### 5-2. 測定方法とデータソース

| 指標ID | 測定方法 | データソース |
|---|---|---|
| AQ-01 | 固定したゴールデンセット（§6-1）を投入し、期待結果と一致した件数の割合を算出します | ゴールデンセットの実行結果 |
| AQ-02 | 前バージョンと同一のゴールデンセットを同一条件で実行し、成功率を比較します | 前バージョンの実行結果との差分 |
| AQ-03 | AIが誤った結果を返した状態を再現し、取り消し操作が完了するまでを確認します | 画面操作＋データの最終状態 |
| AQ-04 | AI機能を失敗させた状態で、代替手段へ到達できるかを操作で確認します | 画面操作 |
| AQ-05 | AI処理を行う全画面で、表示・文言の有無を確認します | 画面表示 |
| AQ-06 | 判断結果の画面・ログで、根拠または確信度が確認できるかを見ます | 画面表示＋アプリログ |
| AQ-07 | §6-2 の悪条件ケース一覧を投入し、**誤った結果を確定させていないこと**を確認します | 画面表示＋アプリログ |
| AQ-08 | 代表入力を n 回（回数は合意値）投入し、結果が一致した割合を算出します | 実行結果の集計 |
| AQ-09 | 設定・リモート構成からAI機能を無効化し、代替手段のみで業務が完了することを確認します | 設定変更後の画面操作 |
| AQ-10 | AI判断を1件発生させ、ログに必要項目がそろっているかを確認します | アプリログ／ログ基盤 |

> **データソース列は、組織プロファイル §5 に記入した実際のツール名へ置き換えてください**（03 §5 と同じ運用です）。

## 6. 非決定的な指標をどう判定するか

**出力が毎回同じとは限らない指標は、「n回測ったうちの1回」では合否を判定できません。** 02 §9（非決定的指標の判定ルール）が本体側の規定で、本節はその適用手順です。

### 6-1. ゴールデンセットの整備（AQ-01 / AQ-02 / AQ-08 の前提）

**固定した評価用データセットがない状態で、AQ-01・AQ-02・AQ-08 を採用してはいけません。** 測定のたびに入力が変わると、値の変化がモデルの変化なのか入力の変化なのか切り分けられません。

| 要件 | 内容 |
|---|---|
| **固定されていること** | バージョン番号を付けて管理し、測定期間中は変更しません |
| **代表性があること** | 実際の利用条件の分布を反映します（良条件だけで構成しない） |
| **期待結果が確定していること** | 1件ごとに期待結果を人が確定させます |
| **悪条件を含むこと** | §6-2 の条件を一定割合で含めます |
| **件数が記録されていること** | 件数・作成日・更新履歴を残します |

ゴールデンセットの所在とバージョンは、**品質評価計画書（05 §2 コンテキストサマリ）に記載**してください。

> **ゴールデンセットの更新は、モデル更新と同時に行わないでください。** 両方を同時に変えると AQ-02（非劣化）が判定できなくなります。更新する場合は、更新前後の両方で一度ずつ測定し、差分の内訳を記録します。

### 6-2. 悪条件ケースの洗い出し（AQ-07）

悪条件は**プロダクトの利用環境から決まります。** 04 の回答を出発点に、以下の観点で列挙してください。

| 観点 | 例 |
|---|---|
| 入力品質の劣化 | 低照度・逆光・ノイズ・解像度不足・遮蔽 |
| 想定外の入力 | 対象が存在しない／複数存在する／範囲外の値 |
| 環境条件 | 通信遅延・帯域制限・端末負荷が高い状態 |
| 境界的な利用者 | 登録データとの差異が大きい状態 |

**AQ-07 の合否は「正しく認識できたか」ではありません。** 悪条件下での正解率はベンダー責務です（§4）。**誤った結果を確定させず、失敗として扱えたか**がアプリ側の判定対象です。

### 6-3. 基準値の書き方

非決定的指標の基準値には、**試行回数と許容幅を必ず含めます。**

| 書き方 | 可否 | 理由 |
|---|---|---|
| 「成功率 95%以上」 | ⚠️ 不十分 | 何件に対する95%かが不明で、再測定時に比較できません |
| 「ゴールデンセット v1.2（200件）に対し成功率 95%以上」 | ✅ 可 | 母数とデータセット版が特定できます |
| 「前バージョン比で成功率の低下が 2ポイント以内」 | ✅ 可 | 非劣化判定の形式です（AQ-02） |
| 「同一入力10回試行で結果一致率 90%以上」 | ✅ 可 | 試行回数が明示されています（AQ-08） |

## 7. 04 の質問票との対応（G群）

AI拡張の採用可否は、04 §4 の **A-5** と **G群**（04 §6-G）で決まります。

| 質問 | 条件 | 立つタグ | 採用される指標 |
|---|---|---|---|
| A-5 AI/ML機能を含むか | 「はい」 | `AI機能あり` | AQ-01 / AQ-04 / AQ-05 / AQ-07 |
| G-1 出力が毎回同じとは限らないか | 「はい」 | `非決定的出力` | AQ-08 |
| G-2 モデル・SDKの更新があるか | 「はい」 | `モデル更新あり` | AQ-02 |
| G-3 AIの判断がそのまま処理を確定させるか | 「はい」 | `自動判断` | AQ-03 / AQ-09 |
| G-4 判断の根拠提示・記録が求められるか | 「はい」 | `説明責任要求` | AQ-06 / AQ-10 |
| G-5 ゴールデンセットを持っているか | 「いいえ」 | （タグなし） | AQ-01 / AQ-02 / AQ-08 を**採用せず**「測定手段未整備」として記録します（§6-1） |

> **A-5 が「いいえ」の場合、G群には回答しません。** AQ指標は1件も母集団に入りません。
