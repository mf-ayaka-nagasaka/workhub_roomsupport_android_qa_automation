# 07. ソースコードから質問票の下書きを作る

| 項目 | 内容 |
|---|---|
| **象限** | 🛠️ ハウツーガイド |
| **対象者** | QA担当（質問票の記入者） |
| **ゴール** | ソースコードを調査して質問票の下書きを作り、回答漏れと推測回答を減らせるようになります |

質問票（04）をゼロから埋めると、回答漏れや推測での記入が発生します。ソースコードが参照できる場合は、**コードから下書きを作ってから人間がレビューする**手順に切り替えると精度が上がります。

---

## 1. 前提

- 対象プロダクトのソースコードが読める状態にあること
- 質問票（04）の構成を把握していること

Claude Code を使う場合は `/quality-criteria-generator [プロダクト名]` を実行すると、Step 2-0 でこの手順を自動で実施できます（Skill全体の使い方は 08 を参照）。手作業でも同じ調査ができます。

---

## 2. 手順

### 手順1：調査対象を絞る

次節の調査対象表にある項目だけを見ます。**闇雲に全コードを読まないでください。** 調査対象は「質問票のどの設問に答えるためか」が決まっているものに限定します。

### 手順2：調査して下書きを書く

調査結果を質問票の回答欄に書き込みます。このとき、**必ず根拠（ファイルパスと該当箇所）を併記します。**

記入例：

```
M-7 OS権限を要求するか？
  → はい（カメラ、位置情報）
     根拠: AndroidManifest.xml の uses-permission
```

**根拠を示せない項目は下書きしません。** 空欄のまま残し、手順4で人間に質問します。

### 手順3：コードで判断できない項目を分ける

以下は**コードからは判断できません。** 下書きせず、必ず人に聞きます。

| 設問 | なぜコードで分からないか |
|---|---|
| M-1（常時稼働） | 実装上は常駐できても、運用で電源を切るかは分からない |
| M-2（無人運用） | 異常時にその場に人がいるかは運用の話 |
| M-3（キオスク運用） | 設定の実装があっても実際にそう運用するかは別 |
| M-9（配布経路） | 配布方法は組織の運用ルール |
| A群すべて | 判定範囲・承認者は組織の話 |
| F群すべて | 契約・過去障害・法令要件は組織の話 |
| C-4（想定最大件数） | 現在のデータ量ではなく「想定」を聞いている |
| D-3（想定セッション長） | 設定値ではなく実際の利用実態 |

### 手順4：人間がレビューして確定する

下書きを表形式で提示し、**「この内容で合っているか」の確認を取ってから確定します。** 下書きをそのまま確定しないでください。

---

## 3. 調査対象と導出できる回答

### モバイル（Android）

| 調査対象 | 導出できる回答 |
|---|---|
| `AndroidManifest.xml` の `uses-permission` | M-7（OS権限利用）、M-4（カメラ・近距離無線通信等の利用） |
| `AndroidManifest.xml` の `lockTaskMode` / MDM設定 | M-3（キオスク運用）の**候補**（運用実態は要確認） |
| `build.gradle` の `minSdkVersion` / `targetSdkVersion` | M-9（対応OS範囲）、CO-01 の分母候補 |
| 依存関係（`build.gradle` の implementation） | M-5（外部SDK依存）、E-M1（監視ツール） |
| `WakeLock` / `ForegroundService` の使用 | M-1（常時稼働）の**候補**（運用実態は要確認） |
| ライフサイクル処理（`onPause` / `onResume`） | M-8（バックグラウンド動作） |

### Web

| 調査対象 | 導出できる回答 |
|---|---|
| `package.json` の依存関係 | W-2（レンダリング方式）、E-W1（監視ツール） |
| `browserslist` 設定 | W-1（対応ブラウザ） |
| CSS のメディアクエリ／ブレークポイント定義 | W-3（対応デバイス幅） |
| 認証関連の実装（SDK・ミドルウェア） | W-8（認証方式） |
| PDF・帳票生成ライブラリの有無 | W-7（帳票出力） |
| 楽観ロック・バージョン列の実装 | W-6（同時編集） |

### 共通

| 調査対象 | 導出できる回答 |
|---|---|
| データモデル・スキーマ定義（テナントID列の有無） | C-1（マルチテナント） |
| ロール・権限の定義箇所 | C-3（権限ロール、ロール種類数） |
| 個人情報・生体情報を扱うフィールド | C-2（個人情報取扱） |
| CSV・一括処理のエンドポイント・画面 | C-5（一括インポート・エクスポート） |
| 削除・一括更新のエンドポイント | C-6（不可逆操作） |
| オフラインキャッシュ・ローカルDBの実装 | D-1（オフライン耐性）、C-7（データ移行） |
| WebSocket・リアルタイムリスナーの実装 | D-2（リアルタイム同期） |
| セッション期限の設定値 | D-3（長時間セッション）の**候補** |
| 監視SDKの初期化コード | E-1、E-2、E-M1、E-W1 |

---

## 4. この手順の限界

コードから読み取れるのは「**実装されているか**」だけです。「**運用上どう使われるか**」は読み取れません。

| 分かること | 分からないこと |
|---|---|
| 使用しているSDK・権限・データモデル・エンドポイントの存在 | 誰がどこでどう使うか |
| 設定値・依存ライブラリ | 異常時にその場に人がいるか |
| 実装されている機能 | 契約上の約束・過去の障害 |

そして**品質判定基準の固有性は、後者から生まれます。** コード調査で埋まるのは質問票の半分程度、という前提で進めてください。残り半分は人に聞くしかありません。

---

## 5. 下書きの保存

確定した回答は、根拠のファイルパスを併記した状態で保存します。次回の見直し時に再調査しやすくなります。

```
docs/quality_criteria/{プロダクト名}/context_profile.md
```

Claude Code の Skill を使った場合は、この場所に自動で保存されます。
