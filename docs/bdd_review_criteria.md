# BDDテスト設計成果物 レビュー基準書

| 項目 | 内容 |
|---|---|
| **象限** | 📗 リファレンス |
| **対象者** | QA担当（BDDテスト設計成果物のセルフレビュー実施者） |
| **ゴール** | 外部レビューに出す前に、仕様書内の食い違い・検証力の弱いシナリオ・不足観点を、一定の基準で自力で洗い出せるようになります |

本書は **`/bdd-workflow-manager` で作成したBDDテスト設計成果物**（ルール・実例／Gherkinシナリオ／観点）をレビューするためのチェックリストです。手動テストケースのレビュー基準は `review_criteria.md`、開発チームの単体テストのレビュー基準は `unit_test_review_criteria.md` にあり、本書とは対象が異なります。

---

## 1. 本書の位置づけ

### 1.1 本書の成り立ち

本書の観点は、⑦「部屋の予約状況をホーム画面に表示できる」に対する外部レビュー（2026-10-21 受領）で挙がった **食い違い21件・不足観点35件を逆引きし、「どの観点で見たからその指摘が出たのか」を言語化したもの**です。したがって本書は理想論の網羅リストではなく、**実際に指摘として成立した型のみ**を収録しています。

### 1.2 レビュー対象

| ファイル | レビューでの役割 |
|---|---|
| PBIチケットの概要・受け入れ条件（Notion） | 突き合わせの片側。**成果物と同じ比重で疑う対象**です |
| `src/test/resources/features/{機能名}/rules.md` | 突き合わせのもう片側。ルール・実例の正本です |
| `src/test/resources/features/{機能名}/scenarios.md` | シナリオの検証力・実行可能性を見ます |
| `src/test/resources/features/{機能名}/viewpoints.tsv` | 不足観点の判定に使います |
| `src/test/resources/features/_master/feature-map.html` | 責務の境界の判定に使う正本です |

### 1.3 レビュー対象外

以下は指摘対象に含めません。

| 対象外 | 理由 |
|---|---|
| 非機能要件（性能・負荷・セキュリティ） | CLAUDE.md のスコープ定義により別計画です |
| 外部SDK・バックエンドの内部ロジック | ベンダー・サーバ側の責務です |
| 決定台帳で他チケットの責務と決まっている処理 | 責務の境界はレビューではなく `/feature-map` で決めます |
| iOS版の用語定義との不一致 | 呼称はAndroid版プロダクトの決定を優先します |
| 修正対象外の記述の表記ゆれ・並び順 | 改善提案に留め、指摘としては挙げません |

## 2. レビューの進め方

観点は5層に分かれ、**番号の小さい層から順に実施します**。下の層の指摘は、上の層が決まらないと書けないためです（例：第1層で「入室待ちの起点時刻」が決まらないうちは、第3層の「例の識別力」を判定できません）。

| Step | 実施内容 | 使う層 |
|---|---|---|
| Step 0 | 対象の読み込みと、**機能の性質の宣言**（第5層の前提になります） | — |
| Step 1 | チケット本文と成果物の突き合わせ | 第1層・第2層 |
| Step 2 | 実例・シナリオ1本ずつの精査 | 第3層・第4層 |
| Step 3 | 宣言した性質から引く不足観点の洗い出し | 第5層 |
| Step 4 | レポート統合（優先順・確認先の振り分け） | — |

---

## 3. 第1層：文書内の整合性（BR-A）

**チケット本文（概要・受け入れ条件）と、成果物（ルール・実例／シナリオ）を対にして並べる**ことで出る指摘です。**最大の収穫源**であり、外部レビューの食い違い21件のうち12件がこの層から出ています。

| ID | 観点 | 突き合わせる対象 | 指摘の型 |
|---|---|---|---|
| BR-A1 | 列挙の数の一致 | 受け入れ条件の「N個の状態」 ⇔ ルールの本数 | 「4つの状態」と言いながら、ルールと実例には3つしか無い |
| BR-A2 | 用語・ラベルの一字一句の一致 | 同じUI要素を指す文字列の全出現箇所 | 同じボタンの名前が3種類ある。テストは文字で合否を見るため1文字違うと落ちる |
| BR-A3 | 境界表現の一致 | 「以内／未満」「以上／超」の全出現箇所 | 冒頭は「1時間以内」、ルールは「1時間未満」 |
| BR-A4 | 起点時刻の定義の一致 | 状態が始まる時刻の定義 | 冒頭は「開始時刻から」、ルールは「事前入室可能時間だけ前から」 |
| BR-A5 | カウント対象の定義 | 「何から何まで」を数えているか | 「次の予定まで」が、予約開始までなのか入室待ちに変わる時刻までなのか一意に決まらない |
| BR-A6 | 正反対の記述 | 同じ挙動への「採る／採らない」 | 冒頭に「起動直後は7秒ボタンを隠す」、ルールに「Android版では採らない」 |
| BR-A7 | 受け入れ条件の取りこぼし | 受け入れ条件の各項 ⇔ 対応するルールの有無 | 受け入れ条件にある「ロゴ長押し」「言語切替」がどのルールにも無い |
| BR-A8 | 二重管理の構造 | 冒頭の概要と後半のルールの記述の重なり | BR-A1〜A7 の根本原因。冒頭は概要に留め、細かい挙動は後半へ寄せる |

### 3.1 BR-A の進め方

1. チケット本文から、**状態の列挙・UI文言・数値と境界表現・時刻の定義**を抜き出して一覧にします。
2. 同じ項目を `rules.md` と `scenarios.md` から抜き出し、**左右に並べます**。
3. 一致しない行だけを指摘として起こします。片側にしか無い行も指摘です（BR-A7）。

> 指摘の書き方は「どちらが正しいか」を断定せず、**両方の記述を並べたうえで直し方を1つ提案する**形にします。どちらを採るかは仕様担当の判断です。

## 4. 第2層：前提と責務の整合（BR-B）

成果物の**前提そのもの**が成立しているかを見ます。

| ID | 観点 | チェック内容 | 指摘の型 |
|---|---|---|---|
| BR-B1 | 状態の「正」の所在 | 画面の状態を決めるのは端末かサーバか、1つに決まっているか | ルール①は端末が自分で計算、ルール⑦⑨はサーバ値を表示、と両方書かれている |
| BR-B2 | 背景と個別ルールの両立 | Gherkin の「背景」と矛盾するルールが無いか | 背景は「ホーム画面を表示している」なのに、ルール⑧は「ホームは表示されず設定画面へ移る」 |
| BR-B3 | 他の仕様書との責務の重複 | 同じ判定を別の仕様書・別チケットでもやっていないか | 「設置空間が未設定なら設定画面へ」は起動準備側でも判定している |
| BR-B4 | 設定の有効・無効の組み合わせ | 設定が無効な構成だけで成立する状況が破綻しないか | 自動ステータス更新が無効の端末が1台だけの部屋は、誰も更新せず永遠に空室のままになる読み方ができる |

> **BR-B1 は最優先で片づけます。** ここが決まらないと、状態の算出・反映・復旧に関わるルールの前提がすべて揺れます。

## 5. 第3層：実例・シナリオの検証力（BR-C）

シナリオが**本当に不具合を検出できるか**を1本ずつ見ます。

| ID | 観点 | チェック内容 | 指摘の型 |
|---|---|---|---|
| BR-C1 | 境界の片側欠け | 境界に言及したら「直前・ちょうど・直後」が揃っているか | 「4日後は反映されない」はあるが「3日後23:59は対象」が無い。「00:01」はあるが「00:00」が無い |
| BR-C2 | 例の識別力 | その例は、第1層で見つけた2つの解釈の**どちらでも通ってしまわないか** | 事前入室可能時間が0分の例しか無いため、「次の予定まで」の定義の違いがテストに現れない |
| BR-C3 | 期待値の強さ | 本来あるべき挙動より緩い期待値になっていないか | 日付変更時の期待値が「1分以内に切り替わる」。1秒ごとに計算しているなら「0:00ちょうど」であるべき |
| BR-C4 | トリガー事象の明記 | 「起きない」ことを確認するシナリオに、**起こす操作**が書かれているか | 「揺れ戻らない」としか書かれておらず、揺れ戻りを起こす事象（古い状態が一度届く）が無い |
| BR-C5 | 到達可能性 | その入力値に到達する経路が実在するか | 「猶予秒数が0」の例があるが、設定画面では0の保存が弾かれる |
| BR-C6 | 失敗の定義 | 「失敗したとき」の失敗が具体化されているか | 「自動キャンセルの実行に失敗した後」の失敗が、サーバエラーなのか通信断なのか不明 |
| BR-C7 | シナリオ名の重複・配置 | 同名シナリオが無いか、所属するルールが正しいか | 同名のシナリオがルール③に2本あり、2本目の内容はルール⑦のもの |
| BR-C8 | 実例表とシナリオの双方向対応 | 片方にあって片方に無い行が無いか | シナリオにあって実例表に無い行、実例表にあってシナリオ化されていない行 |

> **BR-C2 が最も効きます。** 第1層で見つけた食い違いを一覧にしたうえで、「その食い違いを現在の例が区別できるか」を1件ずつ確かめます。区別できない場合は、**区別できる例を1行追加する**のが直し方です。

## 6. 第4層：実行可能性（BR-D）

テストレベルに対して、その手順が**実際に実行できるか**を見ます。

| ID | 観点 | チェック内容 | 指摘の型 |
|---|---|---|---|
| BR-D1 | 実行環境で操作できない前提 | `# @TestLevel:` に照らして、その前提を作れるか | E2E（Cloud実機）では端末の時計を操作できないため、固定時刻を前提にしたシナリオは実行不能。相対時刻で書き直す |
| BR-D2 | Setup / Teardown の明記 | テスト中に作ったデータの後片付けが書かれているか | 作成した予約を削除して元の状態へ戻す記述が無い |
| BR-D3 | 合否の判定が観測可能な値か | 何を見て合否を判定するかが一意に決まるか | 「白基調」「オレンジ基調」が、色そのものなのか内部の状態値なのか不明。文言やラベルなど観測可能な値へ置き換える |
| BR-D4 | クレデンシャルの直書き | 環境URL・アカウント・APIキーが直書きされていないか | CLAUDE.md により、プレースホルダーを使います |

## 7. 第5層：網羅性（BR-E）

**ここだけは成果物の突き合わせでは出ません。** 「その機能がどう置かれ、どう使われるか」という性質を先に宣言し、そこから観点を引きます。

### 7.1 先に機能の性質を宣言する

Step 0 で、対象機能に当てはまる性質を次のカタログから選びます。選んだ性質が、そのまま確認すべきテーマになります。

| 性質 | 当てはまる機能の例 | 引かれるテーマ |
|---|---|---|
| 常設（長時間表示したままになる） | ドア前のホーム画面 | BR-E4 通信と時計、BR-E9 長時間稼働 |
| 操作されないまま状態が変わる | 予約状況の表示 | BR-E2 時間切れ、BR-E3 外部からの変更、BR-E8 復旧 |
| 同じ対象に複数の端末が接続される | 1部屋に2台のタブレット | BR-E5 複数端末 |
| 可変長の文字列を限られた幅に表示する | 空間名のヘッダー | BR-E6 可変長表示 |
| 設定で挙動が変わる | 管理メニューの各設定 | BR-E7 設定の反映 |
| 端末内に記録を持つ | 入室状態の復旧 | BR-E8 復旧 |

### 7.2 テーマごとの観点

| ID | テーマ | 確認する場面 |
|---|---|---|
| BR-E1 | 状態の全列挙 | 未記載の状態／各状態の開始と終了の瞬間／**状態同士が重なったときの優先順位** |
| BR-E2 | 時間切れの瞬間 | 期限が来た瞬間／カウントが0になる瞬間／期限を超過したまま放置されたとき |
| BR-E3 | 外部からの変更 | 作成・削除だけでなく**変更・延長・短縮・移動**／進行中のデータが変更されたとき |
| BR-E4 | 通信と時計 | 切断中の表示／復帰後に取り逃した変更の反映／端末時計とサーバ時刻のズレ |
| BR-E5 | 複数端末 | 片側だけ設定が無効／更新の衝突／設置位置などの端末個別設定 |
| BR-E6 | 可変長表示 | 境界の文字数／半角と全角の混在／空文字／画面の向き／他の経路での名称変更 |
| BR-E7 | 設定の反映 | 再起動なしでの反映／設定そのものが存在しない場合／対象が組織側で削除された場合 |
| BR-E8 | 復旧 | 端末内の記録と実データの不一致／復旧**しない**条件の明記 |
| BR-E9 | 長時間稼働 | 24時間以上の連続表示／スリープ復帰後の追従／日付をまたぐ継続 |

> BR-E1 の**優先順位の確認**は定型です。状態を列挙したら、次は必ず「状態同士がぶつかったらどちらを出すか」を聞きます。

## 8. 指摘の書き方

### 8.1 1件あたりの必須項目

| 項目 | 内容 |
|---|---|
| 指摘ID | 第1層・第2層は `1-n`、第5層は `2-n` のように層で分けて採番します |
| 観点ID | 本書のID（BR-A1 等）。**どの観点で見たから出た指摘かを必ず書きます** |
| 食い違いの対 | チケット本文側の記述と、成果物側の記述を**両方そのまま引用**します |
| 直し方 | 具体的な1案を書きます。断定できない場合は選択肢を並べます |
| 確認先 | **仕様担当／実装確認／QA** のいずれか |

### 8.2 確認先の振り分け

| 確認先 | 該当するもの | 扱い |
|---|---|---|
| QA | 成果物側だけで直せるもの（記述の統一、例の追加、シナリオの移動） | 自分で直します |
| 仕様担当 | どちらが正しい仕様かを決める必要があるもの | **赤カード候補**です |
| 実装確認 | 実際の挙動を確かめないと決まらないもの | **赤カード候補**です |

### 8.3 優先順の付け方

件数の多さではなく、**先行関係**で並べます。「これが決まらないと、あれとこれの前提が揺れる」という依存を先頭に置きます。第2層（特に BR-B1）の指摘は、ほぼ常に先頭に来ます。

## 9. 判定ラベル

| ラベル | 意味 | 次のアクション |
|---|---|---|
| 🔴 食い違い | 先に決めないとテストが書けないもの | 決めてから成果物を直します |
| 🟠 不足観点 | 今の成果物に無いが確認したい場面 | 責務を確かめたうえで追加します |
| 🟡 要確認 | 仕様担当・実装への確認が要るもの | 赤カードとして起票します |
| 🟢 問題なし | 基準を満たしているもの | 対応不要です |

## 10. 指摘を起こす前の責務チェック

**不足観点（🟠）は、挙げる前に必ず決定台帳と突き合わせます。** 「画面の表示が変わるから対象」という粗い基準で積むと、他チケットの責務まで抱え込みます。

判定の基準は次のとおりです（決定台帳 #9）。

| 対象 | 責務 |
|---|---|
| **この端末での操作を伴わずに**状態が変わったときの表示 | 表示側の機能（本機能）で見ます |
| **この端末での操作**そのものと、その成否・エラー表示 | 各操作チケットで見ます |

他チケットの責務と判定したものは、指摘から外すのではなく **「申し送り先つきで一覧に残します」**。そうしないと、着手時に誰も拾いません。
