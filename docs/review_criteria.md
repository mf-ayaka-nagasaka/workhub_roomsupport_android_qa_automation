# テストケースレビュー基準書

## 1. レビュー対象

### 対象データ
- Qaseからエクスポートされた既存テストケース（CSV形式）
- 新規作成されたテストケース（CSV形式）

---

## 2. ケース品質チェック（ミクロ分析）

### 2.1 前提条件の完全性
- [ ] テスト実行に必要な初期状態が明記されている
- [ ] ログイン状態、画面遷移先が指定されている
- [ ] テストデータの準備手順が記載されている
- [ ] 他のテストケースへの依存がないか確認

### 2.2 手順の明確性
- [ ] 各ステップが具体的で、実行者によって解釈のブレがない
- [ ] 操作対象（ボタン名、入力フィールド名）が特定されている
- [ ] 操作順序が論理的で、飛躍がない

### 2.3 期待値の検証可能性
- [ ] 期待される結果が具体的に記述されている
- [ ] 「正しく表示される」等の曖昧な表現がないか
- [ ] 確認ポイント（何を見て合否判定するか）が明確

### 2.4 セキュリティ・情報管理
- [ ] 環境URL、テストアカウント情報がハードコードされていないか
- [ ] プレースホルダー（[テスト用管理者アカウント]等）が使用されているか
- [ ] ※ Notion等の社内ドキュメントへの参照リンクはセキュリティ違反ではない

---

## 3. 構造的冗長の検出（マクロ分析）

### 3.1 同一ロジックの反復パターン
- [ ] 同一のアプリケーションロジックを異なるパラメータで繰り返していないか
- [ ] 代表パターンに集約可能なケースが散在していないか

### 3.2 suite帰属の妥当性
- [ ] 各テストケースが所属するsuiteの検証スコープに合致しているか
- [ ] 別suiteに帰属すべきケースが混入していないか

### 3.3 カバレッジの過不足
- [ ] 機能一覧に対する未カバー機能がないか
- [ ] 過剰なケース（同一観点の重複）がないか
- [ ] 「削り（冗長検出）」と「追加（不足検出）」を同等の重みで分析

---

## 4. 断捨離の判断基準

### 削除を提案するケース
1. **完全重複**: 同一の前提条件・手順・期待値を持つケース
2. **論理的重複**: 異なるパラメータだが同一ロジックを検証しており、代表パターンで十分なケース
3. **スコープ超過**: 当該suiteの検証範囲を超えた検証を行っているケース（別suiteでカバー確認済みの場合）

### 削除を提案しないケース
1. **境界値テスト**: パラメータの境界でアプリケーションの挙動が変わるケース
2. **エラーパターン**: 異なるエラー条件を検証するケース
3. **他suiteで未カバー**: 当該suiteでのみ検証されている観点

### 削除提案時の必須確認
- [ ] CSV全体で同観点のケースの有無を調査済みか
- [ ] 「完全削除」か「別suiteへの切り出し」かの判断材料を提示しているか
- [ ] 根拠を示した上で提案しているか（保守的すぎないか）

---

## 5. レビュー実施手順

### Step 1: スコープ定義
対象suiteの検証スコープ（何をどこまで見るか）を明確に定義する

### Step 2: マクロ分析
1. 機能一覧との照合（不足検出）
2. 構造パターンの分析（冗長検出）
3. suite帰属の確認

### Step 3: ミクロ分析
個別ケースの品質チェック（前提条件、手順、期待値）

### Step 4: 改善提案
1. 削除提案（根拠付き）
2. 修正提案（具体的な修正内容）
3. 追加提案（不足観点のケース）
