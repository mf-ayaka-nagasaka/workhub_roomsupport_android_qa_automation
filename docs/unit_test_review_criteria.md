# 単体テストレビュー基準書（QA視点）

| 項目 | 内容 |
|---|---|
| **象限** | 📗 リファレンス |
| **対象者** | QA担当（単体テストのレビュー実施者） |
| **ゴール** | 開発チームが作成した単体テストに対し、Gherkinシナリオとの網羅性とテストコード自体の品質を、一定の基準で漏れなく指摘できるようになります |

本書は **Android アプリの単体テストコード** をQA視点でレビューするためのチェックリストです。手動テストケースのレビュー基準は `review_criteria.md` にあり、本書とは対象が異なります。

---

## 1. 本書の位置づけ

### 1.1 レビュー対象

| 項目 | 内容 |
|---|---|
| 対象リポジトリ | workhubRoomSupport-Android |
| 対象ソース | 各モジュールの `src/test/`（JVM単体テスト） |
| 対象テストレベル | Gherkin中の `# @TestLevel:` が `ApplicationUnit (JVM)` または `PresentationUnit (JVM / Turbine)` のもの |
| 前提スタック | JUnit4 + `kotlin.test` / MockK / kotest matchers / `kotlinx-coroutines-test` / MockWebServer |

### 1.2 レビュー対象外

以下はレビューの指摘対象に含めません。

| 対象外 | 理由 |
|---|---|
| `src/androidTest/`（計装テスト） | 実機上のE2E領域であり、別の基準で扱います |
| `# @TestLevel: E2E (Cloud実機 / Nightly)` のシナリオ | 単体テストの責務外です |
| `ExampleUnitTest.kt` | プロジェクト生成時のテンプレート残骸です |
| 自動生成コード配下のテスト | 生成物の品質はツール側の責務です |
| 外部SDK・バックエンドの内部ロジックを検証するテスト | CLAUDE.md のスコープ定義によりベンダー・サーバ側の責務です（観点 UT-5 で逆に指摘します） |

### 1.3 前提となる開発フロー

開発チームは、QA側が作成した **Gherkinシナリオを元に単体テストを実装** しています。**テストすべき観点はすべてGherkin側に盛り込まれている**ことが前提です。

したがって本書では、**「どの観点をテストすべきか」の網羅性チェックは UT-0（Gherkin突合）に一本化**します。境界値・異常系・状態遷移といった観点の過不足は、テストコードではなくGherkin側の品質問題として扱い、単体テストレビューでは指摘しません。

| ファイル | 役割 |
|---|---|
| `src/test/resources/features/<機能>/scenarios_with_viewpoints.md` | **網羅チェックの唯一の正本。** シナリオ本体・📐観点ブロック・ルール名のすべてを含みます |

同じディレクトリにある `viewpoints.tsv` / `rules.md` / `_master/viewpoints.tsv` は、レビューでは参照しません。観点もルール名も上記ファイルに内包されており、**正本を複数持つと判定がブレる**ためです。

---

## 2. レビューの進め方

次の順序で実施します。**Step 1 を飛ばして Step 2 から始めてはいけません。** 網羅性の欠落は個別ケースの品質より影響が大きく、先に構造を確定させる必要があるためです。

| Step | 内容 | 実施者 |
|---|---|---|
| Step 0 | 対象の特定（変更されたテストが、どのfeature・どのシナリオに対応するか） | AI |
| Step 1 | **Gherkinシナリオとの突合**（網羅性の検証 / UT-0） | AI |
| Step 2 | **ミクロ品質チェック**（テストコード自体の良し悪し / UT-1 〜 UT-6） | AI |
| Step 3 | **レポート草案の提示**（コンソール出力のみ。この時点では投稿しません） | AI |
| Step 4 | **草案の確認・修正・承認** | **QA担当** |
| Step 5 | 承認された内容をPRコメントとして投稿 | QA担当、または承認後のAI |

### 2.1 承認ゲート

**Step 3 と Step 5 の間には、必ずQA担当による承認を挟みます。**

PRコメントは開発チームに見える外向きの成果物です。誤った指摘や、実現不可能な要求をそのまま投稿すると、レビューそのものの信頼を損ないます。**AIが草案を自動で投稿してはいけません。**

---

## 3. Step 1 — Gherkinシナリオとの突合（UT-0）

本書で**最も重要な観点**です。

### 3.1 チェック項目

| ID | チェック内容 | 重み |
|---|---|---|
| UT-0-1 | 対象テストが、どのfeature・どのシナリオに対応するかを特定できる | MUST |
| UT-0-2 | シナリオ本体（`前提` / `もし` / `ならば`）がテストとして実装されている | MUST |
| UT-0-3 | **📐観点ブロックの各バリエーションが漏れなく実装されている** | MUST |
| UT-0-4 | 期待するエラーメッセージの文言が、Gherkin記載と一致している | MUST |
| UT-0-5 | `# @TestLevel:` の指定と、実際のテストの置き場所・粒度が一致している | SHOULD |
| UT-0-6 | **逆方向チェック**: Gherkinに存在しないテストが混入していない | SHOULD |

**UT-0-3 が最も漏れやすい箇所です。** シナリオ本体だけを実装して📐観点ブロックのバリエーションを落とすパターンが典型的なため、観点ブロックは1行ずつ突き合わせてください。

**UT-0-6 で差分が見つかった場合**、「テストが余計」なのか「Gherkin側が古い」のかを切り分けます。後者であればQA側の更新漏れであり、開発チームへの指摘ではなくQAの宿題になります。

### 3.2 テストレベルの判定

Gherkin中の `# @TestLevel:` コメントで対象かどうかが決まります。

| Gherkin記載 | 単体テストレビュー |
|---|---|
| `ApplicationUnit (JVM)` | ✅ 対象 |
| `PresentationUnit (JVM / Turbine)` | ✅ 対象 |
| `E2E (Cloud実機 / Nightly)` | ❌ 対象外 |

### 3.3 観点の仕分け（A / B / C 分類）

📐観点の中には、**JVM単体テストでは原理的に検証できないもの**が含まれています。これを機械的に「漏れている」と指摘すると、開発チームに実現不可能な対応を求めることになります。各観点を次の3つに仕分けてから指摘の要否を判断してください。

| 分類 | 定義 | 例 | 扱い |
|---|---|---|---|
| **A** | 単体テストで検証可能 | 「大文字小文字を間違えた場合にエラーになる」「2組織なら組織選択画面へ遷移する」「文言が他のエラーと区別可能な一意の値である」 | **MUST。** 実装が無ければ指摘します |
| **B** | 単体では検証不可（UI描画・OS設定に依存） | 「エラーメッセージが画面の適切な位置に表示される」「長文が正しく折り返される」「多言語設定時に設定言語で表示される」 | **指摘しません。** 手動テスト・E2Eでカバーすべき観点として、レポートに申し送り欄を設けて列挙します |
| **C** | 単体では検証困難（外部環境・複数端末に依存） | 「別端末から同じアカウントでログインを試行する」「VPNが切断される」 | **SHOULD。** テストダブルで代替可能かを検討し、可能であれば提案します |

### 3.4 手動テストとの役割分担

A / B / C の仕分け結果は、そのまま**手動テストケースとの役割分担**の判断材料になります。

| 分類 | 手動テストケースでの扱い |
|---|---|
| **A**（単体で担保済み） | 手動ケースから**削減できる候補**として記録します |
| **B**（単体では検証不可） | 手動ケースとして**残す必要があります**。レポートの申し送り欄に列挙します |
| **C**（単体では検証困難） | 代替できなければ手動ケースとして残します |

この記録は独立した観点としては設けず、UT-0 の成果物として扱います。実際の手動ケースへの反映は、別途トレーサビリティ整備の工程で行います。

## 4. Step 2 — ミクロ品質チェック（UT-1 〜 UT-6）

Step 1 で網羅性を確認したうえで、**テストコードとしての作りの良し悪し**を精査します。

「どの観点をテストすべきか」は UT-0 で確認済みのため、ここでは扱いません。本章で見るのは、**同じ観点をテストするとして、そのテストコードが信頼できる作りになっているか**です。

### 4.1 UT-1 独立性・再現性

- [ ] 現在時刻に直接依存していない（`Clock` 等が注入されている）
- [ ] テストの実行順序に依存していない
- [ ] 共有状態（シングルトン・静的フィールド）がテスト間で汚染されない
- [ ] コルーチンのテストで `runTest` が使われている
- [ ] Dispatcher の選択が適切（順序を検証したい箇所で `UnconfinedTestDispatcher` に頼っていない）
- [ ] ViewModel のテストで `MainDispatcherRule` の適用漏れがない
- [ ] ランダム値・UUID に依存していない（必要なら固定値を注入）

> `UnconfinedTestDispatcher` は処理を即時実行するため、本来検証すべき非同期の順序性が隠れることがあります。順序や中間状態を検証するテストでは `StandardTestDispatcher` が適切です。

### 4.2 UT-2 アサーションの質

- [ ] `assertNotNull` や「例外が出ないこと」だけで終わっていない
- [ ] 期待値が具体的で、何を合否判定しているかが読み取れる
- [ ] 1つのテストが1つの観点だけを検証している
- [ ] アサーションライブラリが統一されている（`kotlin.test` / kotest / `org.junit.Assert` の混在）

> 本リポジトリでは `kotlin.test.assertEquals` と kotest の `shouldBe`、JUnit4 の `Assert` が混在しています。失敗時のメッセージの読みやすさに差が出るため、ファイル内での統一を推奨します。

### 4.3 UT-3 テストダブルの妥当性

- [ ] `mockk(relaxed = true)` の濫用により、検証が実質無効化されていない
- [ ] `verify` / `coVerify` が過剰でなく、実装の詳細に結合していない
- [ ] 検証すべき対象（状態 or 振る舞い）に応じた検証方法が選ばれている
- [ ] モックすべきでないもの（検証対象そのもの、値オブジェクト）をモックしていない

> `coVerify` で呼び出し回数や引数を細かく固定しすぎると、リファクタリングのたびにテストが壊れます。外部との契約として重要な呼び出しに絞ります。

### 4.4 UT-4 可読性・命名

- [ ] Arrange / Act / Assert（または Given-When-Then）の構造が読み取れる
- [ ] テスト名から検証内容と期待結果が読み取れる
- [ ] マジックナンバーに意味のある名前が付いている
- [ ] テスト対象と無関係なセットアップで見通しが悪くなっていない

### 4.5 UT-5 スコープ適合

CLAUDE.md のスコープ定義に反するテストが無いかを確認します。Gherkinには現れず、テストコードを読んで初めて分かる問題です。

- [ ] 外部SDK（顔認証・BitLock・Firebase・Datadog）の**内部ロジック自体**を検証していない
- [ ] バックエンドの**処理の正当性**を検証していない
- [ ] 検証の範囲が「アプリがSDK・APIの結果を正しくハンドリングできているか」に留まっている
- [ ] 性能・負荷・セキュリティの検証が紛れ込んでいない（別計画の対象です）

### 4.6 UT-6 `@Qase` の形式

`@Qase` 追記後、またはすでに付与されているテストに対して確認します。

- [ ] `id` / `title` / `level` が記載されている
- [ ] `id` が他のテストと重複していない
- [ ] `title` がGherkinのシナリオ名と対応している
- [ ] `level` がGherkinの `# @TestLevel:` と整合している
- [ ] `description` に feature・ルール・観点の参照が記載されている
- [ ] `steps` の `action` が Arrange + Act、`expected` が Assert に対応している

## 5. 指摘の重み付けと完了条件

### 5.1 重み付け

| 重み | 定義 | 例 |
|---|---|---|
| **MUST** | 修正されないとテストの価値が成立しない | Gherkinの観点が未実装（UT-0-3）、期待値が検証されていない（UT-2）、スコープ違反（UT-5） |
| **SHOULD** | 修正が望ましいが、ブロッカーではない | テストレベルの不一致（UT-0-5）、モックの過剰検証（UT-3）、アサーションライブラリの混在（UT-2） |
| **NICE** | 改善提案にとどめる | 命名・可読性（UT-4）、構造の整理 |

### 5.2 レビューの完了条件

**QA担当が承認したMUST指摘を、PRコメントとして投稿した時点で、QAのレビューは完了**とします。

指摘が修正されたかどうかの追跡、修正チケットの起票は本フローの責務に含みません。開発チームの判断に委ねます。

---

## 6. レポートの様式

レポートは**開発者にとっての重要度順**に並べます。読み始めてすぐ「指摘があるのか無いのか」が分かる構成にしてください。

冒頭には必ず**判定ヘッドライン**を置きます（例: `🔴 要対応: MUST 2件・SHOULD 1件` / 指摘が無ければ `✅ 指摘なし`）。

| 順 | 要素 | 内容 |
|---|---|---|
| **①** | **サマリー** | MUST / SHOULD / NICE / 申し送りの件数 |
| **②** | **指摘一覧** | 観点ID・重み・該当箇所・指摘内容・修正方針。MUST から順に並べます |
| **③** | **シナリオ網羅表** | シナリオ・📐観点ごとに、対応テストの有無とA/B/C分類を並べた表。②の根拠です |
| **④** | **手動テストへの申し送り** | B分類（単体では検証不可）として除外した観点の一覧 |
| **⑤** | **QA側の宿題** | Gherkin側が古い等、QAが対応すべき事項（該当時のみ） |
| **⑥** | **対象と範囲** | レビュー対象のファイル、対応するfeature・シナリオ、除外したもの |

**④と⑤には「※開発側の対応は不要です」を明記します。** 開発者が読み飛ばせるようにするためです。

### 網羅表の形式

| シナリオ / 観点 | 分類 | 対応テスト | 判定 |
|---|---|---|---|
| 単一組織のアカウントで…ログインが完了する | A | `LoginViewModelTest#...` | ✅ |
| └ 📐認証成功: 初回ログインである | A | `LoginViewModelTest#...` | ✅ |
| └ 📐認証成功: 過去にログイン済みである | A | — | ❌ 未実装 |
| └ 📐エラーメッセージの適切性: 表示位置 | B | — | ⏭️ 手動へ申し送り |

### 投稿前の確認

**レポートは草案として提示し、QA担当の承認を得てから投稿します（`§2.1`）。** AIが草案を自動で投稿してはいけません。

### セキュリティ上の注意

レポートに環境URL・テストアカウント・APIキーを転記しないでください。テストコード中にそれらがハードコードされていた場合は、**値そのものを引用せず**「ハードコードされている」という事実のみを指摘します。
