# Skill: qa-case-exporter
デシジョンテーブル（md）を読み取り、QASEインポート用のCSVファイルを生成します。

## Usage
`/qa-case-exporter [チケットNo（例：QA-123）]`

## Context / Scope
- **参照元**: `docs/test_viewpoints/release/{TicketNo}/{AppVer}_{TicketNo}_matrix.html`
- **テンプレート**: `CSVテンプレート_QASE_workhubMobile用 - template_確認テスト (1).csv`
- **出力先**: `docs/test_viewpoints/release/{TicketNo}/{AppVer}_{TicketNo}_cases.csv`
- **事前準備マスター**: ./data/preconditions_master.md

## Instructions

### 1. 事前準備の解決とデータマッピング
- 指定された `_matrix.html` から各テストケースを抽出し、操作内容を特定します。
- まず `./data/preconditions_master.md`（事前準備マスター）を参照し、該当する操作の「事前準備」が存在するか確認してください。
  - **該当あり**: マスターに記載されている事前準備の内容を採用します。
  - **該当なし**: マッピングを一旦保留し、ユーザーに「以下の操作に関する事前準備を入力してください（不要な場合は『なし』と回答）」と質問して回答を待ちます。回答を得たら、その内容を自動的に `./data/preconditions_master.md` に追記してマスターファイルを更新（蓄積）してください。
  - **【重要: 追記フォーマット】** 更新時は必ず「## [カテゴリ系]」「- **対象操作**: ...」「- **事前準備**: ...」のMarkdownリスト構造を厳守して追記してください。適切なカテゴリ（H2）がない場合はカテゴリごと新規作成してください。
    ```markdown
    ## [カテゴリ系]
    - **対象操作**: [操作名]
    - **事前準備**: 
      - [ユーザーが入力した事前準備1]
      - [ユーザーが入力した事前準備2]
    ```
- すべての事前準備が解決したら、テンプレートのカラムに以下のルールでマッピングしてください：
  - `title`: `【WA-{TicketNo}】` + 観点の要約
  - `parameters`: そのケースで選択されている「因子:水準」のリスト
  - `steps_actions`: 操作手順（マトリクスの条件組み合わせ）
  - `steps_result`: 期待値（マトリクスの期待値項目）
  - `preconditions`: 上記で解決（またはユーザー入力）した事前準備
  - `suite`: 「CSVテスト親」等のデフォルト値、またはAppVerに基づくフォルダ名
  - `priority`, `severity`, `cf_6`: 下記「テストケースの優先度・重要度定義ルール」に従って出力してください。
  - その他のカラム（type等）はテンプレートのデフォルト値を継承してください。

#### テストケースの優先度・重要度定義ルール

テストケース生成時、`priority` (または `priority.1`) および `severity` (または `severity.1`) の列には、以下の定義と判定ロジックに従って、指定された文字列（必ずすべて半角小文字）のみを出力してください。

##### 1. severity（不具合重要度）の選択肢と判定基準
テストケースが失敗（不具合流出）した場合の、サービス・ビジネスへの影響度で判定します。

* **`emergency`**: 【Emergency (項目重要度A)】事業継続を脅かす最悪レベルの障害。
* **`critical`**: 【Critical (項目重要度B)】物理的なカギの開閉・出入りができない、安全性が欠如する、またはシステムが完全停止する事象。
* **`major`**: 【Major (項目重要度C)】カギ体験自体は阻害されないが、利用者に強い不安や誤解を与え、かつユーザー側で実施できる回避策がない不具合。
* **`normal`**: 【Normal (項目重要度D)】不具合が発生しても、アプリ再起動や別画面からの操作などの回避策（Workaround）が存在する事象。
* **`minor`**: 【Minor (項目重要度E)】上記以外の軽微な表示崩れ、誤字脱字、モヤっとするレベルの改善点。

##### 2. priority（リグレッション優先度）の選択肢と判定基準
上記で判定した `severity` に基づき、リグレッションテストに含めるべきかどうかの優先度を決定します。

* **`high`**: リグレッションテスト必須・最重要 (P1相当)
  * **マッピング条件**: `severity` が `emergency` または `critical` の場合
  * **扱い**: 正常系・異常系問わず確実に実行するケース（将来のスモークテスト対象）。
* **`medium`**: リグレッションテスト対象 (P2相当)
  * **マッピング条件**: `severity` が `major` の場合
  * **扱い**: 主に主要な正常系シナリオを中心に維持するケース。
* **`low`**: リグレッションテスト除外・確認テストのみ (P3相当)
  * **マッピング条件**: `severity` が `normal` または `minor` の場合
  * **扱い**: 全体のリグレッションテストからは除外（機能修正時の確認テストのみで担保）。

##### 3. cf_6（社内表示用重要度）の出力ルール
* `severity` の判定結果に対応する文字列を出力してください:
  * `emergency` ➔ `Emergency (項目重要度A)`
  * `critical` ➔ `Critical (項目重要度B)`
  * `major` ➔ `Major (項目重要度C)`
  * `normal` ➔ `Normal (項目重要度D)`
  * `minor` ➔ `Minor (項目重要度E)`

### 2. プレビューと編集（重要）
- CSVを書き出す前に、生成されるデータのプレビューをMarkdownの表形式で提示してください。
- ユーザーに「手順をもう少し詳しくして」「この項目のタイトルを変えて」などの手直し要望がないか確認してください。
- 修正指示があれば、データを更新して再提示してください。

### 3. CSVファイルの生成
- ユーザーの合意（「OK」「書き出して」等）を得たら、CSVファイルを生成してください。
- **重要**: カラムの順番やヘッダー名は、提供されたテンプレートと一文字一句違わぬよう厳守すること。
- 文字コードは、Excelでの文字化けを防ぐため「UTF-8 (BOM付き)」または「Shift-JIS」を選択できるようにしてください（デフォルトはUTF-8とします）。

### 4. バージョン管理（Git Operations）
- ファイル保存後、以下の操作を自動（または提案）してください。
  - `git add` および `git commit -m "qa: update test cases for v{AppVer} ({TicketNo})"`
  - `git tag -af v{AppVer} -m "Latest QA artifacts for version {AppVer}"`
  - 既存のタグがある場合でも `-f` (force) オプションで強制更新し、常に最新コミットを指すようにします。

## Constraints
- カラムのズレはインポートエラーの原因になるため、空の列（Unnamed等）も含めてテンプレートを完全再現すること。
- 生成完了後、ファイルパスを明示すること。
- ユーザーの確認なしにファイルを保存しないこと。

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md` および `.claude/memories/qa-case-exporter.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

2. **成果物の再生成に伴う自動蓄積（トリガールール）**:
   - ユーザーの指摘や修正指示によって、一度生成した成果物を作り直す場合、それは「初期出力に考慮漏れやルールの不一致があった」ことを意味します。
   - 成果物を再生成する**前に**、自律的に `.claude/memories/qa-case-exporter.md` へ物理的にファイル編集を行って追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象タスク**: （例: 影響範囲の抽出、テスト観点作成など）
     - **対象機能**: （例: ログイン画面、決済APIなど）
     - **指摘カテゴリ**: （例: 網羅性の不足、仕様の誤認識、具体性の不足、フォーマット違反 など）
     - **指摘された内容**: （例: 重点確認ケースに「ログイン周り」が抜けている）
     - **原因/理由**: （例: 依存関係の読み込みが甘かったため）
     - **今後の対策**: （例: 認証が絡む変更の際は必ずログインケースを強制抽出する）

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、成果物の再生成も終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、成果物を作り直しました」と必ず報告してください。
