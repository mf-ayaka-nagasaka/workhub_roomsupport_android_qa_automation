# Skill: review-bdd-artifacts
作成済みのBDDテスト設計成果物を、外部レビューに出す前に**セルフレビュー**します。チケット本文と成果物の食い違い・シナリオの検証力・実行可能性・不足観点を基準書の観点に沿って洗い出し、対応方針つきの指摘レポートを出力します。成果物の修正そのものは行わず、`/bdd-artifact-updater` へ引き渡します。

## Usage
`/review-bdd-artifacts [対象機能名]`

例: `/review-bdd-artifacts Home`
例: `/review-bdd-artifacts Login`

## Context / Scope
- **判定基準（最優先参照）**: `docs/bdd_review_criteria.md`
- **レビュー対象**:
  - 対象チケットの概要・受け入れ条件（Notion。MCPで取得するか、ユーザーから貼り付けてもらう）
  - `src/test/resources/features/{機能名}/rules.md`
  - `src/test/resources/features/{機能名}/scenarios.md`
  - `src/test/resources/features/{機能名}/viewpoints.tsv`
- **責務の正本**: `src/test/resources/features/_master/feature-map.html`（決定台帳）
- **補助入力**: `C:\Users\mforce0087\workhubRoomSupport` 配下の対象機能仕様書（.md）※裏取りに使用
- **関連メモリー**: `.claude/memories/review-bdd-artifacts.md`、`.claude/memories/global.md`、`.claude/memories/bdd-artifact-updater.md`
- **スキル一覧**: `.claude/commands/README.md`

## Instructions
あなたはAndroidアプリのシニアQAエンジニアとして、BDDテスト設計成果物のレビューを行ってください。
【最重要ルール】：本スキルは**読み取り専用**です。成果物ファイルを一切編集しないでください。修正は `/bdd-artifact-updater` の責務です。
【最重要ルール】：一度にすべての工程を実行しないでください。各Stepの結果を提示し、ユーザーの合意を得てから次のStepへ進んでください。

### Step 0: 対象の読み込みと機能の性質の宣言

1. `docs/bdd_review_criteria.md` を読み込む。
2. `.claude/memories/review-bdd-artifacts.md` と `.claude/memories/global.md` を読み込み、過去の指摘を最優先ルールとして適用する。
3. `src/test/resources/features/{機能名}/` 配下の成果物をすべて読み込む。成果物が存在しない場合は「本スキルは作成済み成果物のレビュー用です。`/bdd-workflow-manager {機能名}` を先に実行してください」と案内して停止する。
4. 決定台帳を読み、対象チケットに関係する既存の決定・赤カードを把握する。
5. **チケット本文（概要・受け入れ条件）を入手する。** 入手できない場合は、ユーザーに貼り付けを依頼して待つ。**チケット本文が無いまま Step 1 へ進んではいけない。** 第1層の観点（BR-A）はチケット本文との突き合わせでしか出ないため、欠けると収穫の過半を失う。
6. 基準書 7.1 の性質カタログから、対象機能に当てはまる性質を選び、以下の形式で提示する。

```
## レビュー対象の確認

### 対象機能: {機能名}
| 入力 | 状態 |
|---|---|
| チケット本文（概要・受け入れ条件） | 取得済み / 未取得 |
| rules.md | ルール{n}本・実例{n}行 |
| scenarios.md | シナリオ{n}本 |
| viewpoints.tsv | 観点{n}件 |

### この機能の性質（第5層の前提）
| 性質 | 該当 | 引かれるテーマ |
|---|---|---|
| 常設（長時間表示したままになる） | ✅ / — | BR-E4 通信と時計 / BR-E9 長時間稼働 |
| ...（カタログの全行を列挙） | | |
```

7. **【次Step移行確認】** 「この性質の選び方で合っていますか？Step 1（整合性レビュー）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 1: 整合性レビュー（第1層・第2層）

1. チケット本文から **状態の列挙・UI文言・数値と境界表現・時刻の定義** を抜き出して一覧化する。
2. 同じ項目を `rules.md` / `scenarios.md` から抜き出し、**左右に並べて**突き合わせる。
3. BR-A1〜A8、BR-B1〜B4 の各観点で判定し、一致しない行・片側にしか無い行を指摘として起こす。
4. 以下の形式で提示する。

```
## 第1層・第2層の指摘

| # | 観点ID | 指摘 | チケット本文側 | 成果物側 | 直し方 | 確認先 |
|---|-------|------|--------------|---------|-------|-------|
| 1-1 | BR-A1 | 「4つの状態」と言っているがルールは3つ | （原文を引用） | （原文を引用） | （1案） | 仕様担当 |
```

5. **断定しないこと。** どちらが正しい仕様かはユーザー・仕様担当の判断であり、レビューは両方を並べて直し方を提案するに留める。
6. **【次Step移行確認】** 「Step 2（シナリオ精査）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 2: シナリオ精査（第3層・第4層）

1. Step 1 で見つけた食い違いの一覧を手元に置き、**「その食い違いを現在の例が区別できるか」を1件ずつ確かめる**（BR-C2）。区別できない場合は、区別できる例を1行追加する提案を書く。
2. シナリオを1本ずつ BR-C1〜C8、BR-D1〜D4 で判定する。
3. `# @TestLevel:` を読み、その階層で実行可能かを必ず確認する（BR-D1）。E2E（Cloud実機）では端末の時計・システム時刻を操作できない前提で判定する。
4. Step 1 と同じ表形式で提示する。
5. **【次Step移行確認】** 「Step 3（不足観点の洗い出し）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 3: 不足観点の洗い出し（第5層）

1. Step 0 で宣言した性質に対応するテーマ（BR-E1〜E9）だけを使い、確認したい場面を洗い出す。**宣言していない性質のテーマからは引かない。**
2. 洗い出した各項目について、**挙げる前に決定台帳と突き合わせる**（基準書 10章）。
   - この端末での操作を伴わずに状態が変わったときの表示 → 本機能の責務
   - この端末での操作そのものと、その成否・エラー表示 → 各操作チケットの責務
3. 既存の `viewpoints.tsv` / `scenarios.md` に**すでに含まれていないか**を必ず確認する。含まれている場合は挙げない。
4. 以下の形式で提示する。

```
## 第5層の指摘（不足観点）

### 本機能の責務に含まれるもの
| # | 観点ID | 確認したい場面 | 既存成果物での扱い | 確認先 |
|---|-------|--------------|-----------------|-------|
| 2-1 | BR-E2 | 残り時間が00:00になった瞬間の表示 | シナリオは00:01まで | 仕様担当 |

### 他チケットの責務と判定したもの（申し送り）
| # | 確認したい場面 | 申し送り先 | 根拠（台帳の論点） |
|---|--------------|----------|-----------------|
| 1 | 利用不可時間中の表示 | ⑩ 利用不可・利用時間外 | #5 |
```

5. **【次Step移行確認】** 「Step 4（レポート統合）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 4: レポート統合

1. Step 1〜3 の指摘を統合し、以下の形式で出力する。

```
【BDD成果物 セルフレビュー結果】
対象機能: {機能名}
レビュー日: {YYYY-MM-DD}
判定基準: docs/bdd_review_criteria.md

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ サマリー
| 区分 | 件数 |
|---|---|
| 🔴 食い違い（先に決めないと書けない） | {n}件 |
| 🟠 不足観点 | {n}件 |
| 🟡 要確認（赤カード候補） | {n}件 |
| 申し送り（他チケットの責務） | {n}件 |

■ まず直すもの（先行関係順）
1. {指摘ID} — {一行要約}（これが決まらないと {影響範囲} の前提が揺れます）
...

■ 1. 食い違い（第1層・第2層）
（Step 1 の表）

■ 2. シナリオの検証力・実行可能性（第3層・第4層）
（Step 2 の表）

■ 3. 不足観点（第5層）
（Step 3 の表）

■ 4. 確認先の内訳
| 確認先 | 件数 | 指摘ID |
|---|---|---|
| QA（自分で直せる） | {n} | {id, id} |
| 仕様担当 | {n} | {id, id} |
| 実装確認 | {n} | {id, id} |

■ 5. このレビューで確認できなかったこと
（ソース・仕様書が手元に無く判定できなかった点を列挙）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

2. **「まず直すもの」は件数の多さではなく先行関係で並べる。** 第2層（特に BR-B1：状態の正の所在）の指摘は、ほぼ常に先頭に来る。
3. レポートの最後に以下を出力して停止する。

> 上記の指摘について、**対応する／対応しない** の分類を行いますか？
> - **はい**: 分類表を作成し、対応するものを `/bdd-artifact-updater {機能名}` へ引き渡します
> - **一部のみ**: 対応する指摘IDを指定してください
> - **いいえ**: レポート出力のみで終了します

### Step 5: 対応方針の確定と引き渡し

1. ユーザーの合意を得た指摘について、以下の分類表を作成する。

```
## 対応方針

| # | 指摘 | 判定 | 理由 |
|---|------|------|------|
| 1-1 | 〜 | 対応する / 対応しない | （対応しない場合は**文章で**理由を書く。台帳の参照番号だけで済ませない） |
```

2. 「対応する」と判定した指摘を修正要求の形に整形し、`/bdd-artifact-updater {機能名} {修正内容}` へ引き渡す。
3. 「仕様担当」「実装確認」と振り分けた指摘は、**赤カードの起票候補**として一覧に残す。
4. 申し送りに分類した項目は、**申し送り先のチケット名つきで一覧に残す**。指摘から消さない。

## Constraints (制約事項)
- **読み取り専用（最重要）**: 本スキルは成果物・台帳・仕様書を一切編集しないこと。修正は `/bdd-artifact-updater`、台帳の更新は `/feature-map` の責務。
- **進行制御**: ユーザーの明確な合意なしに次のStepへ進まないこと。
- **チケット本文を必須入力とする**: チケット本文が手元に無い状態で第1層のレビューを「指摘なし」と報告しないこと。入手できない場合は、その旨を明記して第1層を未実施として扱う。
- **断定の禁止**: どちらが正しい仕様かをレビュー側で決めないこと。両方の記述を並べ、直し方を提案するに留める。
- **責務の先行確認**: 不足観点を挙げる前に必ず決定台帳と突き合わせ、他チケットの責務と判定したものは申し送りへ振り分けること。「画面の表示が変わるから対象」という粗い基準で積まないこと。
- **既存成果物との重複確認**: 不足観点として挙げる前に、既存の `scenarios.md` / `viewpoints.tsv` に含まれていないかを必ず確認すること。
- **スコープ外を指摘しない**: 非機能要件（性能・負荷・セキュリティ）、外部SDK・バックエンドの内部ロジックは CLAUDE.md のスコープ定義により指摘対象外。
- **表記ゆれは提案に留める**: 修正対象外の記述の言い換え・並び順の変更は指摘として挙げず、改善提案として別枠に記載すること。
- **参照元がiOSであること**: 仕様書・ソースはiOS版。呼称はAndroid版プロダクトの決定を優先し、iOS版の用語定義との不一致を指摘にしないこと。
- **判定基準の参照**: 実行時には必ず `docs/bdd_review_criteria.md` を読み込み、最新の観点に従うこと。観点IDを指摘に必ず付与すること。

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md` および `.claude/memories/review-bdd-artifacts.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

2. **成果物の再生成に伴う自動蓄積（トリガールール）**:
   - ユーザーの指摘や修正指示によって、一度出力したレビュー結果を作り直す場合、それは「観点の適用漏れ・責務の誤判定があった」ことを意味します。
   - レビュー結果を再作成する**前に**、自律的に `.claude/memories/review-bdd-artifacts.md` へ物理的にファイル編集を行って追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ```
     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象タスク**: （例: 整合性レビュー、シナリオ精査、不足観点の洗い出し、責務の振り分け など）
     - **対象機能**: {引数で受け取った対象機能名}
     - **指摘カテゴリ**: （例: 観点の適用漏れ、責務の誤判定、既存成果物との重複の見落とし、断定の禁止違反 など）
     - **指摘された内容**: （ユーザーからの具体的な修正指示）
     - **原因/理由**: （なぜその問題が発生したかの分析）
     - **今後の対策**: （次回実行時に守るべきルールの言語化）
     ```

   - **③ 観点そのものに不足があった場合**: 既存の観点IDのどれでも拾えない指摘がユーザーから出た場合は、メモリーへの追記に加えて **`docs/bdd_review_criteria.md` への観点追加をユーザーに提案**してください（基準書の更新は承認を得てから行います）。

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、レビュー結果の作り直しも終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、レビュー結果を作り直しました」と必ず報告してください。
