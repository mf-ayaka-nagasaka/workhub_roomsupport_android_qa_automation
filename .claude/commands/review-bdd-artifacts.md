# Skill: review-bdd-artifacts
作成済みのBDDテスト設計成果物を、外部レビューに出す前に**セルフレビュー**します。チケット本文と成果物の食い違い・シナリオの検証力・実行可能性・不足観点を基準書の観点に沿って洗い出し、対応方針つきの指摘レポートを出力します。成果物の修正そのものは行わず、`/bdd-artifact-updater` へ引き渡します。

## Usage
`/review-bdd-artifacts <対象機能名> [チケットURL]`

例: `/review-bdd-artifacts Home`
例: `/review-bdd-artifacts Login https://www.notion.so/xxxx`

- `<対象機能名>` は必須。省略された場合は「対象機能名を指定してください」と聞いて待つ（推測で選ばない）。
- `[チケットURL]` は任意。省略時の入手順序は Step 0 を参照。

## Instructions
あなたはAndroidアプリのシニアQAエンジニアとして、BDDテスト設計成果物のレビューを行ってください。

【最重要ルール：編集禁止の範囲】
- **編集禁止**: 成果物（`features/{機能名}/` 配下）・決定台帳・仕様書・基準書・本スキルの定義ファイル。修正は `/bdd-artifact-updater`、台帳の更新は `/feature-map` の責務。基準書は「追加提案」まで（更新はユーザー承認後に別途行う）。
- **書き込み可（例外）**: `.claude/memories/review-bdd-artifacts.md`（自己学習ノート）と `reviews/{機能名}/`（レビュー記録）の2か所のみ。
- 「読み取り専用」という言い方はこの2か所の例外を含めて理解すること。

【最重要ルール：進行制御】
- 原則、各Stepの結果を提示し、ユーザーの合意を得てから次のStepへ進む（合意ゲート）。
- **短縮モード**: ユーザーが冒頭で「ゲート無しで最後まで」「一気に進めて」と明示した場合のみ、Step 0 の確認を取った後、Step 1〜3 をまとめて1回で提示し、合意1回で Step 4 へ進む。Step 4 → Step 5 の確認（対応する／しないの分類）は短縮モードでも省略しない。
- 明示がない場合は短縮モードにしない。「急いでいる」程度の発言は明示とみなさない。
- 短縮モードで Step 4 のセルフチェックが通らず「該当Stepへ戻る」場合、戻る先は「まとめて提示した Step 1〜3 の該当する表」であり、直した表だけを再提示して合意を1回取り直す。Step 0 からやり直さない。

### 指摘の共通ルール（Step 1〜3 で使う）

**レビュー回（回）**: `reviews/{機能名}/` にある `R*_review.md` の最大番号 +1（初回は 1）。同じ機能の2回目以降のレビューでも ID が重複しないよう、ID とファイル名の両方に付ける。

**指摘ID**: `R{回}-{Step番号}-{連番}`。Step 1 は `R{回}-1-1, R{回}-1-2…`、Step 2 は `R{回}-2-1…`、Step 3 は `R{回}-3-1…`。申し送りは `R{回}-3-M1, R{回}-3-M2…`。Step をまたいで振り直さない。前回の指摘を参照するときは前回の ID（`R{前回}-…`）をそのまま使う。

> **IDの位置づけ**: IDは**レポートの中で同じ指摘を指し直すため**（「まず直すもの」の並び・前回との差分表・対応方針表）の番号であり、**ユーザーにIDでの指定を求めない**。ユーザーが「なりすましの件」「E2Eで時計を触るやつ」のように自然な言い方で指した場合は、スキル側がIDへ対応づけて「◯◯の件（R{回}-2-3）ですね」と確認してから進める。対応づけに迷う場合のみ、候補を2〜3件挙げて聞く。

**重さ**（申し送り表を除く各表の「重さ」列に、1指摘につき1つだけ記入する）:
| 重さ | 定義 |
|---|---|
| 🔴 食い違い | チケット本文と成果物が矛盾している。どちらかに決めないと成果物が書けない |
| 🟠 不足・不備 | 矛盾はないが、必要な例・観点・実行条件が成果物に無い。または成果物側だけで直せる不備（シナリオ同士の矛盾、E2Eで時計操作が必要、TestLevel 欠落など。確認先は多くの場合 QA） |
| 🟡 要確認 | 🔴🟠 のどちらにも当たらず、仕様担当か実装確認に聞かないと指摘として成立するか判定できないもの |

**赤カード候補**は重さとは別の軸で、「確認先」列から機械的に決まる（確認先が仕様担当・実装確認なら候補。重さは問わない）。サマリーでは 🟡 の件数と赤カード候補の件数を別の行で数える。

**申し送り**（他チケットの責務と判定したもの）には重さ・確認先を付けない。本レビューでは判定しないため。

**確認先**（3種から選ぶ。これ以外を書かない）:
| 確認先 | 意味 |
|---|---|
| QA | QAが自分で直せる（成果物側の修正で済む） |
| 仕様担当 | 仕様をどちらかに決めてもらう必要がある |
| 実装確認 | 実装の実際の挙動を確認しないと判定できない |

**0件のときの書き方**: 指摘が0件の層は、表を省略せず「指摘なし」と書き、**何と何を突き合わせたか**を件数つきで残す。例: 「第1層：指摘なし。チケット本文の状態4件・UI文言12件・数値3件を rules.md と突き合わせた」。何を見たか書かれていない「指摘なし」は「見ていない」と区別できないため認めない。

**例示の置き字**: 本スキル内の表の例は書式を示すためのものであり、値はすべて置き字（`{…}`）である。例の値をそのまま出力に写さない。

### Step 0: 対象の読み込みと機能の性質の宣言

1. `docs/bdd_review_criteria.md` を読み込む（欠落時のふるまいは 3 の入力チェック表に従う）。
2. メモリーを読み込む（手順は末尾「自己学習および指摘の蓄積ルール」の 1 を参照。ここでは重複して書かない）。
3. 入力チェックを行い、以下の表で結果を提示する。欠落時のふるまいは表の右列に従う。

| 入力 | 必須 | 欠落時のふるまい |
|---|---|---|
| 基準書 `docs/bdd_review_criteria.md` | 必須 | 無ければ停止して所在を聞く（最優先参照のため、無いまま進まない） |
| `features/{機能名}/` フォルダ | 必須 | 「本スキルは作成済み成果物のレビュー用です。`/bdd-workflow-manager {機能名}` を先に実行してください」と案内して停止 |
| 機能名の大文字小文字がフォルダ名と不一致（例: home / Home） | — | 一致候補を提示して確認する。推測で選ばない |
| rules.md | 必須 | 無い・空なら停止して案内（上と同じ） |
| scenarios.md | 必須 | 無い・空なら停止して案内（上と同じ） |
| viewpoints.tsv | 任意 | 「欠落」と明記し、Step 3 の重複確認は scenarios.md のみで行う |
| チケット本文 | 必須 | 下記 4 の手順で入手。原則、入手できるまで待つ |
| 決定台帳 | 必須 | 無ければ停止して所在を聞く |
| 仕様書フォルダ | 任意 | 不在なら裏取り未実施として「確認できなかったこと」へ記載 |
| メモリーファイル | 任意 | 無ければ雛形を作成してから開始（雛形の内容は末尾「自己学習および指摘の蓄積ルール」の 1 を参照） |
| `reviews/{機能名}/` | 任意 | 無ければ作成してから開始（レポート・対応方針表の保存先） |
| 前回記録 `reviews/{機能名}/R{前回}_*_review.md` / `_decision.md` | 任意 | 無ければ「初回」とし、レポートの差分節は「前回記録なし」と書く |

4. **チケット本文（概要・受け入れ条件）を入手する。** 順序は ①引数のチケットURL → ②決定台帳に記録された対象チケット → ③ユーザーに貼り付けを依頼。
   - **原則、チケット本文が無いまま Step 1 へ進まない。** 第1層の観点（BR-A）はチケット本文との突き合わせでしか出ないため、欠けると収穫の過半を失う。
   - **例外**: ユーザーが「チケット本文なしで進める」と明示した場合のみ、第1層を「未実施」と明記し、Step 1 は**第2層（成果物内部の整合）のみ実施**してから Step 2 以降を行う。第2層はチケット本文が無くても判定できるため落とさない。この場合、第1層を「指摘なし」とは絶対に書かない。
   - この規則は末尾の制約事項と同一である（二重に定義しない）。
5. 決定台帳「責務の境界線（決定台帳）」の表から、対象機能に関係する論点・赤カードを読み、既存の決定を把握する。
   - 前回記録がある場合は、最新の `_review.md`（前回の指摘一覧）と `_decision.md`（対応する／しない の判定）を読み、Step 4 の差分節の材料にする。今回のレビュー回は `R{回}` として確定し、確認表に載せる。
6. 基準書 7.1「先に機能の性質を宣言する」の性質の表から、対象機能に当てはまる性質を選び、以下の形式で提示する。

```
## レビュー対象の確認

### 対象機能: {機能名}
| 入力 | 状態 |
|---|---|
| チケット本文（概要・受け入れ条件） | 取得済み（{入手経路}） / 未取得 |
| rules.md | ルール{n}本・実例{n}行 |
| scenarios.md | シナリオ{n}本 |
| viewpoints.tsv | 観点{n}件 / 欠落 |
| 仕様書 | 参照可 / 不在（裏取り未実施） |
| 進行 | 通常 / 短縮モード |
| レビュー回 | R{回}（前回: R{前回} / 初回） |

### この機能の性質（第5層の前提）
| 性質 | 該当 | 引かれるテーマ |
|---|---|---|
| {基準書 7.1 の性質} | ✅ / — | {対応するテーマID} |
| ...（7.1 の表の全行を列挙） | | |
```

7. **【次Step移行確認】** 「この性質の選び方で合っていますか？Step 1（整合性レビュー）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 1: 整合性レビュー（第1層・第2層）

1. チケット本文から **状態の列挙・UI文言・数値と境界表現・時刻の定義** を抜き出して一覧化する。
2. 同じ項目を `rules.md` / `scenarios.md` から抜き出し、**左右に並べて**突き合わせる。
3. 基準書に定義された第1層・第2層の全観点（執筆時点の例: BR-A1〜A8、BR-B1〜B4。基準書側が増減した場合は基準書に従う）で判定し、一致しない行・片側にしか無い行を指摘として起こす。
4. 以下の形式で提示する。

```
## 第1層・第2層の指摘

| # | 重さ | 観点ID | 指摘 | チケット本文側 | 成果物側 | 直し方 | 確認先 |
|---|-----|-------|------|--------------|---------|-------|-------|
| R{回}-1-1 | 🔴 | {観点ID} | {一行要約} | （原文を引用） | （原文を引用） | （1案） | QA / 仕様担当 / 実装確認 |
```

5. **断定しないこと。** どちらが正しい仕様かはユーザー・仕様担当の判断であり、レビューは両方を並べて直し方を提案するに留める。
6. 指摘が0件の場合は「指摘の共通ルール」の書き方で、突き合わせた件数を残す。
7. **【次Step移行確認】** 「Step 2（シナリオ精査）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 2: シナリオ精査（第3層・第4層）

1. Step 1 で見つけた食い違いの一覧を手元に置き、**「その食い違いを現在の例が区別できるか」を1件ずつ確かめる**（BR-C2）。区別できない場合は、区別できる例を1行追加する提案を書く。
2. シナリオを1本ずつ、基準書に定義された第3層・第4層の全観点（執筆時点の例: BR-C1〜C8、BR-D1〜D4）で判定する。
3. `# @TestLevel:` を読み、その階層で実行可能かを必ず確認する（BR-D1）。E2E（Cloud実機）では端末の時計・システム時刻を操作できない前提で判定する。
   - **`# @TestLevel:` が無いシナリオ**は、それ自体を BR-D1 の指摘（🟠・確認先 QA）として起こす。階層を推測して判定しない。
4. 以下の形式で提示する（Step 1 の表と違い、比べる相手はチケット本文ではなくシナリオ自身なので、列名は「根拠／現状」とする）。

```
## 第3層・第4層の指摘

| # | 重さ | 観点ID | 指摘 | 対象シナリオ | 根拠／現状（原文を引用） | 直し方 | 確認先 |
|---|-----|-------|------|------------|----------------------|-------|-------|
| R{回}-2-1 | 🟠 | {観点ID} | {一行要約} | {シナリオ名} | {該当行の原文} | （1案） | QA / 仕様担当 / 実装確認 |
```

5. **【次Step移行確認】** 「Step 3（不足観点の洗い出し）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 3: 不足観点の洗い出し（第5層）

1. Step 0 で宣言した性質に対応するテーマ（基準書 7.2「テーマごとの観点」。執筆時点の例: BR-E1〜E9）だけを使い、確認したい場面を洗い出す。**宣言していない性質のテーマからは引かない。**
2. 洗い出した各項目について、**挙げる前に決定台帳と突き合わせる**。振り分けの判断は、**決定台帳「責務の境界線（決定台帳）」の表に並ぶ既存の決定**と、**基準書10章「指摘を起こす前の責務チェック」**に従う。本スキルは判定文を持たない。
   - 既存の決定でカバーされない論点に当たった場合は、無理に振り分けず **🟡 要確認（確認先: 仕様担当）** として挙げ、台帳への追記が必要である旨を書く。
3. 既存の `viewpoints.tsv` / `scenarios.md` に**すでに含まれていないか**を必ず確認する（viewpoints.tsv 欠落時は scenarios.md のみ）。含まれている場合は挙げない。
4. 以下の形式で提示する。

```
## 第5層の指摘（不足観点）

### 本機能の責務に含まれるもの
| # | 重さ | 観点ID | 確認したい場面 | 既存成果物での扱い | 台帳の論点（本機能の責務とした根拠） | 確認先 |
|---|-----|-------|--------------|-----------------|------------------------------|-------|
| R{回}-3-1 | 🟠 | {観点ID} | {場面} | {既存シナリオ・観点の有無} | {台帳の論点番号} | QA / 仕様担当 / 実装確認 |

### 他チケットの責務と判定したもの（申し送り。重さ・確認先は付けない）
| # | 観点ID | 確認したい場面 | 申し送り先 | 根拠（台帳の論点） |
|---|-------|--------------|----------|-----------------|
| R{回}-3-M1 | {観点ID} | {場面} | {申し送り先チケット名} | {台帳の論点番号} |
```

5. **【次Step移行確認】** 「Step 4（レポート統合）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 4: レポート統合

1. **出力前セルフチェック**。以下をすべて満たしてから出力する。満たせない項目があれば、出力せずに該当Stepへ戻る。
   - [ ] すべての指摘（申し送り含む。ただし申し送り先が「非機能周り」のものは除く）に観点IDが付いている
   - [ ] 申し送りを除くすべての指摘に重さ（1つ）・確認先が付いており、確認先は3種のいずれかである
   - [ ] 「〜が正しい」「〜であるべき」など断定表現がない（直し方は「案」として書かれている）
   - [ ] 不足観点は全件、「台帳の論点」列と「既存成果物での扱い」列が埋まっている（空欄＝照らしていない）
   - [ ] サマリーの「赤カード候補」の件数は、確認先の内訳表の「仕様担当」＋「実装確認」の件数と一致する
   - [ ] 前回記録がある場合、前回の全指摘IDが差分表に載っている
   - [ ] 指摘が0件の層には、突き合わせた内容が件数つきで書かれている
   - [ ] 第1層を未実施にした場合、その旨がサマリーに明記されている

2. Step 1〜3 の指摘を統合し、以下の形式で出力する。

```
| 確認先 | 件数 | 指摘ID |
|---|---|---|
| QA（自分で直せる） | {n} | {id, id} |
| 仕様担当 | {n} | {id, id} |
| 実装確認 | {n} | {id, id} |

■ 5. 改善提案（指摘ではない）
（表記ゆれ・並び順など、修正対象外の言い換え案。件数には含めない）

■ 6. このレビューで確認できなかったこと
（チケット本文・仕様書・ソースが手元に無く判定できなかった点を列挙。仕様書が不在の場合は「仕様書による裏取り未実施」を必ず含める）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

3. **「まず直すもの」は件数の多さではなく先行関係で並べる。** 第2層の指摘（執筆時点の例: BR-B1「状態の正の所在」）は、ほぼ常に先頭に来る。
4. レポートを `reviews/{機能名}/R{回}_{YYYY-MM-DD}_review.md` に保存する（回を付けるので同日複数回でも衝突しない）。
5. レポートの最後に以下を出力して停止する。

> 上記の指摘について、**対応する／対応しない** の分類を行いますか？
> - **はい**: 分類表を作成し、対応するものを修正要求書にまとめます
> - **一部のみ**: 対応する指摘を教えてください。**IDでも「なりすましの件」のような普通の言い方でも構いません**（こちらでIDに対応づけます）
> - **いいえ**: レポート出力のみで終了します

### Step 5: 対応方針の確定と引き渡し

1. ユーザーの合意を得た指摘について、以下の分類表を作成する。**判定列はスキルが案（対応する／対応しない＋理由）を埋め、ユーザーが確定する。** ユーザーが変更した行はユーザーの判定を正とし、理由にその旨を残す。
   - ユーザーが自然な言い方で指摘を指した場合は、**スキル側がIDへ対応づけて**分類表に反映する。IDでの指定を求めない。対応づけに迷う場合のみ候補を2〜3件挙げて聞く。

```
## 対応方針

| # | 指摘 | 判定（案→確定） | 理由 |
|---|------|------|------|
| R{回}-1-1 | {一行要約} | 対応する / 対応しない | （対応しない場合は**文章で**理由を書く。台帳の参照番号だけで済ませない） |
```

2. 「対応する」と判定した指摘を、以下の**修正要求書**の書式で**1つにまとめる**（指摘ごとに分けて渡さない）。

```
## 修正要求書: {機能名}（{YYYY-MM-DD}）
| 指摘ID | 対象ファイル | 現状（原文） | 修正後（案） | 根拠（観点ID） |
|---|---|---|---|---|
| R{回}-1-1 | rules.md | {原文} | {修正案} | {観点ID} |
```

3. 「仕様担当」「実装確認」と振り分けた指摘は、**赤カードの起票候補**として分類表の下に一覧で残す。
4. 申し送りに分類した項目は、**申し送り先のチケット名つきで一覧に残す**。指摘から消さない。
5. 保存する（停止より前に行う）。
   - 分類表・赤カード候補・申し送り一覧 → `reviews/{機能名}/R{回}_{YYYY-MM-DD}_decision.md`
   - 修正要求書 → `reviews/{機能名}/R{回}_{YYYY-MM-DD}_request.md`（対応する指摘が0件なら作らず、その旨を decision.md に書く）
6. 引き渡しは**自動実行しない**。保存が終わったら、以下を案内して停止する。

> 修正要求書を `reviews/{機能名}/R{回}_{YYYY-MM-DD}_request.md` に保存しました。
> 次は `/bdd-artifact-updater {機能名} {修正内容}` を実行し、**修正内容に上記ファイルの表を貼り付けて**ください。

## Constraints (制約事項)
- **編集禁止の範囲（最重要）**: 成果物・決定台帳・仕様書・基準書・本スキル定義を編集しないこと。書き込んでよいのは `.claude/memories/review-bdd-artifacts.md` と `reviews/{機能名}/` のみ。修正は `/bdd-artifact-updater`、台帳の更新は `/feature-map` の責務。
- **進行制御**: ユーザーの明確な合意なしに次のStepへ進まないこと。短縮モードは Instructions の定義どおり、冒頭での明示があった場合のみ。
- **チケット本文を必須入力とする**: 原則、入手できるまで Step 1 へ進まない。ユーザーが「無しで進める」と明示した場合のみ、第1層を「未実施」と明記して進む。第1層を「指摘なし」と報告してはならない（Step 0 の 4 と同一規則）。
- **IDでの指定を求めない**: 指摘IDはレポート内の参照と前回差分のための番号である。ユーザーには自然な言い方で指摘を指してもらい、スキル側がIDへ対応づけること。
- **断定の禁止**: どちらが正しい仕様かをレビュー側で決めないこと。両方の記述を並べ、直し方を提案するに留める。
- **責務の先行確認**: 不足観点を挙げる前に必ず決定台帳の「責務の境界線（決定台帳）」の表と突き合わせ、他チケットの責務と判定したものは申し送りへ振り分けること。「画面の表示が変わるから対象」という粗い基準で積まないこと。
- **既存成果物との重複確認**: 不足観点として挙げる前に、既存の `scenarios.md` / `viewpoints.tsv` に含まれていないかを必ず確認すること。
- **スコープ外を指摘しない**: 非機能要件（性能・負荷・セキュリティ）、外部SDK・バックエンドの内部ロジックは CLAUDE.md のスコープ定義により指摘対象外。
- **非機能の懸念の扱い**: レビュー中に気づいた性能・負荷・セキュリティなどの懸念は、指摘にせず申し送り表に残す。申し送り先は「非機能周り」、観点IDは「—」、根拠は「スコープ外」と書く。件数には含めず、メモリー蓄積の対象にもしない。
- **表記ゆれは提案に留める**: 修正対象外の記述の言い換え・並び順の変更は指摘として挙げず、レポートの「改善提案」枠に記載すること。
- **参照元がiOSであること**: 仕様書・ソースはiOS版。呼称はAndroid版プロダクトの決定を優先し、iOS版の用語定義との不一致を指摘にしないこと。
- **判定基準の参照**: 実行時には必ず `docs/bdd_review_criteria.md` を読み込み、最新の観点に従うこと。本スキルに書かれた観点IDの範囲・章番号は執筆時点の例であり、基準書と食い違う場合は基準書を正とする。観点IDを指摘に必ず付与すること（申し送りも含む）。

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md` および `.claude/memories/review-bdd-artifacts.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。
   - `.claude/memories/bdd-artifact-updater.md` も読み込み、引き渡し先で過去に問題になった点（修正要求の書き方の不足など）を Step 5 の修正要求書に反映してください。無ければ読み飛ばします（本スキルは作成しません）。
   - `.claude/memories/review-bdd-artifacts.md` が存在しない場合は、以下の雛形を作成してから開始してください。

     ```
     # BDD成果物セルフレビュー - 学習メモリー
     **総指摘件数**: 0

     ---
     ## 蓄積された指摘事項
     ```

2. **レビュー結果の作り直しに伴う蓄積（トリガールール）**:
   - **蓄積する場合**: ユーザーの修正指示が、次のいずれかに当たると判断したとき。
     - 観点の適用漏れ（基準書にある観点で拾えたはずの指摘を落とした）
     - 責務の誤判定（本機能／他チケットの振り分けを誤った）
     - 既存成果物との重複の見落とし
     - 断定の禁止違反
     - 既存の観点IDのどれでも拾えない指摘（→ 下記 ③）
   - **蓄積しない場合**（作り直しであっても教訓ではない）:
     - チケット本文・仕様書など入力が後から届いたことによる再実行
     - 表の長さ・言い回し・並び順など体裁の注文
     - 仕様側が変わったことによる再レビュー
   - 蓄積する場合は、レビュー結果を再作成する**前に**、`.claude/memories/review-bdd-artifacts.md` へ追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」を、**今回追記した教訓の数だけ**加算して上書きしてください（1回の作り直しで教訓が2つあれば +2、0なら更新しない）。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ```
     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象タスク**: （例: 整合性レビュー、シナリオ精査、不足観点の洗い出し、責務の振り分け など）
     - **対象機能**: {引数で受け取った対象機能名}
     - **指摘カテゴリ**: （観点の適用漏れ / 責務の誤判定 / 既存成果物との重複の見落とし / 断定の禁止違反 / 観点の不足）
     - **指摘された内容**: （ユーザーからの具体的な修正指示）
     - **原因/理由**: （なぜその問題が発生したかの分析）
     - **今後の対策**: （次回実行時に守るべきルールの言語化）
     ```

   - **③ 観点そのものに不足があった場合**: 既存の観点IDのどれでも拾えない指摘がユーザーから出た場合は、メモリーへの追記に加えて **`docs/bdd_review_criteria.md` への観点追加をユーザーに提案**してください（基準書の更新は承認を得てから行います。本スキルは基準書を編集しません）。

3. **完了報告**:
   - 蓄積した場合: 「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、レビュー結果を作り直しました」と報告してください。
   - 蓄積しなかった場合: 「今回の作り直しは（入力追加／体裁の注文／仕様変更）によるもので、メモリーには蓄積していません」と理由つきで報告してください。
