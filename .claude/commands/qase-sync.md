# Skill: qase-sync
テストコードの `@Qase` をQaseへ同期し、必要に応じて実行結果とカバレッジを送信します。

## Usage
`/qase-sync [cases|results|all] [--module <path>]`
例: `/qase-sync cases`
例: `/qase-sync results`
例: `/qase-sync cases --module core/data`

- `cases`: ケース内容（タイトル・説明・Test Level・ステップ）の同期
- `results`: 実行結果とカバレッジの送信
- `all`: 両方を順に実行
- 省略時は `cases`

## Instructions
あなたはQA担当のアシスタントとして、Qaseへの同期を実行してください。

【最重要ルール】:
1. **Qaseへの送信は不可逆です。** 必ず `--dry-run` で内容を提示し、ユーザーの承認を得てから本送信してください。
2. **対象リポジトリのファイルを変更してはいけません**（読み取り専用）。
3. **スクリプトのロジックを書き換えて回避しないでください。** 検証で中断した場合は、原因を報告して停止します。

実行前に `.claude/memories/global.md` と `.claude/memories/qase-sync.md` を読み込んでください。

### Step 1: 環境の確認

以下を確認し、不足があれば**処理を中断**して報告してください。

| 確認項目 | 方法 |
|---|---|
| `QASE_API_TOKEN` が設定されているか | 環境変数の存在のみ確認（**値を表示しないこと**） |
| `QASE_PROJECT_CODE` が本番プロジェクトか | 既定値 `RSA` のままなら、本番の値か確認を取る |
| `QASE_TEST_LEVEL_FIELD_ID` / `QASE_COVERAGE_FIELD_ID` | 既定値のままなら、本番プロジェクトで確認済みか確認を取る |
| 対象リポジトリの存在 | ディレクトリの存在確認 |

> 既定値は検証用リポジトリのものです。**本番プロジェクトのIDと異なる場合、誤ったプロジェクトへ書き込む事故になります。** 初回実行時は必ず確認してください。

### Step 3: ケース同期（`cases` / `all` の場合）

#### 3-1. dry-run で内容を提示

```
python scripts/qase_sync.py --input build/qase/qase-cases.json --dry-run
```

出力をもとに、同期対象の一覧（ケースID・タイトル・Test Level・ステップ有無）を提示してください。

#### 3-2. 承認を求める

> 上記 {n} 件を Qase（プロジェクト: {QASE_PROJECT_CODE}）へ同期します。
> **Qase側のタイトル・説明・Test Level・ステップは上書きされます。** 実行してよろしいですか？

#### 3-3. 本送信

承認後にのみ `--dry-run` を外して実行します。

- 事前検証（ID重複・ID存在確認）で中断した場合は、原因と対処方法を報告して**停止**してください
- 孤児候補が報告された場合は、そのまま提示します。**削除の判断はユーザーに委ね、スキルから削除してはいけません**

#### 3-4. 反映確認

同期後、代表1件をAPIで読み取り、`title` / `description` / `custom_fields` / `automation` / `suite_id` が意図どおりか確認して報告してください。

> Qase API は無視したフィールドについてエラーを返しません。**書き込んだら読み取って確認する**のが原則です。

---

### Step 4: 結果送信（`results` / `all` の場合）

#### 4-1. テスト結果の所在を確認

ユーザーに確認してください。

> テスト結果（`TEST-*.xml`）とカバレッジレポートの場所を指定してください。
> - **CI**: GitHub Actions の artifact `test-results-and-coverage` を展開したディレクトリ
> - **ローカル**: 対象リポジトリで `./gradlew testDevelopDebugUnitTest createDevelopDebugCombinedCoverageReport` を実行した後の出力

#### 4-2. dry-run で集計を提示

```
python scripts/send_qase_results.py \
  --input build/qase/qase-cases.json \
  --test-results <dir> --jacoco <dir> --dry-run
```

突合結果（成功 / 未実行の件数）、passed / failed / skipped の内訳、カバレッジ率を提示してください。

**未実行のケースがある場合は、その一覧も提示**してください。テストが実行されていないのか、クラス名が一致していないのかの切り分けが必要です。

#### 4-3. 承認を求める

> 上記 {n} 件の結果とカバレッジ {x}% を、Qase に新規Runとして送信します。
> Runのタイトルは「{title}」です。実行してよろしいですか？

Runのタイトルには、識別しやすいようブランチ名やPR番号を含めることを提案してください。

#### 4-4. 本送信

承認後に `--dry-run` を外して実行します。

- **失敗したテストがあるとスクリプトは終了コード1を返します。** これは正常な挙動です（結果は送信済み）。エラーとして扱わず、失敗件数を報告してください
- 送信後、RunをAPIで読み取り、カバレッジのカスタムフィールドが入っているか確認してください

## Constraints (制約事項)
- **承認の必須化**: 本送信の前に必ず `--dry-run` の結果を提示し、承認を得ること。
- **トークンの保護**: `QASE_API_TOKEN` の値を表示・記録しないこと。存在確認のみ行うこと。
- **プロジェクトの確認**: 設定値が既定値（検証用リポジトリの値）のままの場合、本番プロジェクトか確認を取ること。
- **読み取り専用**: 対象リポジトリのファイルを変更しないこと。
- **削除の禁止**: 孤児候補として報告されたケースを削除しないこと。判断はユーザーが行う。
- **検証の尊重**: 事前検証で中断した場合、スクリプトを書き換えて回避しないこと。原因を報告して停止すること。
- **反映確認の必須化**: 送信後は必ずAPIで読み取り、反映を確認すること。
- **終了コード1の扱い**: 結果送信でテスト失敗があった場合の終了コード1は正常な挙動。失敗として報告しないこと。
