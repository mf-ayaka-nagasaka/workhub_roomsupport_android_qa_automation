# Skill: qa-matrix-generator
テスト観点からデシジョンテーブルを生成し、人間のフィードバックを反映した修正・更新を支援します。

## Usage
`/qa-matrix-generator [チケットNo]`

## Context / Scope
- **テンプレート（構造参照）**: `./data/デシジョンテーブル_テンプレート(長坂用).xlsx` を因子・水準・期待値の構成参照として使用すること。
- **テンプレート（HTML）**: `docs/test_viewpoints/release/v5.6.0/WSS-1613/v5.6.0_WSS-1613_matrix.html`（※Android版のHTMLテンプレートが作成された時点でパスを更新すること）をHTML出力の参照テンプレートとして使用すること。
- **参照元**: `docs/test_viewpoints/release/{TicketNo}/{AppVer}_{TicketNo}.md`
- **出力先**: `docs/test_viewpoints/release/{TicketNo}/{AppVer}_{TicketNo}_matrix.html`

## Instructions

### 1. 初回生成
- 指定されたテスト観点から「因子」「水準」「期待値」を抽出し、HTML形式のデシジョンテーブルを作成してください。
- **テンプレート参照**: HTMLテンプレートを必ず読み込み、同一のHTML構造・CSSスタイルを踏襲すること。
- **レイアウトルール**:
  - ヘッダー行: `#`, `因子`, `水準`, テストケース番号（1, 2, 3...）を横列に並べる
  - 因子グループ: 青色（`#e8f0fe`）のグループヘッダーで `🔹 条件` セクションを区切る
  - 条件行: 該当するテストケース列に `〇`（`mark-o`、青色 `#2c7be5`）を配置、該当しないセルは `-`（`mark-dash`）
  - 期待値セクション: オレンジ色（`#fef6e8`）の `✅ 期待値` 区切りヘッダーの下に配置
  - 期待値行: 該当テストケース列に `●`（`mark-dot`、緑色 `#27ae60`）を配置、該当しないセルは `-`（`mark-dash`）
  - 否定的な期待値（〜しないこと等）には `×`（`mark-x`、赤色 `#e74c3c`）を使用可
- **必須要素**: タイトル（h1）、メタ情報（AppVer・チケットNo・作成日）、テストケース総数サマリーテーブル、観点ごとのh2見出しとnote（前提条件）
- **記号ルール**: 条件行(🔹)には「〇」「-」、期待値行(✅)には「●」「×」を使用。

### 2. 人間によるレビューと修正 (Feedback Loop)
- テーブル提示後、ユーザーに修正・追加・削除の要望がないか確認してください。
- **修正指示への対応**:
  - 指示を受けたら、論理的な整合性を保ったままテーブルを再構成してください。
  - 修正版を再度提示し、合意を得るまでこのプロセスを繰り返します。

### 3. ファイル確定・保存
- ユーザーの合意（「これでOK」「保存して」等）を得た段階で、出力先ファイルに書き出してください。
  - `docs/test_viewpoints/release/{TicketNo}/{AppVer}_{TicketNo}_matrix.html`
- 最後に、最終的なテストケース数を明示してください。

### 4. バージョン管理（Git Operations）
- ファイル保存後、以下の操作を自動（または提案）してください。
  - `git add` および `git commit -m "qa: update test matrix for v{AppVer} ({TicketNo})"`
  - `git tag -af v{AppVer} -m "Latest QA artifacts for version {AppVer}"`
  - 既存のタグがある場合でも `-f` (force) オプションで強制更新し、常に最新コミットを指すようにします。

## Constraints
- `./data/デシジョンテーブル_テンプレート(長坂用).xlsx` の項目定義から逸脱しないこと。
- HTMLテンプレートのCSS・構造を忠実に再現すること。独自スタイルを追加しないこと。
- ユーザーの確認なしにファイルを保存（上書き）しないこと。
- 修正時は、以前のバージョンとの差分が明確になるような説明を添えること。
- `base/` の観点ファイルを直接書き換えないこと。

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md` および `.claude/memories/qa-matrix-generator.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

2. **成果物の再生成に伴う自動蓄積（トリガールール）**:
   - ユーザーの指摘や修正指示によって、一度生成した成果物を作り直す場合、それは「初期出力に考慮漏れやルールの不一致があった」ことを意味します。
   - 成果物を再生成する**前に**、自律的に `.claude/memories/qa-matrix-generator.md` へ物理的にファイル編集を行って追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象タスク**: （例: 影響範囲の抽出、テスト観点作成など）
     - **対象機能**: （例: ログイン画面、決済APIなど）
     - **指摘カテゴリ**: （例: 網羅性の不足、仕様の誤認識、具体性の不足、フォーマット違反 など）
     - **指摘された内容**: （例: 重点確認ケースに「ログイン周り」が抜けている）
     - **原因/理由**: （例: 依存関係の読み込みが甘かったため）
     - **今後の対策**: （例: 認証が絡む変更の際は必ずログインケースを強制抽出する）

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、成果物の再生成も終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、成果物を作り直しました」と必ず報告してください。
