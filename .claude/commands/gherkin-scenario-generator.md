# Skill: gherkin-scenario-generator
iOS仕様書（Markdown）からビジネスルール・実例を抽出し、BDDガイドラインとテスト設計ルールに則ったGherkinシナリオ（.feature）を一括生成する自動化Skillです。

## Usage
`/gherkin-scenario-generator [対象機能名または仕様書パス]`

例: `/gherkin-scenario-generator reservation`
例: `/gherkin-scenario-generator "C:\Users\mforce0087\workhubRoomSupport\docs\spec\reservation.md"`

## Context / Scope
- **参照元仕様書リポジトリ**: `C:\Users\mforce0087\workhubRoomSupport` 配下の Markdown (.md) ファイル
- **関連メモリー**: `.claude/memories/gherkin-scenario-generator.md`、`.claude/memories/global.md`
- **スキル一覧**: `.claude/commands/README.md`
- **成果物出力先**: 人間（ユーザー）による✅＆承認用の出力テキスト（必要に応じて該当モジュールの `src/test/resources/features/` へ保存）

## Instructions
あなたはAndroidアプリのQA・BDD設計パートナーとして振る舞います。
【最重要ルール】: 添付の「テスト設計ルール」を最優先としつつ、「BDDガイドライン」の設計思想（Whatの記述、宣言的ステップ）に従って処理を実行してください。

### Step 1: 仕様書の読み込みと分析 (Investigate)

> **【必読】このStepを開始する前に、以下のファイルを必ず読み込んでから作業を開始すること：**
> - `C:\Users\mforce0087\workhubRoomSupport` 内の対象となる機能仕様書 (.md)
> - `.claude/memories/gherkin-scenario-generator.md`（存在する場合、過去の指摘事項）
> - `.claude/memories/global.md`

1. 指定された対象機能またはファイルパスから、対応するiOS仕様書（.md）の内容を読み込む。
2. 仕様書から以下の要素を抽出・分析する：
   - 機能の目的および背景
   - 包含されるビジネスルール
   - 正常系・異常系・境界値のシナリオ要素
   - 仕様書から読み取れない曖昧な点・未定義の例外ケース（「赤カード」疑問点）

### Step 2: ルール整理とGherkinシナリオの作成 (Generate)

抽出した内容を基に、以下の2パートで構成される成果物を作成する。

#### ガードレール（作成時の適用ルール）：

##### A. ルール粒度の定義（最重要）
- ❌ **禁止**: 画面のルーティング、1トーストメッセージごとの処理分岐、内部バリデーションの個別ステップを1ルールにしない。
- ⭕ **必須**: 「**誰が**（属性・権限）」「**どのような状態で**」「**何を達成できるか／拒否されるか**」というビジネスルール単位でまとめる。
- 1つのルールには、そのルールを検証するための正常系・異常系の実例（データ・状況の組み合わせ）を複数行で列挙する。

##### B. Gherkin記述3原則（BDDガイドライン 6.3 / 6.5 準拠）
1. **Given=Arrange / When=Act / Then=Assert** の構造に厳格に当てはめる。
2. **宣言的記述（What）**: 「〜ボタンを押す」「〜画面に遷移する」ではなく、「〜を実行する」「〜を要求する」「〜を試みる」と記述する。
3. **中間状態の隠蔽**: 「認証後のバリデーションを実行する」のような内部実装の呼び出しは書かない。ユーザーの目的の操作（例: `もし 佐藤が顔認証を実行する`）で記述する。
4. **観測可能な結果のみ**: `ならば` にはユーザーから観測可能な結果（エラーメッセージの表示、予約の作成成否、ドアの解錠可否など）のみを書く。「〜シートが表示される」「〜トーストが表示される」等のUIコンポーネント名ではなく、「エラーメッセージ "文言" が表示される」「予約は作成されない」のようにビジネス結果として記述する。
5. **決定性の担保**: 時刻や日付が関係する場合、`now()` 等の現在時刻直呼びに依存せず、絶対日時や明確な基準時間を記述する。
6. **具体的なペルソナ**: シナリオには具体的なユーザー名（例: "佐藤"、"鈴木"）を使い、属性・状態を前提で明示する。

#### 出力例（アンカー）：
以下は「今すぐ入室」機能を対象とした場合の出力品質の基準例である。実際の出力はこの粒度・記述スタイルに合わせること。

**ルール例:**
- ルール①: 顔情報登録済み従業員の顔なら予約作成＆入室できる
- ルール②: テナント従業員による予約が許可時のみ会員も予約作成＆入室できる

**パート1テーブル例（ルール①）:**

| 対象 | 顔情報 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 従業員 | 登録済み | 正常系：登録済み従業員の顔で認証 | 予約作成＆入室成功 |
| ゲスト | 登録済み | 異常系：登録済みのゲストが認証 | 権限なしエラー表示 |
| - | 未登録 | 異常系：顔未登録のユーザーが認証 | 顔未登録時のエラー表示 |

**パート2 Gherkin例:**
```gherkin
  # 🟢 正常系：登録済み従業員
  シナリオ: 登録済み従業員の顔認証成功により予約作成と入室ができる
    前提 ユーザー "佐藤" は "従業員" であり、顔データが登録されている
    もし 佐藤が顔認証を実行する
    ならば 予約が作成され、ドアが解錠される

  # 🔴 異常系：登録済みゲスト（権限エラー）
  シナリオ: 登録済みのゲストアカウントでは予約作成・入室が拒否される
    前提 ユーザー "鈴木" は "ゲスト" であり、顔データが登録されている
    もし 鈴木が顔認証を実行する
    ならば エラーメッセージ "予約作成は従業員のみ行えます" が表示される
    かつ 予約は作成されない
```

````markdown

### 機能名: 【仕様書から抽出した機能名】
**機能概要:** 【機能の目的・概要】

### ルール①: 【ビジネスルール名（「誰が」「何を」「達成できる／拒否される」の形式）】
| 対象 | 【因子1】 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |

| 【属性B】 | 【状態2】 | 異常系：【具体的な組み合わせ】 | 【拒否・エラーの結果】 |

※因子の列は、ルールに関わる条件軸（顔情報、契約状態、権限設定 等）に応じて適切に追加する。

```gherkin

  # 🔴 異常系：【ケース名】
  シナリオ: 【拒否されるビジネス結果を主語述語で記述】

    もし 【名前】が【ユーザーの目的の操作（正常系と同じ操作）】
````

### Step 3: 人間による最終確認と承認 (Review & Apply)

1. 生成した「パート1（ルール・実例・疑問点）」および「パート2（Gherkin）」を一括でユーザーに提示する。
2. ユーザーへ以下の選択肢を提示し、フィードバックを求める：
   - **「✅ 承認（OK）」** → 生成結果を確定し、必要に応じて `.feature` ファイルとしてプロジェクトに配置・保存する。
   - **「修正指示（赤カードの回答など）」** → 指摘・回答内容を反映して Step 2 を再実行する。

## Constraints (制約事項)
- **テストコード実装の除外:** 本Skillは `.feature` シナリオの作成・定式化のみを担当し、JUnitやステップ定義コード（Kotlin）の実装は生成対象外とする。
- **独断による仕様補完の禁止:** 仕様書に記載のない動作を推測で仕様化せず、必ず「赤カード（疑問点）」として抽出して提示すること。
- **1機能1ファイル:** 生成されるGherkinは 1機能 = 1 `.feature` ファイルの原則を守ること。

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md` および `.claude/memories/gherkin-scenario-generator.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

2. **成果物の再生成に伴う自動蓄積（トリガールール）**:
   - ユーザーの指摘や修正指示によって、一度生成した成果物を作り直す場合、成果物を再生成する**前に**、自律的に `.claude/memories/gherkin-scenario-generator.md` へ物理的にファイル編集を行って追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ```
     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象機能**: {引数で受け取った対象機能名}
     - **指摘カテゴリ**: （例: 網羅性の不足、仕様の誤認識、表現の手続き化、フォーマット違反 など）
     - **指摘された内容**: （ユーザーからの具体的な修正指示）
     - **原因/理由**: （なぜその問題が発生したかの分析）
     - **今後の対策**: （次回生成時に守るべきルールの言語化）
     ```

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、成果物の再生成も終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、成果物を作り直しました」と必ず報告してください。
