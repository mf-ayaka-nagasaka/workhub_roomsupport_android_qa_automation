# Skill: gherkin-scenario-generator
ルール・実例の成果物（rules.md）を入力として、BDDガイドラインとテスト設計ルールに則ったGherkinシナリオ（scenarios.md）を生成するSkillです。

## Usage
`/gherkin-scenario-generator [対象機能フォルダ名]`

例: `/gherkin-scenario-generator login`
例: `/gherkin-scenario-generator initial_setup`

## Context / Scope
- **入力（参照元）**: `src/test/resources/features/{機能名}/rules.md`（`/rule-example-extractor` の成果物）
- **関連メモリー**: `.claude/memories/gherkin-scenario-generator.md`、`.claude/memories/global.md`
- **スキル一覧**: `.claude/commands/README.md`
- **成果物出力先**: `src/test/resources/features/{機能名}/scenarios.md`

## Instructions
あなたはAndroidアプリのQA・BDD設計パートナーとして振る舞います。
【最重要ルール】: 添付の「テスト設計ルール」を最優先としつつ、「BDDガイドライン」の設計思想（Whatの記述、宣言的ステップ）に従って処理を実行してください。

### Step 1: ルール・実例の読み込み (Load)

> **【必読】このStepを開始する前に、以下のファイルを必ず読み込んでから作業を開始すること：**
> - `src/test/resources/features/{機能名}/rules.md`（`/rule-example-extractor` の成果物）
> - `.claude/memories/gherkin-scenario-generator.md`（存在する場合、過去の指摘事項）
> - `.claude/memories/global.md`

1. 引数で指定された機能名から `src/test/resources/features/{機能名}/rules.md` を読み込む。
2. rules.md が存在しない場合は、先に `/rule-example-extractor` を実行するようユーザーに案内して終了する。
3. rules.md から以下の要素を確認する：
   - 機能名・機能概要
   - 各ルール（ルール名、推奨テスト階層、実例テーブル）
   - 疑問点・未確認事項（赤カード）

### Step 2: Gherkinシナリオの作成 (Generate)

rules.md の各ルールをもとに、Gherkinシナリオを作成する。

#### ガードレール（作成時の適用ルール）：

##### A. Gherkin記述3原則（BDDガイドライン 6.3 / 6.5 準拠）
1. **Given=Arrange / When=Act / Then=Assert** の構造に厳格に当てはめる。
2. **宣言的記述（What）**: 「〜ボタンを押す」「〜画面に遷移する」ではなく、「〜を実行する」「〜を要求する」「〜を試みる」と記述する。
3. **中間状態の隠蔽**: 「認証後のバリデーションを実行する」のような内部実装の呼び出しは書かない。ユーザーの目的の操作（例: `もし 佐藤が顔認証を実行する`）で記述する。
4. **観測可能な結果のみ**: `ならば` にはユーザーから観測可能な結果（エラーメッセージの表示、予約の作成成否、ドアの解錠可否など）のみを書く。「〜シートが表示される」「〜トーストが表示される」等のUIコンポーネント名ではなく、「エラーメッセージ(文言)が表示される」「予約は作成されない」のようにビジネス結果として記述する。
5. **決定性の担保**: 時刻や日付が関係する場合、`now()` 等の現在時刻直呼びに依存せず、絶対日時や明確な基準時間を記述する。
6. **具体的なペルソナ**: シナリオには具体的なユーザー名（例: "佐藤"、"鈴木"）を使い、属性・状態を前提で明示する。

##### B. テスト階層の引き継ぎ
- rules.md の各ルールに記載された `推奨テスト階層` をそのままシナリオのコメントに反映する。
- rules.md に記載がない場合は、以下の判定マトリクスに従って割り当てる。

| 対象となる振る舞い・機能 | 割り当てるテスト階層 | 実行環境 |
| :--- | :--- | :--- |
| Pureな計算・日時判定・解錠権限などのビジネスロジック | **Domain Unitテスト** | JVM (超高速) |
| 予約確認〜解錠準備などの一連のフロー・ユースケース | **Application Unitテスト** | JVM (超高速) |
| ボタン押下後のLoading/Success表示、UiState/Effect変化 | **Presentation Unitテスト** | JVM (Turbine) |
| Room DBデータの読み書き・ローカル通信 | **Infrastructure Integration** | Robolectric / JVM |
| FaceMe、カメラX、NFC、実ゲート機器などのハード連携 | **CI対象外 (手動/実機エージェント)** | 実物ハードウェア |
| ユーザーストーリー（失敗すると業務停止する重要フロー） | **E2Eテスト** | Cloud実機 / Appium |

#### 出力例（アンカー）：
以下は「今すぐ入室」機能を対象とした場合の出力品質の基準例である。実際の出力はこの粒度・記述スタイルに合わせること。

```gherkin
# language: ja
機能: 今すぐ入室
  空室状態の会議室に対して、顔認証を行い即時予約・入室を行う。

  背景:
    前提 タブレットにRoomSupportアプリがインストールされている

  # ────────────────────────────────────────
  # ルール①: 顔情報登録済み従業員の顔なら予約作成＆入室できる
  # ────────────────────────────────────────

  # @TestLevel: ApplicationUnit (JVM)
  # 🟢 正常系：登録済み従業員
  シナリオ: 登録済み従業員の顔認証成功により予約作成と入室ができる
    前提 ユーザー "佐藤" は "従業員" であり、顔データが登録されている
    もし 佐藤が顔認証を実行する
    ならば 予約が作成され、ドアが解錠される

  # @TestLevel: ApplicationUnit (JVM)
  # 🔴 異常系：登録済みゲスト（権限エラー）
  シナリオ: 登録済みのゲストアカウントでは予約作成・入室が拒否される
    前提 ユーザー "鈴木" は "ゲスト" であり、顔データが登録されている
    もし 鈴木が顔認証を実行する
    ならば エラーメッセージ(予約作成は従業員のみ行えます)が表示される
    かつ 予約は作成されない

  # @TestLevel: ApplicationUnit (JVM)
  # 🟡 例外系：認証デバイスタイムアウト
  シナリオ: 認証デバイスのタイムアウト時にエラーメッセージが表示される
    前提 ユーザー "佐藤" は "従業員" であり、顔データが登録されている
    かつ 認証デバイスがタイムアウト状態である
    もし 佐藤が顔認証を実行する
    ならば エラーメッセージ(認証デバイスに接続できません)が表示される
    かつ 予約は作成されない

  # ────────────────────────────────────────
  # E2E: ユーザーストーリー
  # ────────────────────────────────────────

  # @TestLevel: E2E (Cloud実機 / Nightly)
  # 🟢 正常系：主要動線（即時入室）
  シナリオ: 空室状態から顔認証を経て正常に即時予約と入室ができる
    前提 ユーザー "佐藤" は "従業員" であり、すべてのバリデーション条件を満たしている
    もし 佐藤が顔認証を実行する
    ならば 予約が作成され、ドアが解錠される
```

#### 出力フォーマット形式：

```gherkin
# language: ja
機能: 【機能名】
  【この機能の目的や概要の補足情報】

  背景:
    前提 【共通の初期状態（機能の起点となるユーザー操作の直前状態）】

  # ────────────────────────────────────────
  # ルール①: 【ビジネスルール名】
  # ────────────────────────────────────────

  # @TestLevel: 【階層名】 (【実行環境】)
  # 🟢 正常系：【ケース名】
  シナリオ: 【達成されるビジネス結果を主語述語で記述】
    前提 ユーザー "【名前】" は【状態の詳細】
    もし 【名前】が【ユーザーの目的の操作（宣言的・1アクション）】
    ならば 【観測可能なビジネス結果】

  # @TestLevel: 【階層名】 (【実行環境】)
  # 🔴 異常系：【ケース名】
  シナリオ: 【拒否されるビジネス結果を主語述語で記述】
    前提 ユーザー "【名前】" は【エラー条件を満たす状態】
    もし 【名前】が【ユーザーの目的の操作】
    ならば エラーメッセージ(【実際のエラー文言】)が表示される
    かつ 【状態が変わらないことの検証】

  # @TestLevel: 【階層名】 (【実行環境】)
  # 🟡 例外系：【ケース名】
  シナリオ: 【システム起因のエラー時の振る舞いを主語述語で記述】
    前提 ユーザー "【名前】" は【正常な操作条件を満たす状態】
    かつ 【システムや外部要因のエラー条件】
    もし 【名前】が【ユーザーの目的の操作】
    ならば エラーメッセージ(【実際のエラー文言】)が表示される
    かつ 【状態が変わらないことの検証】

  # ────────────────────────────────────────
  # ルール②: 【ビジネスルール名】
  # ────────────────────────────────────────
  ...（同様にルール配下にシナリオを列挙）

  # ────────────────────────────────────────
  # E2E: ユーザーストーリー
  # ────────────────────────────────────────

  # @TestLevel: E2E (Cloud実機 / Nightly)
  # 🟢 正常系：主要動線（【動線名】）
  シナリオ: 【ユーザーストーリーを主語述語で記述】
    前提 ユーザー "【名前】" は【すべての正常条件を満たす状態】
    もし 【名前】が【ユーザーの目的の操作】
    ならば 【観測可能なビジネス結果】
```

### Step 3: 人間による最終確認と承認 (Review & Apply)

1. 生成したGherkinシナリオをユーザーに提示する。
2. ユーザーへ以下の選択肢を提示し、フィードバックを求める：
   - **「✅ 承認（OK）」** → 生成結果を `src/test/resources/features/{機能名}/scenarios.md` として保存する。
   - **「修正指示」** → 指摘内容を反映して Step 2 を再実行する。

## Constraints (制約事項)
- **テストコード実装の除外:** 本Skillはシナリオの作成・定式化のみを担当し、JUnitやステップ定義コード（Kotlin）の実装は生成対象外とする。
- **独断による仕様補完の禁止:** rules.md に記載のない動作を推測で仕様化せず、必ず疑問点としてユーザーに確認すること。
- **1機能1ファイル:** 生成されるGherkinは 1機能 = 1 `scenarios.md` ファイルの原則を守ること。
- **入力の前提:** `src/test/resources/features/{機能名}/rules.md` が存在することを前提とする。存在しない場合は `/rule-example-extractor` の実行を案内して終了する。

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md` および `.claude/memories/gherkin-scenario-generator.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

2. **成果物の再生成に伴う自動蓄積（トリガールール）**:
   - ユーザーの指摘や修正指示によって、一度生成した成果物を作り直す場合、成果物を再生成する**前に**、自律的に `.claude/memories/gherkin-scenario-generator.md` へ物理的にファイル編集を行って追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ```
     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象機能**: {引数で受け取った対象機能名}
     - **指摘カテゴリ**: （例: 網羅性の不足、仕様の誤認識、表現の手続き化、フォーマット違反 など）
     - **指摘された内容**: （ユーザーからの具体的な修正指示）
     - **原因/理由**: （なぜその問題が発生したかの分析）
     - **今後の対策**: （次回生成時に守るべきルールの言語化）
     ```

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、成果物の再生成も終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、成果物を作り直しました」と必ず報告してください。
