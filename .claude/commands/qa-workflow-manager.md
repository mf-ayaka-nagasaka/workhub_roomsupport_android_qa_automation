# Skill: qa-workflow-manager
影響範囲の特定、テスト観点の作成、デシジョンテーブルの生成、QASE用CSVの出力まで、一連のQAプロセスをステップバイステップで実行し、各工程での人間によるレビューとGit管理を統合的に支援します。

## Usage
`/qa-workflow-manager [ver] [ticket_no] "[修正内容]"`
例: `/qa-workflow-manager 1.3.4 20842 "ログインボタンの位置を右端に変更し、未ログイン時のリダイレクト処理を修正"`

## Context / Scope
- **対象ファイル**: `v[ver]_[ticket_no].md`（修正内容）、`[プロジェクト名]_qa_automation/data/*.csv`（テストケース本体）
- **参照元ドキュメント**: `index.md`（機能一覧）、`docs/test_viewpoints/base/*.md`、`[Androidソースリポジトリ]/documents/qa_naming_definition.md`
- **テンプレート**: `./data/デシジョンテーブル_テンプレート(長坂用).xlsx`、`CSVテンプレート_QASE_workhubMobile用 - template_確認テスト (1).csv`
- **出力先（リリース差分）**: `docs/test_viewpoints/release/{ticket_no}/`
- **事前準備マスター**: ./data/preconditions_master.md

## Instructions
あなたはシニアQAエンジニアとして振る舞い、以下のQAワークフローを統括します。
【最重要ルール】：一度にすべての工程を実行しないでください。必ず1つのステップが完了するごとにレポートを出力し、人間のユーザーからレビュー（OKの合意）を得てから次のステップへ進んでください。

### Step 0: 準備（Git Operations）
`/sync-work-branch` スキルを実行し、mainブランチの同期を行ってください。
- 競合（コンフリクト）が発生した場合はユーザーに報告し、解決を待ってから進めてください。

### Step 1: 影響範囲だし (qa-impact-analyzer)
`/qa-impact-analyzer [ver] [ticket_no]` スキルを実行し、影響範囲の特定とテストケース抽出を行ってください。
- **【重要: Step 2への移行確認】** レポートの最後に必ず、ユーザーへ「Step 2へ進むにあたり、以下のどちらのパターンでテスト観点の作成・レビューを進めるか、番号で選択してください。① 人がテスト観点を作成 → Claude Codeがレビューする、② Claude Codeがテスト観点を作成 → 人がレビューする」とプロンプトを出し、入力を待機してください。

### Step 2: テスト観点だしとファイル生成 (qa-viewpoint-manager)
`/qa-viewpoint-manager` スキルを実行し、ユーザーがStep 1で選択したパターン（①または②）に応じてテスト観点の作成・レビューとmdファイル生成を行ってください。
- 保存後、次のステップへ進む許可をユーザーに求めます。

### Step 3: デシジョンテーブル作成 (qa-matrix-generator)
`/qa-matrix-generator [ticket_no]` スキルを実行し、Step 2で作成した観点からHTML形式のデシジョンテーブルを生成してください。
- 保存後、次のステップへ進む許可をユーザーに求めます。

### Step 4: QASE用CSVファイル作成 (qa-case-exporter)
`/qa-case-exporter [ticket_no]` スキルを実行し、Step 3のデシジョンテーブルからQASE用CSVを生成してください。

### Step 5: 完了処理（自動マージとPush）
- 全ての工程とファイルのコミット・タグ打ちが完了したことをユーザーに報告し、「作業用ブランチを `main` ブランチへマージし、リモートへプッシュしてもよろしいですか？」と承認を求めます。
- ユーザーから承認（OK）を得た後、**自律的に以下のGitコマンドを実行**して完了処理を行ってください。
  1. `git checkout main`
  2. `git merge [作業用ブランチ名]`
  3. `git push origin main` （およびタグのプッシュ `git push origin --tags`）
- 競合（コンフリクト）やエラーが発生した場合は直ちに処理を中断し、ユーザーに状況を報告して指示を仰いでください。
- 全ての処理が正常に完了したら、タスク完了を宣言してクローズします。

## Constraints (制約事項)
- **進行制御**: ユーザーの「OK」や「次へ進んで」という明確な合意なしに、勝手に次のStepへ進んだり、ファイルを保存・上書きしたりしないこと。
- **コンテキスト保護**: 巨大なCSVは直接開かず外部ツール（grep等）で処理すること。`base/` 内のファイルや既存のデータ構造を破壊しないこと。
- **フォーマット厳守**: 各Stepで要求されている出力形式（Notion用のインデント、セル記号ルール、CSVテンプレートの一文字一句違わぬカラム構成）を厳格に守ること。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。

     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象タスク**: （例: 影響範囲の抽出、テスト観点作成など）
     - **対象機能**: （例: ログイン画面、決済APIなど）

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、成果物の再生成も終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、成果物を作り直しました」と必ず報告してください。
