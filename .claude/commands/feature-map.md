# Skill: feature-map
Androidの全チケットと、アプリの画面・内部処理の対応を1枚にまとめた「全体マップ」を参照・更新します。Gherkinシナリオを作り始める前に**そのチケットでどこまでを見るのか（責務）を確定**し、確定した内容をマップへ書き戻すことで、チケットごとの責務の重複・抜けを防ぎます。「責務を決めたい」「どのチケットで見るのか」「他のチケットと重複していないか」「全体マップを更新して」のような依頼で使います。

## Usage
`/feature-map [モード] [対象チケット名]`

- `/feature-map scope [チケット名]` … 責務の確定（Gherkin着手前に実行する主モード）
- `/feature-map update [チケット名]` … 成果物の完成後にカバレッジ・状態を更新する
- `/feature-map show` … 現在の責務の決定状況・赤カードを一覧で提示する（更新しない）

例: `/feature-map scope 起動時に予約データを準備してホームを表示できる`
例: `/feature-map update PrepareHome`
例: `/feature-map show`

- モードが省略された場合は `scope` として扱う。
- チケット名が省略された場合は、何のチケットに着手するのかをユーザーにヒアリングしてから進む。

| ブロック | 内容 |
| :--- | :--- |

## モード: scope（責務の確定）

### Step 1: 現状の読み込みと、受け入れ条件の分解

1. `feature-map.html` の**決定台帳**と**チケット一覧**を読み、着手するチケットが既存の決定に触れていないかを確認する。
2. ユーザーから受け入れ条件（AC）を受け取る。提示がなければ提示を依頼する。
3. ACを**1項目1分岐まで分解**する。1つの箇条書きに複数の分岐が入っていることが多いため、必ず分解すること。
4. 分解した各項目について、**仕様書とソースでその処理がどの画面にあるかを確認**し、以下の3つに仕分ける。

```
## 受け入れ条件の分解と仕分け

### 対象チケット: {チケット名}

| AC | 分解した項目 | 実処理の場所 | 責務 | 判定 |
|---|---|---|---|---|
| ① | （1分岐まで分解した内容） | `{ViewModel/UseCase}:{行}` | {画面名} | 🟢対象 / 🔴対象外 / 🟡要判断 |
```

5. **【次Step移行確認】** 「この仕分けで合っていますか？Step 2（実装との突き合わせ）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 2: 実装との突き合わせ（ACに無い処理の洗い出し）

1. 対象画面のエントリポイント（`initialize()` 等）の処理を**先頭から順に列挙**し、各処理がどのACで担保されるかの対応表を作る。
2. **ACに書かれていない処理**（受け入れ条件は検証項目の宣言であって実装の網羅ではないため、必ず差分が出る）を洗い出し、観測可能性を添えて提示する。

```
## ACに書かれていない処理

| 処理 | 実装 | 観測できるか | 他チケットとの重複 | 所見 |
|---|---|---|---|---|
```

3. 観測できない処理・他チケットの責務である処理は**対象外**を推奨し、理由を添える。
4. **【次Step移行確認】** 「Step 3（論点の合意）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 3: 境界の論点の提示と合意

1. 既存チケットと境界が重なる項目を**論点**として提示する。推測で決めず、必ずユーザーの判断を仰ぐ。
2. 各論点には**ソース・仕様書の根拠を必ず添える**。根拠が示せないものは論点として立てず、赤カードにする。
3. ユーザーが決めきれない論点は**赤カード**として扱い、開発チームへの確認事項とする。
4. **【次Step移行確認】** 「合意内容を決定台帳へ記録してよろしいですか？」と確認し、合意を待つ。

### Step 4: 決定台帳への記録とマップの更新

1. 合意された内容を、決定台帳へ追記する（既存の最大番号の続きを採番）。

| 列 | 内容 |
| :--- | :--- |
| # | 連番 |
| 論点 | 「〜はどこで見るか」の形で書く |
| 関係チケット | 丸数字で列挙 |
| 決定 | 確定なら `p-done`、未確定・開発確認なら `p-open` のピル |
| 根拠 | ソースのファイル名・行、仕様書の節 |
| 決定日 | 確定したもののみ記載。赤カードは `—` |

2. フロー図に新しい画面・処理が必要な場合は、ノードを追加し**担当チケットを必ず記載**する。
3. 差分を提示して承認を得てから保存する。保存後に `git diff` で計画外の差分がないことを確認して報告する。
4. **【完了報告】** 確定した責務の範囲を一覧で提示し、「この範囲で `/bdd-workflow-manager {機能名}` に進めます」と案内する。

## モード: update（成果物の完成後）

1. チケット一覧の**状態**と**成果物**の欄を更新する。
2. カバレッジのルール数・シナリオ数を、実際の成果物から数えて更新する。
3. 着手中に判明した責務の決定があれば決定台帳へ追記する。
4. 差分を提示して承認を得てから保存する。

---

## モード: show

1. 決定台帳・赤カード・カバレッジを読み、現状を一覧で提示する。
2. **ファイルは一切更新しない。**

## 図の表示崩れを防ぐルール（最重要）

フロー図（SVG）を編集したら、**保存前に必ず次の7項目を検算し、結果を報告**してください。1件でも引っかかる場合は保存しないこと。

| # | 検証項目 | 基準 |
| :--- | :--- | :--- |
| 1 | 文字のあふれ | ボックス幅 ≧ 最長行の見積もり幅 + 余白22px。見積もりは**半角0.6em・それ以外1.0em** |
| 2 | ノード同士の重なり | 全組み合わせで矩形が交差しないこと |
| 3 | 矢印ラベルの重なり | ラベルの矩形がどのノードとも交差しないこと |
| 4 | レーン見出しの重なり | 見出しがノードとも線（矢印・バス）とも交差しないこと |
| 5 | 矢印の終端 | 接続先の矩形の**辺の4px手前**で終端すること。どの図形にも当たらない終端があれば未完成 |
| 6 | 矢印の最終区間の長さ | **20px以上**。短いと矢印の先端が潰れる |
| 7 | はみ出し | すべてのノードが viewBox の内側に収まること |

- **ボックス幅は手で決めず、文字幅から計算する**（幅 = max(最小幅, 必要幅 + 余白)）。
- **左端にはレーン見出し用の余白（ガター）を確保**し、ノードはその右から並べる。矢印の縦線が見出しを跨がないようにするため。
- **分岐先の手前は広めに空ける**（折れ曲がる矢印の助走距離を確保するため）。
- 検算は目視ではなくスクリプトで行い、検証結果を報告に含めること。

## Constraints (制約事項)
- **進行制御**: ユーザーの明確な合意なしに、次のStepへ進んだり、ファイルを保存・上書きしたりしないこと。
- **部分更新の厳守**: マップの全面再生成は禁止。該当ブロックの該当箇所のみを編集する。既存の決定・論点の文言や採番は変更しない。
- **根拠のない決定を書かない**: 決定台帳の根拠欄には、必ずソースのファイル名・行、または仕様書の節を書く。書けないものは決定にせず赤カードにする。
- **判定の所在はUIまで確認する**: 「どこで判定しているか」を決めるときは、遷移を実行するコード（`router.move` 等）だけでなく、**その操作に到達できるか（ボタン・導線が描画される条件）**まで確認する。先に弾いている画面があれば、そちらが主のゲートで、遷移先の判定は二重のガードとして区別して記述する。
- **認証モードの区別を明記する**: 本プロダクトは**予約認証モードのみが対象**。常時認証モード専用の画面・処理はマップに載せない。同じ役割の画面がモード別に複数ある場合は、ラベルにどちらのものかを必ず明記する。
- **参照元がiOSであることを前提にする**: 仕様書・ソースはiOS版。**呼称はAndroid版プロダクトの決定を常に優先**し、iOS版の用語定義との不一致を赤カードにしない。iOS版は分岐・処理順序・バリデーション条件など**振る舞いの裏取り**にのみ用いる。
- **独断による仕様補完の禁止**: 仕様書・ソースから確認できない動作を推測で書かず、「要確認」と明示するか赤カードにすること。
- **新規作成には使わない**: BDD成果物そのものの作成は `/bdd-workflow-manager`、修正は `/bdd-artifact-updater` を使う。本スキルは責務の確定とマップの保守に限る。

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md` および `.claude/memories/feature-map.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

2. **成果物の再生成に伴う自動蓄積（トリガールール）**:
   - ユーザーの指摘や修正指示によって、一度提示した仕分け・論点・図を作り直す場合、作り直す**前に**、自律的に `.claude/memories/feature-map.md` へ物理的にファイル編集を行って追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ```
     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象タスク**: （例: 受け入れ条件の分解、責務の仕分け、決定台帳への記録、フロー図の更新 など）
     - **対象チケット**: （対象のチケット名）
     - **指摘カテゴリ**: （例: 責務の取り違え、根拠の不足、図の表示崩れ、網羅性の不足 など）
     - **指摘された内容**: （ユーザーからの具体的な指摘）
     - **原因/理由**: （なぜその問題が発生したかの分析）
     - **今後の対策**: （次回実行時に守るべきルールの言語化）
     ```

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、成果物の作り直しも終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、作り直しました」と必ず報告してください。
