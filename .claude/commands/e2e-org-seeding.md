# Skill: e2e-org-seeding
E2E・手動テスト用の3組織へ、メンバーの投入とアクティベートを行います。CSV生成とアクティベートはスクリプトで自動化されていますが、**管理画面での取り込みと招待送信は人の操作が必要**です。本スキルはその全体を進行管理し、各工程の実行・検証・記録を担当します。

## Usage
`/e2e-org-seeding [status|csv|activate|verify] [--org <rsa1|rsa2|rsa3>] [--from <N>] [--to <N>]`

例: `/e2e-org-seeding status`
例: `/e2e-org-seeding csv --org rsa1 --from 1 --to 50`
例: `/e2e-org-seeding activate --org rsa2 --from 1 --to 200`

- `status`: 進捗ファイルを読み、どの組織のどこまでが完了しているかを提示します（**省略時はこれ**）
- `csv`: 一括登録用CSVを生成します
- `activate`: 招待メールを読み取り、アクティベートを実行します
- `verify`: `--dry-run` で到達状況だけを確認します（アクティベートは行いません）

### Step 1: CSVの生成

```
python tools\gen_member_csv.py --org <識別子> --count <件数> --start <開始連番> --out members_<識別子>_<範囲>.csv --send-invitation 0
```

- **`--send-invitation` は必ず `0`（未招待）です。** 理由はStep 2を参照してください。
- 組織2は `--chunk-size 200` で5分割します。1セットずつ完了を確認してから次へ進みます。

生成後、以下を検証して結果を提示します。

| 検証項目 | 期待値 |
|---|---|
| UTF-8 BOM付き / 改行はLFのみ | BOMあり・CRLFなし |
| データ行数 | 指定件数と一致 |
| `sendInvitationEmail` | 全行 `0` |
| カナ欄・`roleCode` | 全行空欄 |
| `code` に `#` を含まないこと | 含まない |

### Step 2: 管理画面での取り込み（**人の操作・ここで停止**）

ユーザーへ以下を依頼し、**処理を停止**してください。

1. 管理画面でCSVを取り込む
2. 一覧が指定件数ぶん **「未招待」** になることを確認する

> **`--send-invitation 0` を使う理由（2026-10-23 確定）**
> CSV取り込み時の自動送信は、空欄でも `1` でも**招待メールが届きません**。空欄と `1` は管理画面のJSで同じ分岐に入るため挙動も同じです。
> **届くことが確認できている経路は「1名ずつ手で追加」と「管理画面からの招待送信（一括可）」の2つだけ**です。そのため、取り込みと送信を分離します。

取り込みが「取り込み中」のまま長時間止まる事象が報告されています。**再現したら件数と所要時間を記録**してください。

---

### Step 3: 招待の送信（**人の操作・ここで停止**）

ユーザーへ、管理画面から対象メンバーを選択して**招待を送信**するよう依頼し、**処理を停止**してください。送信後、一覧が「招待中」へ変わります。

配信にはラグがあります。すぐ届かなくても失敗とは限りません。

---

### Step 3.5: 招待が実際に発行されたかの確認（**必須**）

ユーザーが「送った」と言っても、**メールが1通も発行されていないことがあります**。
配信ラグと区別がつかず、待ち続けて時間を失う原因になります。**必ずここで確認してください。**

```
python tools\check_invites.py --org <識別子>
```

招待メールの件名は `[workhub]<組織名>から招待が届いています` で、**件名に組織名が入ります**。
そのため「どの宛先タグが、どの組織から、何通受け取ったか」が一覧できます。

| 結果 | 意味 |
|---|---|
| 想定件数ぶん届いている | Step 4 へ進みます |
| **0通** | **配信ラグではありません。** 送信そのものが行われていない可能性が高いです。管理画面でメンバーが存在するか、ステータスが「未招待」のままでないかをユーザーに確認してもらってください |
| 組織名が想定と違う | 別の組織に対して取り込み・送信が行われています。組織の切り替えを挟んだ直後に起こりやすい取り違えです |

**`activate_members.py` を何度も流して切り分けようとしてはいけません。** 1回あたり数分かかります。
こちらは数秒で済みます。

## 既知の落とし穴

調査に時間を要した事項です。**同じ道を再び辿らないでください。**

### CSVフォーマット
- **カナ欄（`familyNameKana` / `firstNameKana`）は空にします。** 全角カタカナしか受け付けず、連番もアルファベットも弾かれます。連番は `code` と `email` が持つため、一意である必要はありません
- **`roleCode` は空にします。** 組織に登録済みのコードとしか照合されません
- **1列目に `#` を含む行は読み飛ばされます。** `code` に `#` を使ってはいけません
- 埋めるのは `code` / `familyNameJp` / `firstNameJp` / `email` / `memo` の**5つだけ**で通ります
- **`superUser` は `0`＝システム管理者、`1`＝一般ユーザー**（直感と逆）。空欄なら一般ユーザーです

### 招待メール
- 招待URLは `https://admin.develop-workhub.site/inviteMember?id=<UUID>`。**個人を識別するのはクエリのUUIDだけ**です
- **招待URLが `develop` 環境を指します。** 検証先はStagingなので `develop`→`staging` の書き換えが必要です（`fetch_invite_url.py` が環境変数 `INVITE_HOST_REPLACE` で実施。既定 `develop=staging`）。**メールテンプレートの環境出し分け不備であり、開発への報告候補**です
- **有効期限は約120時間（5日）**、起点は配信時刻。期限切れは再送信でリカバリ可能です
- Gmailの「フォルダサイズの制限」は**「制限しない」のままにします**。組織2では1,000通届くため、上限1,000件設定だと境界に当たります

### アクティベートAPI
**認証ヘッダは不要です。** ブラウザが既存セッションのトークンを付けていただけで、認可には使われていません。

```
GET  /workhubCore/v2/invitations/{id}        → {id, email, organizationName, alreadyRegistered, ...}
POST /workhubCore/v2/invitations/sign-up     → 204
     {"password": "<固定パスワード>", "invitationId": "{id}"}
```

`alreadyRegistered` がアクティベート済みかどうかを表します。これが冪等性の根拠です。

### 所要時間の実測値（2026-10-23）

| 対象 | 実測 |
|---|---|
| 1名（dry-run） | 8.30秒 |
| 5名（dry-run） | 10.61秒 |
| 50名（本番・アクティベート実行） | 158秒 |
| 50名（本番・全員スキップ） | **248秒** |

**支配項はIMAP検索です。** `POST` が1件も走らない「全員スキップ」のほうが遅かったことが根拠です。
少数のdry-runから出した「固定費7.7秒＋1名0.58秒」という見積もりは、**受信箱が大きいと当てはまりません**
（検索時間は受信箱の規模と、その時点の負荷で変動します）。

詳細と対策は次項「受信箱の規模とIMAP検索のコスト」を参照してください。

### 受信箱の規模とIMAP検索のコスト（2026-10-23 判明）

**受信箱には36万通以上あります。** この受信箱はQA全体の共用で、別システムの通知が常時流れ込みます。

`activate_members.py` の `collect_invites` は**宛先ごとにIMAP検索を1往復**投げるため、
**1件あたり約2秒**かかります。実測では50名で107〜248秒。`--parallel` はAPI往復にしか効かず、
**この検索には効きません。**

> **以前「`collect_invites` の書き換えは不要」と判断していましたが、撤回しました。**
> あれは受信箱の規模を知らずに、dry-runの増分（0.58秒）だけで出した結論です。

**→ 2026-10-23 に書き換え済みです。** 既定は `--search-mode bulk`（件名で一度に検索）。

| 方式 | 50名での実測 |
|---|---|
| `per-address`（旧・宛先ごとに検索） | 258秒 |
| `bulk`（新・件名で一度に検索） | **38秒** |

結果が一致することは組織3の50名で確認済みです。旧方式は `--search-mode per-address` として
残してあり、結果を突き合わせたいときに使えます。

**仕組み**: 招待メールの件名は `[workhub]<組織名>から招待が届いています` で ASCII の
`workhub` を含むため、`SINCE <日付> SUBJECT "workhub"` で一度に引けます。本文は200通ずつ
まとめて取得するので、IMAPの往復は件数に比例しません。

- 検索の起点は既定で**7日前**（招待の有効期限が約120時間のため）。`--since` で変更できます
- **非ASCIIの件名で検索すると `imaplib` が落ちます。** 必ず `workhub` で引いてください
- 窓の中の通数に比例して本文取得の時間が増えます。組織2では約1,100通＝**2分前後**の見込みです
