# Skill: bdd-artifact-updater
`/bdd-workflow-manager` で作成済みのBDDテスト設計成果物に対し、リファインメント後に発生した修正・追加を反映します。影響範囲を分析したうえで、必要な成果物の該当箇所だけを部分更新し、修正点以外の既存記述は一切変更しません。

## Usage
`/bdd-artifact-updater [対象機能名] [修正内容]`

例: `/bdd-artifact-updater setting_loader 端末識別情報が取得できない場合はリトライせず即エラー画面に遷移する仕様に変わった`
例: `/bdd-artifact-updater login 生体認証のロック解除にリトライ回数の上限（3回）が追加された`

- `[修正内容]` は省略可能。省略された場合は、何をどう修正するのかをユーザーにヒアリングしてから Step 1 に進むこと。

## Context / Scope
- **入力（起点）**: ユーザーから伝えられた修正内容（リファインメントでの決定事項・仕様変更・指摘）
- **補助入力**: `C:\Users\mforce0087\workhubRoomSupport` 配下の対象機能仕様書（.md）※修正内容の裏取りに使用
- **関連メモリー**: `.claude/memories/bdd-artifact-updater.md`、`.claude/memories/bdd-workflow-manager.md`、`.claude/memories/global.md`
- **スキル一覧**: `.claude/commands/README.md`
- **テンプレート**: `src/test/resources/features/_templates/pbi-flow-map-template.html`
- **更新対象（既存成果物）**:
  - `src/test/resources/features/{機能名}/rules.md`（ルール・実例）
  - `src/test/resources/features/{機能名}/scenarios.md`（Gherkinシナリオ）
  - `src/test/resources/features/{機能名}/viewpoints.tsv`（機能別観点マスター）
  - `src/test/resources/features/{機能名}/scenarios_with_viewpoints.md`（観点分岐版Gherkin）
  - `src/test/resources/features/{機能名}/{機能名}.html`（処理の全体図）
  - `src/test/resources/features/_master/viewpoints.tsv`（観点マスター総合版）

## Instructions
あなたはAndroidアプリのQA・BDDテスト設計パートナーとして振る舞い、既存成果物の修正ワークフローを統括します。
【最重要ルール】：一度にすべての工程を実行しないでください。必ず1つのステップが完了するごとにレポートを出力し、人間のユーザーからレビュー（OKの合意）を得てから次のステップへ進んでください。
【最重要ルール】：本スキルは「部分更新」のスキルです。成果物の全面再生成は行いません。修正対象として合意された箇所以外は、文言・順序・ID・書式を含めて一切変更しないでください。

### Step 0: 修正要求の受付と現状把握

1. `src/test/resources/features/{機能名}/` 配下の既存成果物をすべて読み込む。
   - ディレクトリまたは成果物が存在しない場合は、「本スキルは既存成果物の修正用です。新規作成は `/bdd-workflow-manager {機能名}` を実行してください」と案内して停止する。
2. 作業前に `git status` を確認し、対象ファイルに未コミットの変更がある場合はユーザーに報告して、続行してよいか確認する。
3. 受け取った修正内容を「修正要求」として構造化し、以下の形式で提示する。

```
## 修正要求の確認

### 対象機能: {機能名}

| # | 修正要求 | 種別 | 根拠 |
|---|---------|------|------|
| 1 | （修正内容を1項目ずつ分解して記載） | 変更／追加／削除 | （リファインメントでの決定事項／仕様書の記載 など） |

### 確認したい点（赤カード）
- （修正内容から一意に判断できない点を列挙。なければ「なし」）
```

4. 仕様書（.md）に該当記載がある場合は参照して裏取りし、修正内容と仕様書の記述が食い違う場合は必ず赤カードとして提示する。
5. **【次Step移行確認】** 「上記の理解で合っていますか？Step 1（影響分析）に進んでよろしいですか？」とユーザーに確認し、合意を待つ。赤カードが残っている間は次へ進まない。

### Step 1: 影響分析（更新計画の提示）

1. 合意された修正要求ごとに、`rules.md` → `scenarios.md` → `viewpoints.tsv` / `scenarios_with_viewpoints.md` → `{機能名}.html` → `_master/viewpoints.tsv` の順で影響を判定する。
2. 各成果物について「どの箇所を」「どう変えるか（追加／変更／削除）」を、既存のルール番号・シナリオ名・観点IDなど**実在する識別子を引用して**特定する。
3. 以下の形式で更新計画を提示する。

```
## 影響分析結果

| 成果物 | 影響 | 更新箇所 | 変更内容の要約 |
|-------|------|---------|--------------|
| rules.md | あり | ルール③ | リトライ条件を削除し、即エラー遷移に変更 |
| scenarios.md | あり | シナリオ「〜」 | Then の期待結果を変更／新規シナリオ1件追加 |
| viewpoints.tsv | なし | - | 既存観点で充足 |
| scenarios_with_viewpoints.md | あり | 〜 | 〜 |
| {機能名}.html | あり | 裏側の処理 段 | 〜 |
| _master/viewpoints.tsv | なし | - | 新規観点なし |

### 影響なしと判断した理由
- （「影響なし」とした成果物について、なぜ更新不要かを1行ずつ明記）
```

4. **【次Step移行確認】** 「この更新計画で進めてよろしいですか？」とユーザーに確認し、合意を待つ。
   - 以降のStepは、ここで「影響あり」と合意された成果物のみを対象とする。「影響なし」とした成果物は**開かない・触らない**。

### Step 2: rules.md の部分更新

1. `/rule-example-extractor` のルール・実例の記述ルールに従い、該当箇所の修正後テキストを作成する。
2. **差分形式**（変更前／変更後の対比）でユーザーにプレビュー提示する。
3. 承認を得たら、該当箇所のみを置換して保存する。
4. 保存後に `git diff src/test/resources/features/{機能名}/rules.md` を実行し、計画外の差分が出ていないことを確認してユーザーに報告する。
5. **【次Step移行確認】** 「Step 3（scenarios.md の更新）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 3: scenarios.md の部分更新

1. `/gherkin-scenario-generator` のBDDガイドライン・テスト設計ルール・ガードレールに従い、該当シナリオの修正後テキストを作成する。
2. シナリオを**追加**する場合は、既存シナリオの並び・命名規則・記述粒度に合わせて挿入位置を決め、その位置をユーザーに提示する。
3. シナリオを**削除**する場合は、削除対象と削除理由を明示し、個別に承認を得る（まとめて承認を取らない）。
4. 差分形式でプレビュー提示し、承認を得たら該当箇所のみを置換して保存する。
5. 保存後に `git diff` で計画外の差分がないことを確認して報告する。
6. **【次Step移行確認】** 「Step 4（観点・観点分岐Gherkin の更新）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 4: 観点マスター・観点分岐Gherkin の部分更新

1. `/viewpoint-extractor` のルールに従い、修正によって以下が発生するかを判定する。
   - 既存観点の記述変更
   - 新規観点の追加（`_master/viewpoints.tsv` との照合を必ず実施し、既存観点で表現できる場合は新規追加しない）
   - 観点分岐版Gherkinの分岐変更
2. 以下を差分形式でプレビュー提示する。
   - `viewpoints.tsv` の変更行（Markdownテーブル形式で可読化して提示）
   - `scenarios_with_viewpoints.md` の変更箇所
   - `_master/viewpoints.tsv` への追加行（追加がある場合のみ）
3. 承認を得たら、該当行・該当箇所のみを更新して保存する。
   - `_master/viewpoints.tsv` は**追記・該当行の更新のみ**とし、他機能の行は絶対に並び替え・削除・再整形しない。
4. 保存後に `git diff` で計画外の差分がないことを確認して報告する。
5. **【次Step移行確認】** 「Step 5（処理の全体図の更新）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 5: 処理の全体図（HTML）の部分更新

1. `/pbi-flow-map` のルールとテンプレートの構造を踏襲し、該当箇所（流れ図のノード／テストケース対応表／エラー文言の逆引き表）のみを更新する。
2. HTMLは**全面再生成しない**。既存HTMLの該当要素のみを編集し、CSS・スクリプト・レイアウト構造には手を入れない。
3. 更新結果（スクリーンショットまたは変更箇所の抜粋）をユーザーに提示する。
4. 推測した点があれば質問で潰す。
5. 承認を得たら保存し、`git diff` で計画外の差分がないことを確認して報告する。
6. **【次Step移行確認】** 「Step 6（完了処理・コミット）に進んでよろしいですか？」と確認し、合意を待つ。

### Step 6: 完了処理（コミット）

1. 修正内容を一覧でユーザーに報告する：

```
## BDD成果物 修正完了レポート

### 対象機能: {機能名}

### 修正要求
| # | 修正要求 | 反映先 |
|---|---------|-------|
| 1 | 〜 | rules.md ルール③ / scenarios.md シナリオ「〜」 |

### 更新した成果物
| # | ファイル | 変更行数 | 変更内容 |
|---|---------|---------|---------|
| 1 | `features/{機能名}/rules.md` | +3 / -2 | 〜 |

### 更新しなかった成果物
| ファイル | 理由 |
|---------|------|
| `features/{機能名}/viewpoints.tsv` | 既存観点で充足のため |
```

2. 「上記の修正をコミットしてよろしいですか？」とユーザーに承認を求める。
3. 承認を得たら、更新したファイルのみを `git add` → `git commit` する。コミットメッセージは以下の形式：
   - `test: {機能名} BDDテスト設計成果物を修正`
   - 修正要求の要約をコミット本文に箇条書きで記載する。

## Constraints (制約事項)
- **進行制御**: ユーザーの「OK」や「次へ進んで」という明確な合意なしに、勝手に次のStepへ進んだり、ファイルを保存・上書きしたりしないこと。
- **部分更新の厳守（最重要）**: 成果物の全面書き換え（ファイル全体の再生成・上書き保存）は禁止。必ず該当箇所のみを置換する編集を行うこと。
- **既存記述の保全**: 修正対象外の記述について、文言の言い換え・表記ゆれの統一・並び順の変更・採番のふり直し・インデントや空行の整形を、たとえ改善目的であっても行わないこと。気づいた改善点は**提案のみ**に留め、別途承認を得てから対応する。
- **識別子の維持**: 既存のルール番号・シナリオ名・観点IDは変更しない。追加時は既存の最大値の続きを採番する。
- **差分の自己検証**: 各Stepでの保存後は必ず `git diff` を確認し、合意した更新計画に含まれない差分が出ていないかを検証すること。計画外の差分を検出した場合は、ユーザーに報告して元に戻すこと。
- **影響なしの成果物には触れない**: Step 1 で「影響なし」と合意した成果物は、編集はもちろん保存操作も行わないこと。
- **各スキルのルール遵守**: 各Stepでは対応するスキル（rule-example-extractor / gherkin-scenario-generator / viewpoint-extractor / pbi-flow-map）に定義されたガードレール・制約事項をすべて遵守すること。
- **スキル定義の参照**: 各Stepの実行時には、対応するスキル定義ファイル（`.claude/commands/{スキル名}.md`）を必ず読み込み、最新のルールに従うこと。
- **独断による仕様補完の禁止**: 仕様書に記載のない動作、およびリファインメントで決まっていない動作を推測で仕様化せず、必ず疑問点（赤カード）としてユーザーに確認すること。
- **新規作成には使わない**: 成果物が未作成の機能に対しては本スキルを使わず、`/bdd-workflow-manager` へ誘導すること。

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md`、`.claude/memories/bdd-artifact-updater.md`、`.claude/memories/bdd-workflow-manager.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

2. **成果物の再生成に伴う自動蓄積（トリガールール）**:
   - ユーザーの指摘や修正指示によって、一度提示した修正案を作り直す場合、修正案を再作成する**前に**、自律的に `.claude/memories/bdd-artifact-updater.md` へ物理的にファイル編集を行って追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ```
     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象タスク**: （例: 影響分析、rules.md更新、scenarios.md更新、観点更新、全体図更新 など）
     - **対象機能**: {引数で受け取った対象機能名}
     - **指摘カテゴリ**: （例: 影響範囲の見落とし、修正点以外の改変、仕様の誤認識、具体性の不足、フォーマット違反 など）
     - **指摘された内容**: （ユーザーからの具体的な修正指示）
     - **原因/理由**: （なぜその問題が発生したかの分析）
     - **今後の対策**: （次回実行時に守るべきルールの言語化）
     ```

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、修正案の作り直しも終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、修正案を作り直しました」と必ず報告してください。
