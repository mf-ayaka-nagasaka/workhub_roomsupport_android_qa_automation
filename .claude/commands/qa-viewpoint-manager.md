# Skill: qa-viewpoint-manager

テスト観点の作成・レビュー、標準フォーマットでのmdファイル生成、およびGitタグによる管理を支援します。

## Usage

`/qa-viewpoint-manager`

## Context / Scope

- **参照元（インプットの3本柱）**:
  1. **仕様書**: `C:\Users\mforce0087\[Androidソースリポジトリ]\documents\RoomSupport` 配下のファイル（画面単位の仕様・振る舞い。別リポジトリ、マルチルートワークスペース前提）
  2. **命名定義**: `docs/qa_naming_definition.md`（用語・命名ルール）
  3. **ドメイン観点**: `docs/test_viewpoints/base/domain/` 配下のファイル（OS, 端末, 権限などプロダクト特有の要素）
- **出力先（リリース差分）**: `docs/test_viewpoints/release/{TicketNo}/`

## Instructions

### 0. 実行モードの確認と選択

コマンドが実行されたら、まず最初に以下のメッセージを表示し、ユーザーにどちらのパターンで進行するか選択させてください。

どちらのパターンでテスト観点の作成・レビューを進めますか？番号を入力してください。
① 人がテスト観点を作成 → Claude Codeがレビューする
② Claude Codeがテスト観点を作成 → 人がレビューする

ユーザーからの回答を待ってから、選択されたパターン（1-A または 1-B）に進んでください。

### 1-A. パターン①（人が作成 → Claudeがレビュー）の場合

- **情報の入力受付**: ユーザーに対し、「修正内容」「テスト観点ドラフト」「対象AppVer」「チケットNo」を入力（貼り付け）するよう案内してください。
- **分析**: 入力を受け取ったら、`git diff` や、仕様書（別リポジトリ）、命名定義、ドメイン観点（`base/domain/`）を横断して参照し、影響範囲を分析します。
- **レビューレポートの出力**: 以下の形式でレポートを出力し、人間へフィードバックを求めます。
  - 修正内容の解釈: AIが理解した変更要約
  - 評価スコア: 網羅性・整合性を5段階評価
  - 具体的な指摘: 不足している観点、修正が必要な表現、懸念点
  - 追加提案: AI側で生成した「追加すべき観点」の具体案

人間からのレビュー承認が得られたら、「2. mdファイル生成（共通）」へ進んでください。

### 1-B. パターン②（Claudeが作成 → 人がレビュー）の場合

- **情報の入力受付**: ユーザーに対し、「修正内容」「対象AppVer」「チケットNo」を入力するよう案内してください。テキストだけでなく、チケットのスクリーンショット（画像）も受け付けます。（※このモードではテスト観点ドラフトの入力は求めません）

#### 1-B-1. 改修点の特定（起点の明確化）
- 画像が提供された場合は、Read ツールで画像ファイルを読み取り、チケットの内容（修正内容、期待値、再現手順、背景、AppVer、チケットNo等）を抽出する。
- チケットから「何が変わったか/何を直すか」を1〜3行で要約し、起点機能（改修点）を特定する。
- 改修が複数ある場合は、改修点を箇条書きで分ける（最大3つ程度に整理）。それぞれに対して観点を作る。

#### 1-B-2. 関連機能の洗い出し（水平・垂直・連携）
改修点を起点に、仕様書（別リポジトリ）、ドメイン観点（`base/domain/`）、および `git diff` を参照しながら「絡む機能」を列挙する。
出力は **必須（今回見る）** / **周辺（デグレ候補）** / **除外（理由付き）** に分類する。

- **垂直（フロー前後）**: ユーザーの一連の流れ（前工程→当該工程→後工程）を切り出し、前後の機能を列挙する。
- **水平（類似機能・同カテゴリ）**: 同種の画面/設定/導線/モード/権限制御など、似た構造の機能を列挙する。
- **連携（他プロダクト・他画面・外部）**: workhub-web / 管理画面 / 他端末 / 外部連携（カレンダー等） / 通知先 / ログ基盤 など、結果が波及する先を列挙する。「データ反映」や「整合性」が絡む場合は、どこに反映されるべきか（確認箇所）まで明示する。

#### 1-B-3. QA検証観点の作成
以下のフォーマットで、チケット本文に貼れる「QA検証観点」を作成する。

```markdown
# {修正タイトル} テスト観点

**チケットNo**: {TicketNo}
**対象AppVer**: {AppVer}
**修正内容**: {1〜3行の要約}

---

## ゴール
- …

## 前提
- …

## 観点1: {観点タイトル}
{何を確認するか（期待値を含む）}

### 要素
- {分岐条件1}
    - パターンA
    - パターンB
- {分岐条件2}
    - パターンA
    - パターンB

## 観点2: {観点タイトル}
…

## デグレ
- …

## ユースケース
- …

## エラー系（異常系）
- …
```

#### 1-B-4. 観点の作り方（ルール）

**要素の定義:**
- 要素＝分岐条件（バリエーション）として扱う。
- 2パターン以上あって掛け合わせ・網羅をしたいものだけを「要素」に書く。
- 1パターンしかない固定条件は、要素に書かず **前提** または **観点文の中** に含める。

**観点の粒度:**
- 観点は「何を確認するか」が一文で読める形にする（期待値を含める）。
- 観点が複数の確認先（例：端末画面＋workhub-webのデータ）を持つ場合は、観点文に「確認箇所」を含めるか、要素とは別に箇条書きで明示する。

**観点の順序:**
1. まず「改修点そのもの（直接影響）」の観点を先に置く
2. 次に「関連機能（水平・垂直・連携）」へ広げる
3. 最後に「デグレ」「ユースケース」「エラー系」を置く

**OS/端末別の扱い:**
- OS/端末別は常に必須にしない。
- 次のように「OS/端末差分が疑われる根拠」がある場合のみ要素として追加する：
    - 特定OSのみ再現/非再現
    - カメラ/画面回転/省電力/バックグラウンド/権限ダイアログなど端末依存が主因候補
    - OSアップデート後から発生

#### 1-B-5. レビューレポートの出力
- 観点の後に以下の形式でレポートを出力し、ユーザーへフィードバックを求める。
  - **修正内容の解釈**: AIが理解した変更要約
  - **関連機能の分類**: 必須 / 周辺 / 除外
  - **評価スコア**: 網羅性・整合性を5段階評価
  - **確認したい不足情報（最大3点）**: 不明点があっても仮置きで完成させた上で列挙

- 修正指示があれば対応し、最終的な承認が得られたら「2. mdファイル生成（共通）」へ進んでください。

### 2. mdファイル生成（共通：人間合意後）

パターン①または②で最終的なテスト観点について人間の合意が得られたら、以下のルールでファイルを保存してください。

- **ファイル名**: `docs/test_viewpoints/release/{TicketNo}/{AppVer}_{TicketNo}.md`
- **内容**: 確定した最終的なテスト観点

### 3. バージョン管理（Git Operations）

ファイル保存後、以下の操作を自動（または提案）してください。

- `git add` および `git commit -m "qa: update test viewpoints for v{AppVer} ({TicketNo})"`
- `git tag -af v{AppVer} -m "Latest QA artifacts for version {AppVer}"`
- 既存のタグがある場合でも `-f` (force) オプションで強制更新し、常に最新コミットを指すようにします。

## Constraints

- 指摘は建設的なトーンで行うこと。
- 参照元（仕様書、命名定義、ドメイン観点）のファイルは読み取り専用とし、直接書き換えないこと。
- 最終的なファイル生成とTag打ちは、必ずユーザーの合意を得てから実行すること。
- チケットにすでに期待値表や観点メモがある場合はそれを尊重し、矛盾がある場合は矛盾点を短く指摘し、より安全な書き方に整える。
- 用語はチケット本文の言い回しに合わせる。コード内部の変数名は使わず、製品UIの用語で記述すること。
- 不明点があっても、まずは仮置きで観点を完成させる。
- AI向けメタ説明は出力しない。開発も読むチケット本文に貼れる粒度・表現にする。

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md` および `.claude/memories/qa-viewpoint-manager.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

2. **成果物の再生成に伴う自動蓄積（トリガールール）**:
   - ユーザーの指摘や修正指示によって、一度生成した成果物を作り直す場合、それは「初期出力に考慮漏れやルールの不一致があった」ことを意味します。
   - 成果物を再生成する**前に**、自律的に `.claude/memories/qa-viewpoint-manager.md` へ物理的にファイル編集を行って追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象タスク**: （例: 影響範囲の抽出、テスト観点作成など）
     - **対象機能**: （例: ログイン画面、決済APIなど）
     - **指摘カテゴリ**: （例: 網羅性の不足、仕様の誤認識、具体性の不足、フォーマット違反 など）
     - **指摘された内容**: （例: 重点確認ケースに「ログイン周り」が抜けている）
     - **原因/理由**: （例: 依存関係の読み込みが甘かったため）
     - **今後の対策**: （例: 認証が絡む変更の際は必ずログインケースを強制抽出する）

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、成果物の再生成も終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、成果物を作り直しました」と必ず報告してください。
