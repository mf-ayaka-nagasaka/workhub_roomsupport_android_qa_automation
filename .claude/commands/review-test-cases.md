# Skill: review-test-cases
ガイドラインと参照ドキュメントを照合し、指定された機能グループのテストケースの品質レビュー・断捨離（不要ケース削除）・修正提案を行います。

## Usage
`/review-test-cases [csv_path] [target_suite]`
例: `/review-test-cases data/testcases/ROOM_02_labeled.csv 認証・解錠・セキュリティ`

- **仕様書（正当性検証）**: `[Androidソースリポジトリ]\documents\` 配下の最新仕様書（読み取り専用）
- **事前準備マスター（前提条件検証）**: `C:\Users\mforce0087\workhub_roomsupport_android_qa_automation\data\preconditions_master.md`

## Instructions
あなたはシニアQAエンジニアとして、既存テストケースの品質レビュー・断捨離・修正提案を行ってください。
【最重要ルール】：Phase 1（レビュー・提案出力）とPhase 2（承認後の実行）を分離し、ユーザーの明確な承認なしにCSVファイルを更新しないでください。

### Phase 1: レビュー・断捨離＆改善提案の出力

#### 1-1. 対象ケースの抽出
- 引数 `csv_path` から `target_suite` に該当するテストケースを抽出します。
- 巨大なCSVは直接開かず、`grep -E` 等のシェルコマンドを使用してフィルタリングしてください（コンテキスト保護）。
- 抽出されたケース数をまず報告してください。

#### 1-2. Step 1 — マクロレビュー（構造分析・過不足判定）

**目的**: 個別ケースの品質を見る前に、機能グループ全体の「テスト構造」が妥当かを判定する。

以下のドキュメントを読み込み、**ケース群の全体構造**を分析してください。
- 仕様書（`仕様書配下`の関連ドキュメント）
- `機能一覧.csv`（機能カバレッジの基準）
- `qa_priority_guidelines.md`（重要度の基準）

**分析の観点:**

1. **構造的冗長パターンの検出（過剰の削り）**:
   - **パラメータ展開の過剰**: 同一のアプリロジックを、1パラメータの違いだけで全パターン横展開しているケース群を特定する（例: 全曜日・全権限・全ユーザー種別）。代表ケースへの集約を検討する。
   - **並行構造の冗長**: 異なるハードウェアや設定値で同一のアプリ挙動をテストしている並行ケース群を特定する（例: 3DAS/2DASで同一UI応答をテスト）。CLAUDE.mdのスコープ定義（「アプリがSDKの結果を正しくハンドリングできているか」）に照らし、アプリ挙動が同一なら代表1件＋差分ケースに集約を検討する。
   - **条件変化が結果に影響しないケース**: 前提条件を変えても期待値が常に同一になるケース群を特定する（例: 予約認証モードでは全時間条件で「解錠可」）。結果が変わらないなら代表1件で十分。

2. **仕様に対する不足（抜け漏れ）の検出**:
   - 仕様書・`機能一覧.csv` と既存ケースを照合し、テストされていない機能・観点・シナリオを特定する。
   - 不足が見つかった場合は、追加すべきケースの概要を提案する。

3. **旧仕様ケースの検出**:
   - 仕様変更で廃止された画面・パラメータ・フローに基づくケースを特定する。

#### 1-3. Step 2 — ミクロレビュー（個別ケース精査）

**目的**: Step 1を通過した（削除対象でない）ケースに対して、1件ずつの品質を精査する。

専用の参照ドキュメントが存在しない項目については、既存ケースの文脈・`qa_priority_guidelines.md`・一般的なQAベストプラクティスに基づいて推測レビューを行ってください。

1. **ガイドライン照合**:
   - `qa_priority_guidelines.md` を読み込み、各ケースの Priority（P1/P2/P3）と Severity が不具合重要度の定義と整合しているか検証する。
   - 不整合がある場合は、正しい Priority/Severity を提案する。

2. **前提条件の完全性チェック**:
   - `preconditions_master.md` を参照し、テストケースの前提条件が十分に記載されているか検証する。
   - 隠れた前提（Bluetooth接続状態、特定の扉設定等）の欠落を指摘する。

3. **再現性・明確性チェック**:
   - 操作手順が第三者でも再現可能な具体性を持っているか検証する。
   - 期待値が「正常に動作すること」等の曖昧な表現になっていないか検証する。
   - UI文言が開発内部用語ではなく画面上の表示文言に揃っているか検証する（`qa_naming_definition.md` 参照）。

各ケースに対して以下の判定ラベルを付与する:
- **PASS**: 問題なし
- **EDIT**: 修正が必要（前提条件・手順・期待値・Priorityのいずれか）
- **DELETE**: Step 1で削除対象と判定済み

> - **はい**: 全件適用
> - **一部のみ**: 適用するケース番号を指定してください（例: 削除#1,#3 / 修正#2 / 追加#1）
> - **いいえ**: 更新をキャンセル

### Phase 2: 承認後の実行

ユーザーから承認（「はい」「OK」等）を受け取った後、以下を実行してください。

#### 2-1. 削除の実行
- 削除提案で承認されたケースの行をCSVから除去する。
- 削除した行を `data/logs/ROOM_removed_cases_log.csv` に追記保存する（バックアップ）。
  - ログファイルが存在しない場合は、元CSVと同じヘッダー行＋ `removed_date` と `removed_reason` カラムを追加して新規作成する。
  - ログファイルが既に存在する場合は、ヘッダーを重複させずに行のみを追記する。

#### 2-2. 修正の実行
- 修正提案で承認されたケースについて、タイトル・前提条件・操作手順・期待値・Priority等を更新する。

#### 2-3. 追加の実行
- 追加提案で承認されたケースについて、CSVの末尾に新規行を追加する。
- 新規ケースのフォーマット（カラム構成）は既存ケースに準拠する。`v2.id` は空欄とし、QASEインポート時に自動採番させる。

#### 2-4. ファイル保存
- 更新後のCSVを `csv_path` にUTF-8（BOMなし）で上書き保存する。
- 保存後、変更サマリー（削除{n}件、修正{n}件、追加{n}件）を報告する。

#### 2-5. バージョン管理（Git Operations）
- ファイル保存後、以下の操作を実行してください。
  - `git add {csv_path} data/logs/ROOM_removed_cases_log.csv`
  - `git commit -m "qa: review and clean up test cases ({target_suite})"`

## Constraints (制約事項)
- **進行制御**: ユーザーの明確な承認なしに、CSVファイルを更新・上書きしないこと。
- **コンテキスト保護**: 巨大なCSVは直接開かず外部ツール（grep等）で処理すること。
- **参照元の保護**: 仕様書（別リポジトリ）、`base/` 内のファイル、ガイドライン文書は読み取り専用とし、直接書き換えないこと。
- **バックアップ必須**: 削除するケースは必ず `data/logs/ROOM_removed_cases_log.csv` にログとして残すこと。
- **推測レビューの明示**: 専用の参照ドキュメントが存在せず推測でレビューした項目については、レポート内で「※推測に基づくレビュー」と明記すること。
