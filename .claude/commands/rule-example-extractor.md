# Skill: rule-example-extractor
仕様書（Markdown）からビジネスルール・実例（正常系・異常系・例外系）を抽出・整理し、テスト設計の基盤となるルール・実例ドキュメント（rules.md）を生成するSkillです。

## Usage
`/rule-example-extractor [対象機能名または仕様書パス]`

例: `/rule-example-extractor reservation`
例: `/rule-example-extractor "C:\Users\mforce0087\workhubRoomSupport\docs\spec\reservation.md"`

## Context / Scope
- **参照元仕様書リポジトリ**: `C:\Users\mforce0087\workhubRoomSupport` 配下の Markdown (.md) ファイル（現状はiOS版仕様書。将来的にAndroid版の対象プロダクト仕様書に切替予定）
- **関連メモリー**: `.claude/memories/rule-example-extractor.md`、`.claude/memories/global.md`
- **スキル一覧**: `.claude/commands/README.md`
- **成果物出力先**: `src/test/resources/features/{機能名}/rules.md`
- **フォルダ名**: 仕様書に合わせた機能名を使用する

## Instructions
あなたはAndroidアプリのQA・テスト設計パートナーとして振る舞います。
【最重要ルール】: テスト設計ルールを最優先とし、仕様書のUI挙動をビジネスルール単位で抽出・整理してください。

### Step 1: 仕様書の読み込みと分析 (Investigate)

> **【必読】このStepを開始する前に、以下のファイルを必ず読み込んでから作業を開始すること：**
> - `C:\Users\mforce0087\workhubRoomSupport` 内の対象となる機能仕様書 (.md)
> - `.claude/memories/rule-example-extractor.md`（存在する場合、過去の指摘事項）
> - `.claude/memories/global.md`

1. 指定された対象機能またはファイルパスから、対応する仕様書（.md）の内容を読み込む。
2. 仕様書から以下の要素を抽出・分析する：
   - 機能の目的および背景
   - 包含されるビジネスルール
   - 正常系・異常系・境界値のシナリオ要素
   - 仕様書から読み取れない曖昧な点・未定義の例外ケース（「赤カード」疑問点）

> **【参照スコープの制限】**
> 仕様書の操作イベント（セクション3等）に【UI挙動】と【内部処理】が分離して記載されている場合、ルール抽出の対象は **【UI挙動】のみ** とする。
> 【内部処理】（Keychain操作、トークン保存、ポーリングタスク、リポジトリ呼び出し等）はルールの根拠として参照してよいが、それ自体を独立したルールにしてはならない。
> 判定基準: 「そのルールの前提条件・操作・期待結果がすべてユーザーの画面操作と画面表示だけで記述できるか？」— Noならルール化対象外。

### Step 2: ルール・実例の整理 (Generate)

抽出した内容を基に、ルール・実例ドキュメントを作成する。

#### ガードレール（作成時の適用ルール）：

##### 実例の分類定義
各ルールの実例（データ・状況の組み合わせ）は、以下の3分類で振り分けること。
- **🟢 正常系**: ユーザーの正しい操作に対する振る舞い（キャンセルなどの仕様上想定された代替フローも含む）
- **🔴 異常系**: ユーザーの誤操作や無効な入力に対する振る舞い
- **🟡 例外系**: ユーザーの誤操作ではなく、システムの状態や外部要因（タイムアウト、実ハード起因など）によって発生するエラーケース

##### ルール粒度の定義（最重要）
- ❌ **禁止**: 画面のルーティング、1トーストメッセージごとの処理分岐、内部バリデーションの個別ステップを1ルールにしない。
- ❌ **禁止**: ユーザーが画面上で観測できない内部実装の振る舞い（トークン保存、Keychainポーリング、バックグラウンドタスクの起動・停止、リポジトリ層の呼び出し等）を独立したルールにしない。
- ⭕ **必須**: 「**誰が**（属性・権限）」「**どのような状態で**」「**何を達成できるか／拒否されるか**」というビジネスルール単位でまとめる。ルールの前提条件・操作・期待結果はすべて**ユーザーの画面操作と画面表示**で記述できるものに限る。
- 1つのルールには、そのルールを検証するための正常系・異常系の実例（データ・状況の組み合わせ）を複数行で列挙する。

##### テスト階層（ピラミッド）自動割り振りルール
仕様書から抽出したルールに対し、以下の判定マトリクスに従って最適な「テスト階層」および「実行環境」を自動割り当てする。

| 対象となる振る舞い・機能 | 割り当てるテスト階層 | 実行環境 | 判定基準 |
| :--- | :--- | :--- | :--- |
| Pureな計算・日時判定・解錠権限などのビジネスロジック | **Domain Unitテスト** | JVM (超高速) | 【MUST】Android依存ゼロ。分岐を最も厚くテストする。 |
| 予約確認〜解錠準備などの一連のフロー・ユースケース | **Application Unitテスト** | JVM (超高速) | 【MUST】外部依存は手書きFakeに差し替えてロジックを通しで検証。 |
| ボタン押下後のLoading/Success表示、UiState/Effect変化 | **Presentation Unitテスト** | JVM (Turbine) | 【MUST】実機描画はせず、ViewModelの受発注ストリームを検証。 |
| Room DBデータの読み書き・ローカル通信 | **Infrastructure Integration** | Robolectric / JVM | 【SHOULD】原則JVM上のRobolectricで回し、実OS挙動要時のみ実機。 |
| FaceMe、カメラX、NFC、実ゲート機器などのハード連携 | **CI対象外 (手動/実機エージェント)** | 実物ハードウェア | 自動テスト化せず、手動または専用検証環境で確認。 |
| ユーザーストーリー（失敗すると業務停止する重要フロー） | **E2Eテスト** | Cloud実機 / Appium | 失敗時に業務停止するユーザーストーリーのみ最少化してNightly実行。 |

**出力時のルール:**
- 各ルールのヘッダー直下に **`推奨テスト階層:`** と **`割り振り理由:`** を出力する。

#### 出力例（アンカー）：
以下は「今すぐ入室」機能を対象とした場合の出力品質の基準例である。実際の出力はこの粒度・記述スタイルに合わせること。

```markdown
## ルールの洗い出しと正常系・異常系の分類

### 機能名: 今すぐ入室
**機能概要:** 空室状態の会議室に対して、顔認証を行い即時予約・入室を行う。

---

### ルール①: 顔情報登録済み従業員の顔なら予約作成＆入室できる
**推奨テスト階層:** Application Unitテスト (JVM)
**割り振り理由:** 認証→権限チェック→予約作成の一連のユースケースフローを通しで検証するため。

| 対象 | 顔情報 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 従業員 | 登録済み | 🟢 正常系：登録済み従業員の顔で認証 | 予約作成＆入室成功 |
| ゲスト | 登録済み | 🔴 異常系：登録済みのゲストが認証 | 権限なしエラー表示 |
| - | 未登録 | 🔴 異常系：顔未登録のユーザーが認証 | 顔未登録時のエラー表示 |
| 従業員 | 登録済み | 🟡 例外系：認証デバイスがタイムアウト | デバイスエラー表示 |

### ルール②: 利用可能時間内のユーザーのみ予約作成＆入室できる
**推奨テスト階層:** Domain Unitテスト (JVM)
**割り振り理由:** 日時比較ロジック（Pure Kotlin）であり、Android依存ゼロで最も高速に検証できるため。

| 対象 | 利用時間 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 従業員 | 時間内 | 🟢 正常系：利用可能時間内に入室 | 予約作成＆入室成功 |
| 従業員 | 時間外 | 🔴 異常系：利用可能時間外に入室試行 | 時間外エラー表示 |

---

### ❓ 疑問点・未確認事項（赤カード）
- [ ] 認証デバイスタイムアウトの具体的な秒数が未定義
- [ ] 利用可能時間の境界値（開始時刻ちょうど、終了時刻ちょうど）の扱いが未確認
```

#### 出力フォーマット形式：

````markdown
## ルールの洗い出しと正常系・異常系の分類

### 機能名: 【仕様書から抽出した機能名】
**機能概要:** 【機能の目的・概要】

---

### ルール①: 【ビジネスルール名（「誰が」「何を」「達成できる／拒否される」の形式）】
**推奨テスト階層:** 【判定マトリクスに基づく階層名】 (【実行環境】)
**割り振り理由:** 【判定マトリクスのどの行に該当し、なぜその階層が最適かの1行説明】

| 対象 | 【因子1】 | 実例（データ・状況の組み合わせ） | 期待される振る舞い |
| :--- | :--- | :--- | :--- |
| 【属性A】 | 【状態1】 | 🟢 正常系：【具体的な組み合わせ】 | 【達成される結果】 |
| 【属性B】 | 【状態2】 | 🔴 異常系：【具体的な組み合わせ】 | 【拒否・エラーの結果】 |
| 【属性C】 | 【状態3】 | 🟡 例外系：【システム起因のエラー条件】 | 【例外時のエラー結果】 |

※因子の列は、ルールに関わる条件軸（顔情報、契約状態、権限設定 等）に応じて適切に追加する。
※必要に応じてルール②、ルール③...と列挙

---

### ❓ 疑問点・未確認事項（赤カード）
- [ ] 【仕様書から読み取れなかった境界値・例外ケース・未定義の仕様】
````

### Step 3: 人間による最終確認と承認 (Review & Apply)

1. 生成したルール・実例ドキュメントをユーザーに提示する。
2. ユーザーへ以下の選択肢を提示し、フィードバックを求める：
   - **「✅ 承認（OK）」** → 対象機能フォルダを作成し、`src/test/resources/features/{機能名}/rules.md` として保存する。
   - **「修正指示（赤カードの回答など）」** → 指摘・回答内容を反映して Step 2 を再実行する。
3. 保存後、次のステップとして `/gherkin-scenario-generator {機能名}` でGherkinシナリオを生成できることをユーザーに案内する。

## Constraints (制約事項)
- **ルール・実例のみ:** 本Skillはビジネスルールと実例の抽出・整理のみを担当する。Gherkinシナリオの生成は `/gherkin-scenario-generator` が担当する。
- **独断による仕様補完の禁止:** 仕様書に記載のない動作を推測で仕様化せず、必ず「赤カード（疑問点）」として抽出して提示すること。
- **1機能1ファイル:** 生成されるドキュメントは 1機能 = 1 `rules.md` ファイルの原則を守ること。
- **フォルダ名:** 仕様書に合わせた機能名を使用する。

---

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md` および `.claude/memories/rule-example-extractor.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

2. **成果物の再生成に伴う自動蓄積（トリガールール）**:
   - ユーザーの指摘や修正指示によって、一度生成した成果物を作り直す場合、成果物を再生成する**前に**、自律的に `.claude/memories/rule-example-extractor.md` へ物理的にファイル編集を行って追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ```
     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象機能**: {引数で受け取った対象機能名}
     - **指摘カテゴリ**: （例: 網羅性の不足、仕様の誤認識、具体性の不足、フォーマット違反 など）
     - **指摘された内容**: （ユーザーからの具体的な修正指示）
     - **原因/理由**: （なぜその問題が発生したかの分析）
     - **今後の対策**: （次回生成時に守るべきルールの言語化）
     ```

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、成果物の再生成も終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、成果物を作り直しました」と必ず報告してください。
