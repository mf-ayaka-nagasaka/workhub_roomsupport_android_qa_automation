# Skill: review-unit-tests
開発チームが作成した単体テストコードを、Gherkinシナリオとの突合を軸にQA視点でレビューし、PRコメント用のレポートを作成します。

## Usage
`/review-unit-tests [pr_number|pr_url|file_path] [feature_name] [scenario]`
例: `/review-unit-tests 183 login RSA-3`
例: `/review-unit-tests 183 login "単数組織に所属するアカウントでログインが完了する"`
例: `/review-unit-tests https://github.com/bitkey-service/gateaccess-android/pull/183 login RSA-3`
例: `/review-unit-tests core/data/src/test/kotlin/.../AuthServiceImplTest.kt login`

- `pr_number`: レビュー対象のPR番号（`gh pr diff` で差分を取得）
- `pr_url`: PRのURL。`{owner}/{repo}` とPR番号を抽出し、`pr_number` と同じ扱いにします
- `file_path`: PR番号の代わりに、ファイルパスを直接指定することも可能
- `feature_name`: 対象機能のディレクトリ名（省略時はStep -1で特定）
- `scenario`: **対象シナリオ**。QaseケースID（`RSA-3` 等）またはシナリオ名で指定します。**開発チームからのレビュー依頼はシナリオ単位で来る**ため、通常はこれを指定してください。省略時はfeature全体が対象になります

## Context / Scope
- **レビュー基準書（最優先参照）**: `docs/unit_test_review_criteria.md`
- **Gherkinシナリオ（網羅チェックの唯一の正本）**: `src/test/resources/features/{feature_name}/scenarios_with_viewpoints.md`
- **レビュー対象リポジトリ（読み取り専用）**: `C:\Users\mforce0087\gateaccess-android`（GitHub: `bitkey-service/gateaccess-android`）

> 同じディレクトリにある `viewpoints.tsv` / `rules.md` / `_master/viewpoints.tsv` は参照しないでください。観点もルール名も `scenarios_with_viewpoints.md` に内包されており、正本を2つ持つと判定がブレます。
- **学習メモリー**: `.claude/memories/global.md` および `.claude/memories/review-unit-tests.md`

## Instructions
あなたはシニアQAエンジニアとして、単体テストコードのレビューを行ってください。

【最重要ルール】:
1. **PRコメントは外向きの成果物です。ユーザーの明確な承認なしに、絶対に投稿しないでください。**
2. **レビュー対象リポジトリのファイルを、本スキルで変更してはいけません（読み取り専用）。**
3. 判定は必ず `docs/unit_test_review_criteria.md` の観点ID（UT-0 〜 UT-6）に紐づけてください。独自の観点を発明しないでください。

実行前に必ず `.claude/memories/global.md` と `.claude/memories/review-unit-tests.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

### Step -1: Gherkinの最新化

**目的**: リポジトリ内のGherkinが古いまま突合すると、網羅性の判定自体が誤りになります。レビュー前に正本を最新化します。

#### -1-1. 対象featureの特定
- 引数 `feature_name` が指定されていればそれを使用します。
- 省略された場合は、PR差分のファイルパス・クラス名から対象機能を推定し、`src/test/resources/features/` 配下の候補を提示してユーザーに確認してください。

**対象シナリオの特定（`scenario` 指定時）**

- `scenario` がQaseケースID形式（`RSA-3` 等）の場合、`scenarios_with_viewpoints.md` 内で当該IDを含むシナリオ行を検索します。
- シナリオ名で指定された場合は、完全一致または部分一致で検索します。
- **1件に特定できない場合（0件 / 複数件）は、候補を提示してユーザーに確認してください。勝手に決めてはいけません。**
- 特定したシナリオの**本体（`前提`/`もし`/`ならば`）と、直後の📐観点ブロック**が突合対象です。それ以外のシナリオは対象外として扱います。
- 対象シナリオと、そのTestLevel・観点の数を報告してください。

#### -1-2. ディレクトリの存在確認
- `src/test/resources/features/{feature_name}/` が存在しない場合、**処理を中断**してください。

  > ⛔ `{feature_name}` のGherkinが未整備のため、レビューを実行できません。
  > 本スキルは「テストすべき観点はすべてGherkin側に盛り込まれている」ことを前提としています。
  > 先にGherkinシナリオを作成してから、再度実行してください。

- **ディレクトリを勝手に新規作成してはいけません。**

#### -1-3. 最新Gherkinの取得
- ユーザーに、**観点つきGherkin**（`scenarios_with_viewpoints.md` に相当する内容）の貼り付けを依頼してください。

  > 📋 `{feature_name}` の最新のGherkinシナリオ（**観点つき**）を貼り付けてください。
  > リポジトリ内の `scenarios_with_viewpoints.md` を、この内容で全文置き換えます。
  > 変更が無ければ「変更なし」と入力してください（既存ファイルをそのまま使用します）。

- 「変更なし」と回答された場合は、既存ファイルをそのまま使用してStep 0へ進みます。

#### -1-4. 差分の提示と承認
- 貼り付けられた内容と既存ファイルの差分を取得し、要約して提示してください（シナリオの増減・観点の増減・文言変更の件数）。
- **全文置換**であることを明示したうえで、承認を求めてください。
- 承認後に `scenarios_with_viewpoints.md` を上書き保存します。承認が得られない場合は更新せず、既存ファイルで続行するか中断するかを確認してください。

> ⚠️ 部分マージはしないでください。Gherkinは生成物であり、部分的な反映は不整合の原因になります。

### Step 0: レビュー対象の特定

#### 0-0. 引数の正規化
第1引数がPRのURLだった場合、`{owner}/{repo}` とPR番号を抽出し、以降は `pr_number` として扱います。

- 抽出したリポジトリが `bitkey-service/gateaccess-android` と異なる場合は、**処理を中断**し、対象外のリポジトリである旨を報告してください。
- 正規化した結果（PR番号）を、処理の冒頭で明示してください。

#### 0-1. 差分の取得
- `pr_number` が指定された場合: `gh pr diff {pr_number} -R bitkey-service/gateaccess-android` で差分を取得します。巨大な差分はコンテキストを圧迫するため、まずファイル一覧（`--name-only` を付与）を取得し、テストコードに絞り込んでから本文を読んでください。
- `file_path` が指定された場合: そのファイルを直接読み込みます。

#### 0-2. 対象外の除外
基準書 `§1.2` に従い、以下を除外します。除外したものはレポートに明記してください。
- `src/androidTest/` 配下
- `ExampleUnitTest.kt`
- 自動生成コード配下のテスト
- `# @TestLevel: E2E (Cloud実機 / Nightly)` に対応するシナリオ

#### 0-3. 対応関係のマッピング
- 変更された各テストが、Gherkinのどのシナリオ・どの📐観点に対応するかを特定します。
- 対応が特定できないテストは **UT-0-1 の指摘候補** として記録してください。
- この時点で「対象テスト件数」「対応するシナリオ件数」を報告してください。

#### 0-4. 早期停止ゲート（対応0件の場合）

**対象シナリオに対応するテストが1件も無い場合、Step 1 へ進まずに停止してください。**

```
⛔ 対象シナリオに対応するテストが見つかりませんでした。

対象シナリオ: {シナリオ名}
変更されたテスト: {n}件（いずれも対象シナリオに紐づきません）

| テスト | 内容 |
|---|---|
| {Class}#{method} | {1行要約} |

考えられる原因:
- 対象PRとシナリオの組み合わせが意図と異なる
- このPRがリファクタリング等で、シナリオの実装を含まない

対象の組み合わせをご確認ください。
このまま品質観点（UT-1〜UT-5）中心のレビューとして続行する場合は「続行」と入力してください。
```

- **「続行」の指示があるまで Step 1 へ進んではいけません。**
- 差分を全件読んでレポートまで作成してから手戻りすると、コンテキストと時間を大きく浪費します。

### Step 1: Gherkinシナリオとの突合（UT-0）

基準書 `§3` に従って実施します。**本スキルで最も重要な工程です。**

#### 1-1. 観点の仕分け（A / B / C）
Gherkinの各シナリオ・📐観点を、基準書 `§3.3` の定義に従って分類してください。

- **A**: 単体テストで検証可能 → 未実装なら **MUST指摘**
- **B**: 単体では検証不可（UI描画・OS設定依存） → **指摘しない。** 手動テストへの申し送りとして記録
- **C**: 単体では検証困難（外部環境・複数端末依存） → **SHOULD。** テストダブルでの代替を検討・提案

> B分類を「漏れている」と指摘してはいけません。開発チームに実現不可能な対応を求めることになります。

#### 1-2. 網羅チェック（UT-0-1 〜 UT-0-6）

| ID | チェック内容 | 重み |
|---|---|---|
| UT-0-1 | 対象テストが、どのfeature・どのシナリオに対応するかを特定できる | MUST |
| UT-0-2 | シナリオ本体（`前提` / `もし` / `ならば`）がテストとして実装されている | MUST |
| UT-0-3 | 📐観点ブロックの各バリエーションが漏れなく実装されている | MUST |
| UT-0-4 | 期待するエラーメッセージの文言が、Gherkin記載と一致している | MUST |
| UT-0-5 | `# @TestLevel:` の指定と、実際のテストの置き場所・粒度が一致している | SHOULD |
| UT-0-6 | 逆方向チェック: Gherkinに存在しないテストが混入していない | SHOULD |

- **UT-0-3 は1行ずつ突き合わせてください。** シナリオ本体だけ実装して観点ブロックを落とすのが典型的な漏れ方です。
- **UT-0-6 で差分を検出した場合**、「テストが余計」なのか「Gherkin側が古い」のかを切り分け、後者であれば**開発への指摘ではなくQAの宿題**としてレポートに分けて記載してください。

### Step 2: ミクロ品質チェック（UT-1 〜 UT-6）

基準書 `§4` に従い、**テストコードとしての作りの良し悪し**のみを精査します。

| ID | 観点 | 主な確認内容 |
|---|---|---|
| UT-1 | 独立性・再現性 | 時刻依存、実行順依存、共有状態の汚染、`runTest` の使用、Dispatcher選択、`MainDispatcherRule` の適用漏れ |
| UT-2 | アサーションの質 | 弱いアサート、曖昧な期待値、1テスト多目的、アサーションライブラリの混在 |
| UT-3 | テストダブルの妥当性 | `mockk(relaxed = true)` の濫用、`coVerify` の過剰指定、モック対象の選択 |
| UT-4 | 可読性・命名 | AAA構造、テスト名の自己説明性、マジックナンバー |
| UT-5 | スコープ適合 | 外部SDK・バックエンドの内部ロジックを検証していないか（CLAUDE.md準拠） |
| UT-6 | `@Qase` の形式 | 必須項目、id重複、title/levelのGherkinとの整合、description、stepsの対応 |

#### 2-1. UT-6 の適用条件

**`@Qase` が既に付与されているテストにのみ適用します。** 未付与を指摘してはいけません。

`@Qase` はレビュー完了後にQAが `/qase-annotation-writer` で付与する工程です（基準書 §4.6 冒頭）。レビュー対象に `@Qase` が1件も無い場合、UT-6 は「**対象外（QAが後工程で付与）**」とレポートの ■6 に明記してください。

#### 2-2. 指摘を出す前のフィルタ

**QAレビューの役目は「観点の抜け漏れが無いか」を見ることです。** 以下に該当する指摘は、観点IDが当てはまる場合でもレポートに載せないでください。

| 除外する指摘 | 理由 |
|---|---|
| 実行時・判定結果に影響しない書き味の話（記法の好み、冗長なセットアップ、コメントの有無） | 開発チームの判断領域です |
| 判定基準が基準書に記載されていない観点 | 根拠を示せない指摘になります。切り分けできない場合は「QA側の宿題」へ回してください |

**UT-2 / UT-4 で指摘を出す場合は、「この指摘が通らないと観点の検証が成立しない、または失敗時に原因を特定できない」ことを説明できるかを確認してください。** 説明できないものは除外します。

> 例: 「1つのテストに2つの観点が入っており、失敗時にどちらが壊れたか切り分けられない」は**残します**。「アサーションの書き方を揃えると読みやすい」は**除外します**。

> **「どの観点をテストすべきか」はStep 1で確認済みです。** 境界値・異常系・状態遷移の過不足をここで再度チェックしてはいけません。それはGherkin側の品質問題であり、本スキルの指摘対象外です。

### Step 3: レポート草案の提示

以下の形式でコンソールに出力してください。**この時点では絶対に投稿しないでください。**

**開発者が読み始めてすぐ「指摘があるのか無いのか」が分かる順序にしてください。** 冒頭の判定ヘッドラインとサマリーを必ず先頭に置きます。

```
【単体テストレビュー】#{pr_number} / feature: {feature_name} / 対象シナリオ: {scenario} / {YYYY-MM-DD}

🔴 要対応: MUST {n}件・SHOULD {n}件
（指摘が1件も無い場合は「✅ 指摘なし」と表示する）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 1. サマリー

| 区分 | 件数 |
|---|---|
| 🔴 MUST（要対応） | {n}件 |
| 🟡 SHOULD（推奨） | {n}件 |
| 🔵 NICE（提案） | {n}件 |
| ⏭️ 手動テストへ申し送り（対応不要） | {n}件 |

■ 2. 指摘一覧

### 🔴 MUST

| # | 観点ID | 該当箇所 | 指摘内容 | 修正方針 |
|---|---|---|---|---|
| 1 | UT-0-3 | {file}:{line} | {指摘} | {方針} |

### 🟡 SHOULD
（同上の形式。無ければ「なし」）

### 🔵 NICE
（同上の形式。無ければ「なし」）

■ 3. シナリオ網羅表（UT-0）

> `scenario` が指定されている場合、網羅表とカバレッジの分母は**対象シナリオのみ**です。同じfeature内の他シナリオは対象外として ■6 に件数のみ記載してください。

| シナリオ / 観点 | 分類 | 対応テスト | 判定 |
|---|---|---|---|
| {シナリオ名} | A | {Class}#{method} | ✅ |
| └ 📐{観点名}: {バリエーション} | A | — | ❌ 未実装 |

| 項目 | 内容 |
|---|---|
| レビュー対象ファイル | {n}件 |
```

> - **修正**: 修正内容を指示してください（草案を作り直します）

ユーザーからの応答を待ちます。**「はい」等の明確な承認を受け取るまで、次へ進んではいけません。**

「修正」と指示された場合は、草案を作り直す**前に**、後述の自己学習ルールに従ってメモリーへ追記してください。

### Step 5: PRコメントの投稿

承認後にのみ実行します。

- 投稿内容を一時ファイルに書き出し、`gh pr comment {pr_number} -R bitkey-service/gateaccess-android --body-file {一時ファイル}` で投稿してください（日本語・改行の欠落を防ぐため、`--body` での直接指定は避けます）。
- 一時ファイルはスクラッチパッドディレクトリに作成し、投稿後に削除してください。
- 投稿後、コメントのURLを報告してください。
- `file_path` 指定で実行された場合（PR番号が無い場合）は投稿を行わず、「投稿先のPRが指定されていないため、レポートの出力のみ行いました」と報告してください。

## Constraints (制約事項)
- **進行制御**: ユーザーの明確な承認なしに、PRへコメントを投稿しないこと。Gherkinファイルも承認なしに更新しないこと。
- **参照元の保護**: レビュー対象リポジトリ（`gateaccess-android`）のファイルは読み取り専用。本スキルでは一切変更しないこと。
- **リポジトリの明示**: `gh` コマンドには必ず `-R bitkey-service/gateaccess-android` を付与すること。カレントディレクトリはQAリポジトリのため、省略すると誤ったリポジトリを操作する。
- **観点の固定**: 判定は基準書の観点ID（UT-0 〜 UT-6）に紐づけること。基準書に無い観点で指摘しないこと。
- **B分類の保護**: UI描画・OS設定に依存する観点を「未実装」として指摘しないこと。
- **コンテキスト保護**: 巨大なPR差分は全文を読み込まず、ファイル一覧で絞り込んでから必要な範囲のみ読むこと。
- **セキュリティ**: 環境URL・テストアカウント・APIキーをレポートに転記しないこと。ハードコードを発見した場合は、**値を引用せず**「ハードコードされている」という事実のみを指摘すること。
- **Gherkin更新の原則**: `scenarios_with_viewpoints.md` の更新は全文置換のみ。部分マージはしないこと。
- **未整備時の中断**: featureディレクトリが存在しない場合は、ディレクトリを作成せず中断すること。
- **レビュー範囲の限定**: `scenario` が指定された場合、突合対象は当該シナリオの本体と📐観点ブロックのみとすること。同じfeature内の他シナリオを網羅チェックの対象にしないこと。
- **早期停止**: 対象シナリオに対応するテストが0件の場合、Step 1 へ進まずに停止し、対象の組み合わせを確認すること。
- **指摘の抑制**: 実行時・判定結果に影響しない書き味の指摘、および判定基準が基準書に無い観点での指摘を出さないこと。後者は「QA側の宿題」へ回すこと。

## 自己学習および指摘の蓄積ルール（最重要）
