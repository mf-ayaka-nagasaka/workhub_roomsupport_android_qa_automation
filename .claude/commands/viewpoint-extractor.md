# Skill: viewpoint-extractor
Gherkinシナリオ（scenarios.md）を入力として、他機能にも展開・再利用できる汎用的なテスト観点を抽出し、仕様書との照合を経て観点マスターおよび観点分岐版Gherkinシナリオを出力するSkillです。

## Usage
`/viewpoint-extractor [対象機能フォルダ名]`

例: `/viewpoint-extractor login`
例: `/viewpoint-extractor initial_setup`

## Context / Scope
- **入力（参照元）**: `src/test/resources/features/{機能名}/scenarios.md`（`/gherkin-scenario-generator` の成果物）
- **照合用仕様書**: `C:\Users\mforce0087\workhubRoomSupport` 配下の対象機能仕様書（現状はiOS版。将来的にAndroid版の対象プロダクト仕様書に切替予定）
- **関連メモリー**: `.claude/memories/viewpoint-extractor.md`、`.claude/memories/global.md`
- **スキル一覧**: `.claude/commands/README.md`
- **成果物出力先**:
  - `src/test/resources/features/{機能名}/viewpoints.tsv`（観点マスター）
  - `src/test/resources/features/{機能名}/scenarios_with_viewpoints.md`（観点分岐版Gherkinシナリオ）

## Instructions
あなたはAndroidアプリのQA・テスト設計パートナーとして振る舞います。
【最重要ルール】: シナリオに特化した固有の値（特定のアカウント名や入力文字列など）をそのまま使わず、**他の機能にも展開・再利用できる汎用的な観点**として抽象化・言語化してください。

### Step 1: Gherkinシナリオと仕様書の読み込み (Load)

> **【必読】このStepを開始する前に、以下のファイルを必ず読み込んでから作業を開始すること：**
> - `src/test/resources/features/{機能名}/scenarios.md`（`/gherkin-scenario-generator` の成果物）
> - `C:\Users\mforce0087\workhubRoomSupport` 内の対象機能仕様書 (.md)
> - `.claude/memories/viewpoint-extractor.md`（存在する場合、過去の指摘事項）
> - `.claude/memories/global.md`

1. 引数で指定された機能名から `src/test/resources/features/{機能名}/scenarios.md` を読み込む。
2. scenarios.md が存在しない場合は、先に `/gherkin-scenario-generator` を実行するようユーザーに案内して終了する。
3. 対応する機能仕様書（.md）を `C:\Users\mforce0087\workhubRoomSupport` から読み込む。
4. scenarios.md から以下の要素を把握する：
   - 機能名・機能概要
   - 各ルールとその配下のシナリオ（正常系・異常系・例外系）
   - E2Eシナリオ

### Step 2: テスト観点の抽出 (Extract)

scenarios.md の各シナリオを分析し、汎用的なテスト観点を抽出する。

#### ガードレール（抽出時の適用ルール）：

##### A. 抽象化の原則
- シナリオの固有名詞（ユーザー名、組織名、具体的なメールアドレス等）は観点に含めない。
- 「ログインが拒否される」→「認証失敗」のように、ビジネス操作をテスト観点レベルに抽象化する。
- 1つの観点が複数機能に適用可能な汎用性を持つよう命名・記述する。

##### B. カバレッジの原則
- **全シナリオが最低1観点に紐づくこと**を保証する。抽出後にカバレッジを検証し、漏れがあれば観点を追加する。
- 正常系だけでなく、異常系・例外系・境界値・画面遷移・状態保持などの観点も網羅する。
- 横断的な観点（エラーメッセージの適切性など、複数シナリオにまたがるもの）も抽出する。

##### C. 要素の充実
- 「要素」列には、シナリオに明示されている値を太い軸とし、同じ観点で一般的に検証されるべき代表値を補完する。
- 要素はテストケース展開時の組み合わせ候補として機能するため、具体的かつ網羅的に列挙する。

##### D. 対象シナリオの紐づけ
- 「対象シナリオ」列には、scenarios.md 内のシナリオ名（`シナリオ:` の後の文言）をそのまま記載する。
- 1観点に複数シナリオが紐づく場合は改行区切りで列挙する。
- E2Eシナリオは、対応する観点（認証成功、条件分岐遷移など）に紐づける。

#### 出力カラム定義：

| カラム名 | 定義 | 記述例 |
| :--- | :--- | :--- |
| **観点名** | 抽象化した短く分かりやすいテスト観点の名称 | 認証成功、通信切断（処理中）、確認ダイアログ |
| **カテゴリ** | 観点の分類 | 操作・状態、異常系、端末・権限、入力、画面遷移 |
| **適用条件** | どういうケース・機能のときにこの観点を考慮すべきか | ログイン・認証機能がある、必須入力項目がある画面 |
| **要素** | 検証すべき具体的なバリエーション（スラッシュ区切り） | 正しいID・PW/単一組織/複数組織/初回ログイン/再ログイン |
| **チェック内容** | 具体的に何を検証すべきか | 有効な認証情報で正常にログインが完了し、次画面へ遷移すること |
| **対象シナリオ** | 紐づくシナリオ名（改行区切り） | 単一組織のアカウントで正しい認証情報を入力するとログインが完了する |

#### 出力例（アンカー）：
以下は「ログイン・組織選択」機能を対象とした場合の出力品質の基準例である。

```tsv
観点名	カテゴリ	適用条件	要素	チェック内容	対象シナリオ
認証成功	操作・状態	ログイン・認証機能がある	正しいID・PW/単一組織/複数組織/初回ログイン/再ログイン	有効な認証情報で正常にログインが完了し、次画面へ遷移すること	単一組織のアカウントで正しい認証情報を入力するとログインが完了する
認証失敗（不正クレデンシャル）	異常系	ログイン・認証機能がある	未登録ID/誤パスワード/ID・PW逆入力/大文字小文字違い/コピペ時前後空白	未登録ID・誤パスワード等でログインが拒否され、適切なエラーメッセージが表示されること	未登録のメールアドレスではログインが拒否される\n誤ったパスワードではログインが拒否される
確認ダイアログ	画面遷移	破壊的・不可逆な操作のボタンがある	確定/キャンセル/ダイアログ外タップ/バックキー/ダイアログ表示中のタスクキル	操作実行前に確認ダイアログが表示され、確定後に正しい画面へ遷移すること	組織選択画面からログアウトするとログイン画面に戻る
```

> **TSV形式の理由:** NotionのデータベースにTSVをそのままコピー＆ペーストで取り込めるため。「対象シナリオ」列で複数シナリオがある場合は `\n`（リテラルなバックスラッシュn）で区切る。

### Step 3: 仕様書との照合 (Verify)

Step 2 で抽出した観点を、Step 1 で読み込んだ仕様書と照合し、矛盾・漏れを検出する。

#### 照合チェック項目：

| チェック観点 | 確認内容 |
| :--- | :--- |
| **エラーメッセージの一致** | シナリオに記載されたエラー文言が、仕様書に定義された文言と一致しているか |
| **画面遷移の整合性** | シナリオの遷移先が、仕様書の画面フロー定義と矛盾していないか |
| **条件・分岐の網羅** | 仕様書に記載された条件分岐が、観点の要素として漏れなく反映されているか |
| **用語の一貫性** | シナリオで使用している用語が、仕様書の用語定義と一致しているか |
| **振る舞いの正確性** | 各観点のチェック内容が、仕様書に記載された期待動作と矛盾していないか |

#### 照合結果の処理：
1. **矛盾が検出された場合**: 矛盾箇所を一覧で提示し、仕様書の記載に基づいて観点・要素を修正してから Step 4 に進む。
2. **矛盾がない場合**: 「仕様書との照合: 矛盾なし」と報告し、Step 4 に進む。
3. **仕様書に記載がなく判断できない場合**: 「赤カード（要確認）」としてユーザーに提示する。

### Step 4: 観点分岐版Gherkinシナリオの生成 (Enhance)

Step 2 で抽出した観点の「要素」を、scenarios.md の各シナリオに反映し、観点分岐版のGherkinシナリオを生成する。

#### ガードレール（生成時の適用ルール）：

##### A. 分岐の判定基準
- 観点の「要素」が複数あり、かつ要素ごとに前提〜ならばのバリエーションを展開する意味があるシナリオのみ分岐対象とする。
- 要素展開の意味が薄いシナリオ（例: アカウントロック等、条件が固定的なもの）は分岐せず、元のシナリオをそのまま維持する。

##### B. フォーマットルール
- `シナリオ:` 表記を維持する（`シナリオアウトライン:` は使用しない）。
- ベースとなる前提〜ならば（代表ケース）を先に記載する。
- その後に `# 📐 観点：{観点名}` コメントを置き、観点の要素ごとの前提〜ならばを列挙する。
- 1つのシナリオに複数観点がある場合は `# 📐 観点：{観点名A}` と `# 📐 観点：{観点名B}` を順に記載する。

##### C. ルール構造の維持
- `# ルール①:` / `# ルール②:` のグルーピング、`# @TestLevel:` コメント、正常系/異常系/例外系の分類コメントはすべて維持する。
- E2Eシナリオは観点分岐の対象外とし、そのまま維持する。

#### 出力例（アンカー）：

```gherkin
  # @TestLevel: ApplicationUnit (JVM)
  # 🔴 異常系：ネットワーク起因のログイン失敗
  シナリオ: ネットワーク障害時はログインが拒否される
    前提 ユーザー "佐藤" は有効なWorkhubアカウントを持っている
    かつ ログイン画面が表示されている
    かつ タブレットがインターネットに接続されていない
    もし 佐藤がログインを実行する
    ならば エラーメッセージ(インターネットに接続されていません)が表示される
    かつ ログインは完了しない

    # 📐 観点：オフライン状態
    前提 タブレットがWi-Fi OFFの状態である
    もし 佐藤がログインを実行する
    ならば エラーメッセージ(インターネットに接続されていません)が表示される

    前提 タブレットが機内モードの状態である
    もし 佐藤がログインを実行する
    ならば エラーメッセージ(インターネットに接続されていません)が表示される

    前提 タブレットがSIM無効の状態である
    もし 佐藤がログインを実行する
    ならば エラーメッセージ(インターネットに接続されていません)が表示される

    # 📐 観点：通信切断（処理中）
    前提 タブレットがインターネットに接続されている
    もし 佐藤がログインを実行し、認証処理中にネットワークが切断される
    ならば エラーメッセージ(認証中にネットワークエラーが発生しました)が表示される

    前提 タブレットがインターネットに接続されている
    もし 佐藤がログインを実行し、レスポンス待ち中にタイムアウトする
    ならば エラーメッセージ(認証中にネットワークエラーが発生しました)が表示される

    前提 タブレットがインターネットに接続されている
    もし 佐藤がログインを実行し、処理中にVPNが切断される
    ならば エラーメッセージ(認証中にネットワークエラーが発生しました)が表示される
```

### Step 5: 人間による最終確認と承認 (Review & Apply)

1. 以下の2つの成果物をユーザーにプレビュー提示する：
   - **観点マスター**: Markdownテーブル形式（視認性のため）
   - **観点分岐版Gherkinシナリオ**: Gherkinコードブロック形式
2. 仕様書との照合結果（矛盾の有無・修正箇所・赤カード）を報告する。
3. プレビューの末尾に、カバレッジ確認結果（全シナリオ数と紐づき状況）を報告する。
4. ユーザーへ以下の選択肢を提示し、フィードバックを求める：
   - **「✅ 承認（OK）」** → 以下の2ファイルを保存する。
     - `src/test/resources/features/{機能名}/viewpoints.tsv`（観点マスター）
     - `src/test/resources/features/{機能名}/scenarios_with_viewpoints.md`（観点分岐版Gherkin）
   - **「修正指示」** → 指摘内容を反映して Step 2 から再実行する。
5. 保存後、NotionDBへの取り込み手順を案内する：
   - 「viewpoints.tsv の内容を全選択→コピーし、Notionのデータベースビューにペーストしてください」

## Constraints (制約事項)
- **観点抽出と観点分岐Gherkinの生成:** 本Skillはテスト観点の抽出・整理、および観点分岐版Gherkinシナリオの生成を担当する。テストケースの生成は行わない。
- **仕様書照合の範囲:** 仕様書との照合はUI挙動（画面遷移・エラーメッセージ・条件分岐）に限定する。内部処理の検証は対象外。
- **汎用性の維持:** 観点名・適用条件・チェック内容は特定機能に依存しない汎用的な表現とすること。対象シナリオ列のみ機能固有の記述を許容する。
- **全シナリオカバレッジ:** scenarios.md 内のすべてのシナリオが最低1観点に紐づくことを保証すること。
- **1機能1ファイル:** 生成される観点マスターは 1機能 = 1 `viewpoints.tsv` ファイル、観点分岐版Gherkinは 1機能 = 1 `scenarios_with_viewpoints.md` ファイルの原則を守ること。
- **入力の前提:** `src/test/resources/features/{機能名}/scenarios.md` が存在することを前提とする。存在しない場合は `/gherkin-scenario-generator` の実行を案内して終了する。

## 自己学習および指摘の蓄積ルール（最重要）

本スキルを実行する際、以下の記憶の読み込みと書き込みのプロセスを必ず実行してください。
【厳守】: 本Skillの定義ファイル自体は絶対に編集・上書きしないでください。

1. **実行前の記憶確認**:
   - タスクを開始する前に、必ず `.claude/memories/global.md` および `.claude/memories/viewpoint-extractor.md` を読み込み、過去の指摘事項を最優先のルールとして適用してください。

2. **成果物の再生成に伴う自動蓄積（トリガールール）**:
   - ユーザーの指摘や修正指示によって、一度生成した成果物を作り直す場合、成果物を再生成する**前に**、自律的に `.claude/memories/viewpoint-extractor.md` へ物理的にファイル編集を行って追記・更新してください。

   **【書き込み・更新の手順】**
   - **① 累積件数の更新**: メモリーファイルの最上部にある「総指摘件数」の数値を +1 カウントアップして上書きしてください。
   - **② 指摘内容の追記**: 既存の内容を消さずに、以下のフォーマットに従ってファイルの末尾に追記してください。

     ```
     ### [YYYY-MM-DD] 指摘事項_{連番}
     - **対象機能**: {引数で受け取った対象機能名}
     - **指摘カテゴリ**: （例: 抽象化の不足、カバレッジ漏れ、要素の不足、カテゴリ分類の誤り など）
     - **指摘された内容**: （ユーザーからの具体的な修正指示）
     - **原因/理由**: （なぜその問題が発生したかの分析）
     - **今後の対策**: （次回抽出時に守るべきルールの言語化）
     ```

3. **完了報告**:
   - 指摘事項のファイルへの書き込み（総件数の更新と末尾への追記）が完了し、成果物の再生成も終わったら、ユーザーへ「指摘内容をメモリーに蓄積し、総指摘件数を〇件に更新した上で、成果物を作り直しました」と必ず報告してください。
