# Skill: pbi-flow-map
PBI・ユーザーストーリー・ルール&実例・Gherkin シナリオが書かれた .md（テスト仕様）から、非エンジニア向けの「処理の全体図」を1枚の .html にする。画面／裏側の処理／残るものを段に分けた流れ図と、テストケースをクリックすると図の該当箇所が光る対応表、エラー文言から止まった場所を逆引きする表を含む。「全体図を html で」「処理の流れを図に」「テストケースがどこの話か分かる図」「フローを平易に図解して」のような依頼、あるいは .md のテスト仕様を渡されて図解・可視化を求められたら、機能の種類（ログイン、予約、通知、設定など）を問わず、"全体図" という言葉が無くてもこのスキルを使う。

## Usage
`/pbi-flow-map [対象機能名]`

例: `/pbi-flow-map login`
例: `/pbi-flow-map initial_setup`
例: `/pbi-flow-map reservation`

## Context / Scope
- **入力（起点）**: `src/test/resources/features/{機能名}/` 配下のテスト仕様書（rules.md, scenarios.md, scenarios_with_viewpoints.md）
- **テンプレート（完成例）**: `src/test/resources/features/_templates/pbi-flow-map-template.html`
- **関連メモリー**: `.claude/memories/global.md`
- **スキル一覧**: `.claude/commands/README.md`
- **成果物出力先**: `src/test/resources/features/{機能名}/{機能名}.html`
  - ファイル名は元の .md（rules.md）の機能名と同じにし、拡張子だけ .html とする
  - 元の .md と同じフォルダに置く

## Instructions
あなたはAndroidアプリのQA・テスト設計パートナーとして振る舞います。
テスト仕様（.md）を読んで、**「このテストケースは処理のどこの話か」を一目で指せる1枚の HTML** を作ります。
読み手は QA や非エンジニア。文章ではなく図で伝え、専門用語は使いません。
機能ごとに1枚作る前提で、どの機能でも同じ手順・同じ見た目にします。
このファイルだけで完結します。外部の雛形や参考ファイルはテンプレート以外ありません。

### 成果物の約束ごと

利用者からの修正指示で固まったもの。守らないと手戻りになる。

- **ファイル名は元の .md と同じ名前で拡張子だけ .html**。元の .md と同じフォルダに置く。
- `<title>` と `<h1>` もファイル名と同じ文言。その上の小さなラベルは `<フォルダ名> ／ 全体マップ`。
- **専門用語はページのどこにも出さない**。切り替えで見せる仕組みも不要。
  サービス名・API 名・トークン名・内部処理名は「利用者にとって何が起きるか」で言い換える。
  例: 「◯◯ Platform 認証」→「本人確認」、「△△ にログイン」→「組織に入る」、
  「カスタムトークンでサインイン」→「データを見る許可をもらう」、「Firestore 書き込み」→「予約を記録する」。
- **「見どころ」「重点」のような推奨セクションは付けない**。どこを重く見るかは読み手が決める。
- **ページ下部に元資料や推測点の注記を書かない**。推測は質問で潰す（手順5）。
- 文章は最小限。説明したくなったら図の要素（矢印ラベル、赤の ✕、青の点線）で表す。
- 見た目と操作は毎回同じ（テンプレートをそのまま踏襲する）。機能ごとに変わるのは図の中身、カード、表の行だけ。

### Step 1: .md を読み、流れを取り出す

> **【必読】このStepを開始する前に、以下のファイルを必ず読み込んでから作業を開始すること：**
> - `src/test/resources/features/{機能名}/rules.md`
> - `src/test/resources/features/{機能名}/scenarios.md`
> - `src/test/resources/features/{機能名}/scenarios_with_viewpoints.md`（存在する場合）
> - `.claude/memories/global.md`

読むところ: 「背景」の処理列挙、「受け入れ条件」、「ルール & 実例」の表、Gherkin の全シナリオ
（打ち消し線のシナリオも、載せるかどうかを後で質問するために拾っておく）。

取り出すもの:

1. **画面**（利用者が見るもの・操作するもの）
2. **裏側の処理**（順番付き）: 受け入れ条件に「A → B → C の順で完了」の形で書かれていることが多い
3. **分岐点**: 「件数が0/1/複数なら」「権限があれば」「期限内なら」のような判定
4. **残るもの**（保存・記録されるもの）と、**中断 → 再開でどこへ戻るか**。
   「タスクキル→再起動」「通信切断後に再試行」系シナリオの期待結果から逆算する
5. **失敗する場所とエラー文言**: 各エラーメッセージがどの処理で出るか

先に「専門用語 → 平易な言葉」の対応表を作ってから図に入る。

### Step 2: 段の構成を決め、解釈を提案する

「処理の全体図」は 画面遷移 / 裏側の処理フロー / 状態（保存）の変化 の3通りに読める。
テストケースを図に当てる用途では **上下に段を重ねた1枚** が最も速い
（画面遷移だけだと「処理中に落ちた」系が置けず、処理フローだけだと「ボタン非活性」系が置けない）。

- 上段「画面（利用者が見るもの）」: 常に置く
- 中段「裏側で起きていること」: 常に置く
- 下段「残るもの（中断したときの戻り先）」: 保存・再開のシナリオがある機能だけ。無ければ2段にする

依頼が曖昧なら、この段構成を「こういうことでは？」と提案しつつ作る。

### Step 3: HTML を組む

> **【必読】以下のテンプレートファイルを必ず読み込んでから作業を開始すること：**
> - `src/test/resources/features/_templates/pbi-flow-map-template.html`
>
> このファイルはログイン機能の完成例である。CSS・JS・全体構造（header / figure / section.index / table）を
> **そのまま踏襲**し、機能ごとに変わるのは以下の部分だけ：
> - `<title>` と `<h1>` のテキスト、`.eyebrow` のフォルダ名
> - `.lead` の説明文（何をしてから何に着くまでを1文）
> - SVG 内の箱・矢印・エラー文言（図の中身）
> - テストケースのカード（`.cards` 内の `.card` と `.group`）
> - エラー文言の表（`<table>` の行）
> - JS 冒頭の `LABEL` オブジェクト（key → 短い表示名）と `SCREEN_KEYS` / `SAVE_KEYS`（チップの色分け用）だったものは、テンプレートの `data-k` 属性によるCSS色分け方式に置き換わっている

**図（SVG）の描き方**

- viewBox は幅 1440。3段なら高さ 560（レーン y=16/156/418）、2段なら 400
- 画面 = 角丸の箱 `screen`（幅 110〜180、高さ 64、上段 y=52）
- 処理 = ①②③… 付きの箱 `step`（幅 150、高さ 64、中段 y=200）。判定 = ひし形 `step-diamond`
- 残るもの = 青い箱 `save-box`（幅 150、高さ 40、下段 y=445）。その下に「再開 → どこへ」を1行
- 緑の実線 `flow` = うまくいく道。箱より先に描く。矢印ラベル `lbl` は短く、
  隣の箱に食い込まないよう `text-anchor="end"` で箱の手前に寄せる
- 赤の ✕ テキスト `err` = その箱で失敗する理由。1行3〜9文字、箱の左端揃えで下に最大3行
  （y=292, 308, 324）。判定から下へ抜ける失敗は `err-line` の短い矢印 + 文言
- 青の点線 `save` = 処理と残るものの結びつき（処理箱の右寄り x から下ろす）、
  開始時の「あれば続きから再開」
- クリック対象は `<g class="hit" data-key="…" tabindex="0" role="button">` で包む。
  key は 画面: 短い英字（`boot` `L` `D` など）、処理: `1` `2` …、残るもの: `A` `B` `C`
- 横の間隔は 40 以上。ラベルは 11px、箱の名前は 13px

**テストケースのカード**

- 実例表と Gherkin シナリオを1件1カード。`data-keys="L,2,3"` に図の key を通る順に列挙
- 緑ドット `dot ok` = 正常系、赤ドット `dot ng` = 異常系
- グループ見出しは元資料の「ルール①」「ルール②」「通し（E2E）」に対応させる
- チップは JS が `data-keys` から自動生成する。JS 冒頭の `LABEL` に key → 短い表示名を入れる

**エラー文言の表**

- 「画面に出る言葉 → 止まった場所」。同じ文言が複数箇所で出るなら「③ 0件のとき ／ ⑤ △△のとき」と併記

### Step 4: 描画を1回だけ確認する

- Playwright は `file://` を開けない。`python3 -m http.server` で配信する
- 日本語ファイル名は URL エンコードしても 404 になることがある。作業用フォルダに
  ASCII 名（`map.html`）でコピーして配信し、確認後に消す
- 幅 1480px でフルページのスクリーンショットを1枚撮って見る。直すのは
  「ラベルが箱に重なる」「文字がはみ出す」のような明らかな崩れだけ。再撮影はしない
- 確認後、サーバーを止め、`.playwright-mcp/` とコピーを消す

### Step 5: 推測した点を質問で潰す

資料から読み取れず推測で描いた点（保存のタイミング、中断後の再開位置、
あるエラーがどの処理で出るか、打ち消し線の機能を載せるか など）は、
**ページに注記せず、完成後に選択肢付きで質問する**。
「現状の図のまま」を第1選択肢にし、答えに応じて図を直す。質問は3〜4件にまとめ、1回で済ませる。

### 報告

最後に、ファイルのパス、採った解釈（段構成の理由）、質問、スキップした確認
（再撮影していない、ダークモード未確認 など）を短く書く。
