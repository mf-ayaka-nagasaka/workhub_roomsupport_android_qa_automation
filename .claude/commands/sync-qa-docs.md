# Skill: sync-qa-docs
開発リポジトリの指定ブランチを最新化してソースコードを分析し、QAリポジトリの機能一覧やテスト観点表との相違点を洗い出します。更新候補をユーザーに提示し、承認を得てからファイルを反映します。

## Usage
`/sync-qa-docs [対象の開発ブランチ名]`
（例：`/sync-qa-docs next-release` や `/sync-qa-docs main`）

## Context / Scope
- **ワークスペース**: `roomsupport_IOS×Android`（ソースコードとQAリポジトリを内包）
- **ソースコード（開発リポジトリ）**: `[Androidソースリポジトリ]`
- **QAリポジトリ**: `workhub_roomsupport_android_qa_automation`
- **対象ドキュメント**:
  - 機能一覧: `workhub_roomsupport_android_qa_automation/docs/test_viewpoints/base/index.md`
  - テスト観点表: `workhub_roomsupport_android_qa_automation/docs/test_viewpoints/base/` 以下の各機能ごとのMarkdownファイル
- **前提条件**: マルチルートワークスペース上で両方のリポジトリが参照・操作できること。

## Instructions
あなたは優秀なシニアQAエンジニアとして振る舞ってください。
以下のステップでタスクを実行してください。必ずステップ1〜2を完了した時点で一度ユーザーに確認を求めてください。

### 1. 環境の準備と最新化 (Setup & Pull)
- 開発リポジトリ（`[Androidソースリポジトリ]`）のディレクトリに移動してください。
- 指定されたブランチ（引数で指定されたブランチ）に切り替え、リモートから最新のソースコードを取り込んでください（`git pull` または `git fetch` 後のマージ）。

### 2. 調査・分析と更新候補の抽出 (Investigation & Diff Check)
- 最新化したソースコードの内容、および直近のコミットログや変更点（`git log` や `git diff`）を分析してください。
- QAリポジトリ側の「機能一覧（`index.md`）」および「各機能のテスト観点表（`base/` 以下のファイル）」を読み込んでください。
- ソースコードの変更点（追加機能、仕様変更、修正）と、現在のQAドキュメントの記述を比較し、**相違している部分（追記・修正が必要な箇所）を「更新候補」として抽出**してください。

### 3. ユーザーへの確認（一時停止）
- 抽出した更新候補を、以下の構成でユーザーに提示し、**「この内容でQAドキュメントを更新して良いか」**確認を求めてください。
  - ソースコード側の主な変更サマリー
  - 機能一覧（`index.md`）の更新候補（差分イメージ）
  - 各テスト観点表ファイルの更新候補（どのファイルのどこをどう変えるか）
- **※ユーザーから「更新OK」の合図（承認）が出るまで、次のステップ（ファイルの書き換え）には進まないでください。**

### 4. 実行・反映 (Action)
- ユーザーから更新の承認を得たら、QAリポジトリ（`workhub_roomsupport_android_qa_automation`）側のディレクトリに移動してください。
- ステップ2で抽出した更新候補に基づいて、機能一覧およびテスト観点表のMarkdownファイルを直接書き換えて更新してください。
- 守るべきルール:
  - 既存のMarkdownの表構造やフォーマットを崩さないこと。
  - 開発側のソースコード（`[Androidソースリポジトリ]`）は読み取り専用とし、絶対に編集・変更を加えないこと。

### 5. 完了報告 (Reporting)
- すべてのファイル更新が完了したら、更新したファイルの一覧を添えて完了報告を行ってください。

## Constraints (制約事項)
- ユーザーの承認なしにQAドキュメント（Markdownファイル）を直接書き換えてはいけません。必ず一度差分を提示して確認を取ってください。
- 既存の重要なテスト観点を、明確な理由なく削除・上書きしないこと。
