- **指摘カテゴリ**: 仕様の誤認識（到達しない分岐をルール化した）
- **指摘された内容**: ルール⑧として「利用不可のときタイムラインは表示されず、画面下部に何も表示されない」と書いたところ、「これってどういうことですか？画面全体が変わると認識した上で見てました」と指摘された。ソースを追い直すと、`checkUnavailableTime()` は **利用時間外のときだけでなく `reservationStatus == .unavailable` のときも `isUnavailableTime = true`** にしており、`MainMenuView` はその時点で画面全体を利用不可の表示へ差し替える。したがって `renderBottom()` の `case .unavailable: Text("")`（画面下部だけが空になる分岐）には**到達しない**。ユーザーの認識どおり「画面全体が変わる」が正しかった。

- **今後の対策**: ①描画の分岐をルール化する前に、**その分岐を含む View が描画される条件を上位までさかのぼって確認する**。上位で画面ごと差し替わる条件がある場合、下位の分岐は到達不能として扱い、ルールにしない。②「〜のときは表示されない」というルールを書いたら、**その状態で画面に何が出ているのかを必ず特定して書く**（「何も出ない」で済ませない）。特定できない場合は赤カードにする。③状態を表す語（利用不可・利用時間外）が複数の内部値に対応している場合は、どの内部値を指すのかを確認してから成果物の語を決める。

  - ②「この設定は判定に使われない」という**否定の振る舞い**をルールにしたが、その設定は予約認証モードでは設定画面に項目自体が出ず、QAが値を変えて確かめることができない。確かめられないものはルールではない。指摘事項_11③・_15① の「その設定が実際に変更できるかを確認する」を、**変更できない設定については『ルールにしない』という結論に結び付けられていなかった**。
- **今後の対策**:
  - ①タップ・長押し・スワイプなど**利用者の操作に対する反応をルール化するときは、実機での確認を前提にする**。参照元にハンドラがあることだけを根拠にしない。実機で確認できていない場合は、ルールに残したうえで**赤カード（実装確認）を必ず添える**。
  - ②「この設定／この値は使われない」という否定のルールは立てない。**QAがその設定を変更できないなら、検証できないので対象外**とし、「責務の切り分け」の表に1行残す。受け入れ条件に書かれていても同じで、依存しないことは他のルールの正常系が通ることで結果的に担保される。

### [2026-11-11] 指摘事項_24
- **対象機能**: 利用不可の表示（Unavailable）
- **指摘カテゴリ**: 用語の不適切（成果物内の他の用語と紛らわしい）／赤カードの立て方（実機と参照元の食い違いを「未実装」と決めつけた）
- **指摘された内容**:
  - ①「利用不可の表示」という用語に対し、「下のメッセージと被っててややこしいので画面にしたらどうですか？」と指摘された。同じ成果物の中に「利用不可の表示」と「利用不可のメッセージ」が並び、どちらを指すのか読み分けられなかった。
  - ②赤カード②（利用不可のメッセージをタップしても何も起きない件）について、「これはiOSで以前意図的に何も起こらないように実装した認識です。iOSに準拠したとしても振る舞いからしたら問題ないように見えるので不要かと」と取り下げを指示された。
- **原因/理由**:
  - ①用語を1つずつ決めており、**成果物の中の用語を並べて読み比べる確認をしていなかった**。「利用不可の◯◯」が2つあると、接頭辞が同じぶん読み手は最後の語でしか区別できない。
  - ②実機の挙動（何も起きない）が参照元のコード（タップの受け口がある）と食い違ったとき、**「受け入れ条件に書いてあるのだから未実装だろう」と推論し、その推論を前提にルールを残して赤カードを立てた**。実際は意図的にそう実装されたもので、振る舞いとして問題が無かった。bdd-workflow-manager 指摘事項_24 の「画面で観測できる問題が無いものは論点にしない」を、受け入れ条件との食い違いという別の形で破った。
- **今後の対策**:
  - ①用語を決めたら、**成果物内の全用語を一覧に並べて読み比べ**、接頭辞・接尾辞が重なって紛らわしいものが無いかを確認する。要素の大きさが違うもの（画面全体／その中の一要素）は、「画面」「メッセージ」のように**別の語種で区別**する。
  - ②実機の挙動が参照元のコードや受け入れ条件と食い違ったときは、**「未実装」を既定にせず、まず『現行の振る舞いで問題があるか』を1問で確認する**。問題が無ければ赤カードは立てず、現行の振る舞いを正としてルールを書き換えるか、対象外として「責務の切り分け」に移す。受け入れ条件に書いてあることは、それ自体が実装の裏付けにならない。

- **対象機能**: 顔認証で利用者を特定できる（FaceAuth）
- **指摘カテゴリ**: 用語の不適切（人物の種別と顔の登録状態を混同）／根拠の薄い境界値の実例／実例の分類の誤り／前提の作り方の誤認（画面を取り違えた）／遷移先の誤り（参照元の実装をAndroid版の動線と突き合わせずに書いた）

  - ⑤ルール②⑥の期待結果を「ホーム画面に戻る」と書いたところ、「Androidは顔認証→認証が通れば予約作成画面や動線ごとの遷移先に遷移します」「照会後の遷移先は予約作成画面／解錠・予約削除・退室・入室の場合はホーム画面」と指摘された。
- **原因/理由**:
  - ①軸は「端末に顔情報が同期されているか」なのに、対象欄に**人物の種別（来訪者）を例として持ち込んだ**ため、種別で決まるかのように読めた。指摘事項_15②（People の種別まで確認してから語を決める）の再発で、今回は「確認せずに種別名を例示した」形。
  - ②指摘事項_8（境界値を置く）を満たすことを優先し、**設定の上限値を使った実例が運用上あり得るかを考えなかった**。参照元の比較が `confidence > similarRate`（超過）であることは裏取りできていたが、「上限値を設定すると誰も認証できなくなる」という**仕様上の疑義**に気づかず、実例として成立するかのように書いた。疑義は実例ではなく赤カードに置くべきだった。
  - ③実例の分類を「利用者の思いどおりにならなかった＝例外」と機械的に判断した。分類の定義（🟡はシステムの状態や外部要因によるエラー）に照らせば、**仕様として用意された案内が出るのは正常系**である。
  - ④画面の呼称を**ソースのファイル名の近さだけで同一視**した。`FacePropertiesDebugView` と `FaceRecognitionDebugView` の2つがあり、管理メニューの項目がどちらへ遷移するか（`AdminMenuViewModel.swift:137` → `FaceRecognitionDebugRoute`）を確認していなかった。指摘事項_14（描画の末端だけを読んで到達経路を確認しない）の再発。
  - ⑤参照元（iOS）は認証成功後に必ず `MainMenuRoute` へ戻り、ホーム側が操作の種類に応じて処理を続ける作りで、**その実装をそのまま期待結果にした**。Android版は動線ごとに遷移先が分かれる作りで、`bdd-workflow-manager` 指摘事項_27 で言語化した「UIの配置・遷移先はAndroid版の方針を優先する」を、同じセッションの別の工程でまた破った。
- **今後の対策**:
  - ①実例の対象欄には、**そのルールの軸に直接関係する属性だけ**を書く。軸が「データの状態」なら人物の種別を例示しない。種別で振る舞いが変わる場合にだけ種別を軸として立てる。
  - ②設定値を変えた実例を書く前に、「**その値を設定した運用が成立するか**」を自問する。成立しない値（上限にすると機能が使えなくなる等）は実例にせず、**仕様の疑義として赤カードに立てる**。
  - ③実例の分類は定義に戻して判定する。**仕様として用意された案内・ガイドが出るケースは🟢正常系**。🔴は誤操作・無効な入力、🟡はシステムの状態や外部要因。利用者が目的を達成できたかどうかで分類しない。
  - ④前提の作り方に画面を挙げるときは、**その画面へ到達する導線（どのメニューのどの項目から開くか）をソースで確認してから書く**。似た名前の画面が複数ある場合は、遷移を指定している箇所（`router.move(to:)`）まで追う。
  - ⑤**認証・操作の後の遷移先を書く前に、Android版の動線が参照元と同じかをユーザーに確認する**。参照元が1画面に集約している処理でも、Android版では画面が分かれていることがある。
