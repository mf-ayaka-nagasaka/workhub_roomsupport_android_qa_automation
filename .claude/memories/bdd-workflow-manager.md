### [2026-09-25] 指摘事項_7
- **対象タスク**: Gherkin生成
- **対象機能**: 予約認証設定の変更
- **指摘カテゴリ**: 過剰削除（テスト階層の誤判断）
- **指摘された内容**: API失敗系の例外系シナリオ（設定保存API失敗・設定コピー登録API失敗）を「ブラックボックスで再現不能」として勝手に削除したが、単体テスト（PresentationUnit / JVM / Turbine）ではAPIモックにより再現可能であるため削除すべきではなかった。
- **原因/理由**: 過去の指摘事項（gherkin-scenario-generator 指摘_1「ブラックボックステストで再現不能なAPI失敗は除外」）を、テスト階層を考慮せず一律に適用してしまった。手動テストで再現不能でも、推奨テスト階層が単体テストであればモックで再現できる。
- **今後の対策**: API失敗系の例外系シナリオの除外判断は「推奨テスト階層」を必ず確認する。PresentationUnit/ApplicationUnit等の単体テスト階層ならモック可能なため含める。除外するのはE2E・手動テスト階層でのみ再現不能なケースに限定する。ユーザーに確認なく勝手に削除しない。

### [2026-09-25] 指摘事項_8
- **対象タスク**: ルール抽出 / Gherkin生成 / 観点抽出
- **対象機能**: 予約認証設定の変更
- **指摘カテゴリ**: 仕様の誤認識（ブロック方式の誤解）
- **指摘された内容**: ルール②を「保存時のバリデーションで予約設定なしスペースの保存を拒否しエラーを表示する」と定義していたが、実際のメカニズムは「予約設定（通常予約またはサードプレイス）のあるスペースのみをスペース選択項目に表示するフィルタリング」であり、選択できないためエラー自体が発生しない。
- **原因/理由**: 仕様書のエラーメッセージ記載をそのまま採用し、UIレベルでの制御方式（表示フィルタリングによるブロック vs 保存時バリデーションによるブロック）を確認しなかった。
- **今後の対策**: ルールの「ブロック方式」を定義する際は、「どのタイミングで・どのUI手段で制御しているか」（表示フィルタリング / 入力制限 / 保存時バリデーション）を区別すること。仕様書にエラーメッセージがあっても、実際のUIがそのエラーを発生させるフローかどうかを確認する。

### [2026-09-29] 指摘事項_9
- **対象タスク**: ルール抽出 / Gherkin生成 / 観点抽出
- **対象機能**: 予約認証モードでの初期設定（initial_setup）
- **指摘カテゴリ**: 仕様の誤認識（ウィザード構造）／網羅性の不足／工程間の約束の不履行
- **指摘された内容**: レビュー指摘を受け、以下が判明した。(1) ウィザードの「設定方法選択（テンプレート/コピーの2択）」と「利用タイプ選択（Standard/Enterprise/ThirdPlace/ビルテナント/カスタム）」が1つのルールに潰れており、利用タイプ選択ステップが丸ごと欠落していた。(2) カスタムは設定方法ではなく利用タイプの選択肢であり、選択時は設定画面へ遷移せず settingState を completed にして即保存する。(3) コピー元0件時は「非表示」ではなく「ボタン非活性」。(4) 今すぐ入室の解錠タイミングの表示条件に誤った前提（解錠機能有効）を付けていた。(5) rules.md の注記で「数値・文字数バリデーションは観点抽出フェーズで網羅する」と約束したが、viewpoints.tsv にも scenarios_with_viewpoints.md にも一切反映されていなかった（マスターには両観点が存在した）。(6) 完了→ホーム到達、完了後の再起動でウィザードが再表示されないこと、各ステップの戻る操作、顔認証有効化済み組織での認証方式選択スキップ、削除確認ダイアログ、保存ボタン連打防止が未カバー。
- **原因/理由**: (a) 仕様書（legacy_initial-setting.md）のページ一覧を読んだだけでソースコードの遷移ロジック（InitialSettingViewModel の SettingType / RoomSupportSettingType の二段構造）まで確認しなかった。(b) 「〜は次工程で担保する」と注記した項目を、次工程で実際に反映したか検証する手順が無かった。(c) iOS版ソースの実装をそのままAndroid版の期待値として採用しかけた（コピー元一覧の常時認証モード除外）。
- **今後の対策**: ①ウィザード型機能では、ページ遷移を司る enum / 状態機械をソースで確認し、ステップの数と各ステップの選択肢を1対1でルール化する。②rules.md に「次工程で担保する」と書いた項目は、Step 3 完了時に viewpoints.tsv / scenarios_with_viewpoints.md へ実際に反映されたかを必ず突き合わせて確認する。③参照元がiOS版仕様・ソースである以上、実装の細部（表示ラベル・一覧の絞り込み範囲など）はAndroid版の期待値と一致しない前提で扱い、差異が疑われる箇所はユーザーに確認する。④完了ステップを持つフローでは「完了後の遷移先」「完了後の再起動時の挙動」を必ず実例に含める。⑤保存・登録ボタンには連打防止（処理中の操作ブロック）の実例を含める。
